# 12 周目の設計と実行手順

工場の 12 周目の設計。8〜11 周目は、作る役の合格率が天井に張り付き、下書き役の系統（Claude / Codex）の差を測れなかった。10 周目は規則の絡みで、11 周目は外部サービスの偽物で難しさを作ろうとしたが、どちらも 4 依頼すべてが天井で、本番を流さずに閉じた（[../lap-11/report.md](../lap-11/report.md)「結論」）。この周は、11 周目の報告の「次の周への候補」1 に挙がった**ブラウザの画面**（factory#4）を難しさの軸にし、天井から下りた依頼で 8 周目と同じ 2×2 を測る。

画面を使う前に要るとされた 2 つ（判定の側の揺れを作る役の落ちと分けること、ブラウザを起こす費用）は、[browser-estimate.md](browser-estimate.md) で測った。結論は条件付きの go で、その条件（判定し直しで結果が変わった組を除く、待ちを抜いたシナリオをゲートで探す）をこの文書で規則にする。

この文書は設計と定義の方針だけを決める。モデルは 1 度も呼んでいない。周も始めていない。読んだ工場のコードは、factory#52 の入った main（6bd68a1）と、factory#55・#56 のコミット（463db75、72f048a・a3c2468・a23909e）である。

**オーナーに決めてほしいこと**は末尾にまとめた。承認されるまで実走しない。

## 言葉

11 周目の手順書と同じ言葉を使う（系統 c / x、組の名前 R-ab-k、腕 cc・cx・xx・xc、D・Ds・Dp、Q、天井、床、帯、絡み、事前の基準、書き直し、工場の側の確かめ）。新しい言葉は次のとおり。

- **画面**: アプリが自分で返す HTML のページ。利用者はブラウザでそこを操作する。依頼ごとに 1〜2 枚。
- **test id**: 画面の要素に付ける `data-testid` の名前。仕様のインターフェースの `testIds` に名前だけが載り、シナリオはこの名前で要素を指す。
- **画面の段**: シナリオの段のうち `"ui"` を持つもの（`goto`・`fill`・`click`）。段の後の `expect` は、画面の見える文字を test id ごとに読み、通るまで最大 5 秒読み直す（`UI_LIMITS.settleMs`）。
- **画面の規則**: 規則（10 周目の言葉）のうち、画面の上でしか確かめられないもの。画面に何が出るか（エラーの文言、並び、件数、表示の形）と、画面の操作がどう効くか（ボタンを押すと何が変わるか、段を戻ると入力が残るか）の 2 種類がある。
- **判定**: build の作業場をシナリオで 1 回採点すること。`replicate` の 1 回目と、`replicate --rescore` の 1 回ずつが、それぞれ 1 回の判定である。
- **判定し直し**: `replicate --rescore`。モデルを呼ばずに、残してある build を同じシナリオでもう一度判定する。factory#56 から、置き換える前の記録を `replicates/history/<build>.<k>.json`（k = 1 が最も古い）に残し、`tally` が判定の間で結果が変わった（シナリオ × build）を表にする。
- **揺れた組**: 3 回の判定（1 回目と判定し直し 2 回）で、合否が変わった（組の名前 × シナリオ × build）。判定の側の揺れとして Q と P から除く（下の「揺れの規則」）。
- **待ちを抜いたシナリオ**: 前の画面の操作の結果を `expect` で確かめないまま、次の操作をするシナリオ。工場は `expect` のある段でしか待たないので、正しいアプリでも落ちたり通ったりする（browser-estimate.md の `race-two-in-order`、20 回中 17 回落ちた）。

この文書の `../lap-11/` などの相対リンクは、factory-notes の `laps/` に置いたときの位置を指す。

## 何を確かめるか

**問い**（8 周目と同じ）: 別の系統のシナリオで、作る役の合格率が下がるか。前提 1「隠せば合わせ込みは防げる」が、同じ系統のシナリオでは過大評価になっていないか、を問う。

**この周の条件**: 作る役が天井に張り付かない依頼で測ること（10・11 周目と同じ）。

**この周で新しく確かめること**: 画面を使う依頼が、予備選別と本番の 2×2（`draft --ui`、`draft --spec-from`、`replicate --score`、`replicate --rescore`）を最後まで通るか。判定の側の揺れが、系統の差や作る役の落ちに見える形で残らないか。

## 難しさの軸の選び方

### なぜ画面か

8〜11 周目で作る役が落ちた点は、どれも API の規則の側にあった。11 周目は、アプリの外の答え（偽物）を足しても天井だった。全員が落ちた 2 本も、偽物とは関係の無い入力の検査の 1 点だった（[../lap-11/report.md](../lap-11/report.md)「全員が落ちたシナリオの読み」）。画面は、作る役が落ちうる場所を 2 つ足す。

1. **同じ振る舞いを、API と画面の 2 か所で正しく出す必要がある。** 画面は API を呼んで描く。API が正しくても、画面がエラーを出さない、並びを変える、古い一覧を残す、といった落ち方がありうる。これまでのシナリオは、アプリの応答しか見ていなかった。
2. **複数の段からなる操作の状態を、画面が持つ。** 段を戻ったときに入力が残るか、取り消しの後に何が出るか、絞り込みを掛けたまま追加したときに一覧に出るか、など。状態がサーバーだけでなく画面にもある。

系統の差の面からは、シナリオの下書き役が「どの段で何を見るか」を自分で選ぶことが効く。11 周目は、Codex の下書き役のほうが要求の確認段をシナリオごとに書いた（[../lap-11/report.md](../lap-11/report.md)「偽物の段の記述」）。画面でも、どこに `expect` を置くかは系統ごとに違いうる。

### 新しい仕組みは画面だけにする

11 周目の runbook は「偽物と画面を同時に初めて使うと、天井から下りたときに、どちらのせいかを分けられない」として画面を後に回した。この周は逆に、偽物を使わない（`--service` を付けない）。依頼は HTTP の API と画面だけを持ち、外部サービスは無い。

### 長さと絡みは 10・11 周目にそろえる

違いを画面だけにするため、依頼の長さと絡みを 10・11 周目の候補の範囲にそろえる。

- 語数は 694〜901 語（10・11 周目の候補の範囲）。
- 事前の基準の絡みは 34 組以上（10・11 周目と同じ線）。
- そのうえで、画面の規則を 8 つ以上含める（11 周目のサービスの規則と同じ下限。下の「事前の基準」）。

### 画面の判定の制約に合わせた依頼の書き方

工場の画面の判定には次の制約がある（`src/browser.ts`、`src/roles.ts` の `UI_STEPS`、README の「browser UI」）。依頼はこの内側で書き、制約にぶつかる形のシナリオが出にくいようにする。

| 判定の制約 | 依頼の書き方 |
|---|---|
| 操作は `goto`・`fill`・`click` だけ。キーボード、ホバー、選択（`<select>`）、ファイル、複数のタブは無い | 画面の操作は、文字の入力欄とボタンだけで書く。選ぶ操作はボタンの並び（「未完了」「完了」「すべて」など）にする。Enter で送る、ドラッグで並べ替える、は依頼に入れない |
| `expect` が読むのは、test id ごとの見える文字（入力欄はその値）だけ。シナリオは、自分で入れた文字か、依頼文が決めた文字しか確かめられない | 確かめさせたい表示は、依頼文が文言と形を決め切る（エラーの文言、金額の書き方、件数の表示、空のときの文言）。見た目（色、位置、強調）は規則にしない |
| test id は仕様の下書き役がインターフェースに名前だけ書く | 依頼文が、画面の要素の名前を挙げる（「入力欄 `titleInput`」「一覧の各行 `taskRow`」）。下書き役ごとに名前が割れて、シナリオが要素を指せなくなる形を避ける |
| 1 画面に test id の付いた要素は 500 個、文字は 64,000 字まで | 一覧は 1 ページの件数を依頼文で決め（20 件程度まで）、それより多い件数は送りで見せる |
| `expect` の読み直しは 1 段 5 秒まで。`expect` の無い段は待たない | 画面の遅さを難しさにしない（browser-estimate.md「12 周目の推奨」）。時間で動く表示（タイマー、数秒後に消える通知、アニメーション）は依頼に入れない。時刻が要るときは、11 周目と同じく API の時計（`POST /clock`）で進める |
| 画面のシナリオは、シナリオ 1 本ごとに新しいアプリと新しいブラウザ | 再読み込み（同じ `goto`）で何が残るかは確かめられる。ブラウザを閉じた後の保存（localStorage など）は依頼に入れない |

### 依頼（候補 4 つ、骨子）

どれも新規のアプリで、HTTP の API と画面 1〜2 枚を持ち、データはメモリに持つ。画面はその API を呼んで描く。外部サービスは無い。規則は 10・11 周目と同じく書き切る。8〜11 周目の依頼は使わない。依頼文（英語、`requests/` に置く）・`rules.json`・定義ファイルは、この骨子が承認された後に書く（末尾の 2）。

難しさは、browser-estimate.md が挙げた 3 つ（入力の検査とエラー表示、絞り込みと並び順、複数の段からなる操作）に分けて置く。4 つ目は 3 つを混ぜる。

| 依頼 | 画面 | 主な画面の規則と、API の規則との絡み |
|---|---|---|
| cart-checkout | 商品の一覧と、かご・会計の 1 枚 | 数量の入力欄ごとの検査（整数、在庫まで）と、項目ごとの決まったエラーの文言。誤りがある間は会計のボタンが効かず、どの行が誤りかを出す。クーポンの条件（最低金額、対象の分類）が合わないときは理由の文言を出し、合計は依頼文の端数の規則と表示の形で出す。会計の後は在庫が減り、一覧の「残り」の表示も変わる |
| task-board | 1 枚（一覧、絞り込みのボタン、文字の絞り込み） | 状態のボタン（「未着手」「作業中」「完了」「すべて」）と文字の絞り込みを重ねる。並びは依頼文の規則（期限、同じなら作成の順）。絞り込み中に追加した項目は、条件に合うときだけ一覧に出る。状態ごとの件数は絞り込みに関係なく出す。最後の 1 操作を取り消すボタンがあり、取り消した後の一覧と件数を決めておく |
| expense-wizard | 3 段の入力（基本、明細、確認）と、提出済みの一覧の 2 枚 | 段ごとの検査と、次の段へ進めないときのエラーの文言。戻ると入力が残り、確認の段から明細を直すと合計が変わる。明細の合計と上限の規則（分類ごと、日ごと）。提出すると番号を振り、一覧は分類ごとの小計を出す。提出を断られたときは番号を振らず、入力を残す |
| room-slots | 日付ごとの枠の一覧と、予約の 1 枚 | 日付の入力で一覧を替え、空き・満席・自分の予約を決まった文言で出す。予約の重なり、1 人あたりの上限、取消の締め切り（API の時計）を、画面の文言とボタンの効き（押せないときの理由）で出す。満席の枠を予約しようとしたときの文言と、その後の一覧の出方を決めておく |

- 4 つとも、作成担当（Claude）が書く。参照実装は作らない（9〜11 周目と同じ）。
- 画面の要素の名前（test id）、確かめさせたい文言と表示の形は、依頼文に書き切る（上の表）。
- 依頼ごとに、画面で確かめにくい振る舞い（保存の中身、並行の操作）は API で確かめられるようにする。シナリオの下書き役は、画面の段と HTTP の段を混ぜて書ける（browser-estimate.md「12 周目の推奨」）。

## 天井を避けられるかの確かめ（2 段、10・11 周目と同じ形）

### 1. 事前の基準（モデルを呼ばない）

11 周目の `rules.json` と `arms.ts --precheck` を使い、候補 4 つを足す。11 周目の印 `service` の代わりに、規則に印 `ui` を付ける（数え方は 11 周目と同じ。画面の規則の定義は上の「言葉」）。

**基準**: 語数が 694〜901 語、絡みが 34 組以上、画面の規則が 8 つ以上。3 つともそろわない候補は外す。外した結果、候補が 2 つ未満になれば、実走の前に窓口に知らせる。

限界も 10・11 周目と同じで、数えるのは作成担当である。

`rules.json` は依頼文と同じ時期に書く（11 周目の PR #26 と同じ形）。11 周目の形に `minUi`（画面の規則の下限）と、依頼ごとの `ui` を足し、`service`・`minService` を外す。較正の 3 依頼（9 周目の厳密版）と、絡みの線（較正の最大の 2 倍で 34）は 11 周目のまま使う。

### 2. 予備選別（11 周目の形に、判定し直しを足す）

- 候補の依頼ごとに `R-cc-p`（`draft --ui`）、`R-cx-p`（`--spec-from R-cc-p`、Codex のシナリオ）、`replicate R-cc-p --k 4 --score R-cx-p --max-cost 15` を流す。
- **選別の build の後に、判定し直しを 2 回かける**（依頼ごとに `replicate R-cc-p --score R-cx-p --rescore` を 2 回）。モデルは呼ばない。1 回目と合わせて 3 回の判定がそろう（下の「揺れの規則」）。
- Q の定義、帯（30 % ≤ Q < 90 %）、床（Q < 30 %）、本番に回す最大の数（3、Q の低い順）は 10・11 周目と同じ（[../lap-10/runbook.md](../lap-10/runbook.md)「予備選別」）。違いは、Q を揺れた組を除いて計算することだけである。
- 置き換えの確かめ（`arms.ts --placeholders`）は 11 周目のまま使う。画面の段の `path` と `text` は、すでに置き換える場所として数えている。

### 揺れの規則（事前に決める。[screen.json](screen.json) と [prereg.template.json](prereg.template.json) の `flakeRule`）

browser-estimate.md「判定の側の揺れを、作る役の落ちと分ける方法」の 1 を規則にしたもの。

- **比べる判定**: build ごとに、同じ工場の版での最後の 3 回（`replicates/history/<build>.<k>.json` と、今の `replicates/<build>.json`）。工場の不具合を直して採点し直したときは、直した工場で判定し直しをさらに 2 回かけ、直した後の 3 回で比べる（直す前の判定と混ぜると、直したことによる変化が揺れに見えるため）。使った判定の番号（k）は `screen-summary.md` に書く。
- **揺れた組**: 3 回のうちで合否が変わった（組 × シナリオ × build）。
- **Q からの除き方**: 揺れた組は、その build のその組の合格割合の分母と分子の両方から除く（その build の残りのシナリオで割合を出す）。3 回とも同じ結果の組は、その結果を使う。シナリオ全体を除くのは、下の読みで待ちを抜いたシナリオと決めたときだけである。
- **記録**: 揺れた組は `screen-flakes.json`（`{"<set>": {"<scenario id>": ["<build>", ...]}}`）に書き、ゲート `main` で `screen-errors.json` と一緒に固定する。`tally` の「Verdicts that changed across judgements」の表と同じ中身になることを確かめる。
- **止める線**: 揺れた組が、ある依頼の（組 × シナリオ × build）の 5 % を超えたら、その依頼の Q を出さず、ゲート `main` の前に窓口に知らせる。browser-estimate.md の見込みは、待ちを正しく書いたシナリオで 1 % 未満である。5 % を超えるなら、待ちの誤りが多いか、本番の負荷で判定の仕組みそのものが揺れている。どちらにしても、除いた後の Q で帯を決めると、測る側の誤りで帯に入った依頼を本番に回すことになる。
- 揺れた組を除いた後に、ある組のシナリオが 1 本も残らない build は、その組の合格割合を出さない。そうなった build がある依頼は、Q を出さず集計を止める（10 周目の `screen-errors.json` と同じ扱い）。

見逃す率（browser-estimate.md）: 待ちを抜いたシナリオの落ちる率を 0.85 とすると、4 build すべてで 3 回とも同じになって見逃す確率は約 15 % である。判定を 5 回にすると約 4 % に下がるが、毎回落ちる・毎回通る誤りは回数を増やしても見つからない。そこで、回数は 3 回にとどめ、下の読みで補う。

### 選別で読むシナリオ（11 周目の「全員が落ちたシナリオ」を広げる）

ゲート `main` の前に、作成担当は次の 2 種類をすべて読む。

- 全員が落ちたシナリオ（10・11 周目と同じ）。
- 揺れた組を 1 つでも持つシナリオ（新しい。browser-estimate.md の 3）。

読む順は 11 周目と同じで、待ちの誤りを足す。

1. **工場を先に疑う。** 落ちた段が画面の段なら、runner の詳細（`failedStep`・`detail`）に出た落ちた確認と、build の作業場の画面の実装を照らす。読んだ画面の全体は結果に残らないので、実装を読んで推し量ったことを `screen-summary.md` に書く。工場の不具合が見つかれば、10・11 周目と同じく lap を止めたまま直し、モデルを呼ばずに採点し直す（上の「比べる判定」と下の「採点し直しの手順」）。
2. **期待値の誤り**（8 周目の規則のまま）。依頼文と食い違う期待値、計算が成り立たない期待値。画面では、依頼文が決めていない文言や見た目を確かめる段もここに入る（`UI_STEPS` は、シナリオ自身が入れた文字か依頼文が決めた文字だけを確かめるよう書いている）。1 本ずつ依頼文の引用を付けて `screen-errors.json` に書く。
3. **待ちの誤り**（新しい）。`expect` の無い画面の段の次に、別の操作（`fill` / `click`）が来るシナリオで、その段の結果が後の段の合否を左右するもの。browser-estimate.md「2. 待ちの書き方を読む」の形である。期待値の誤りと同じく `screen-errors.json` に「wait」として書き、シナリオ全体を Q から除く。factory#55 で下書き役への説明に「次の操作の前に、前の操作で変わるものを `expect` に書く」が入ったので、出る数は減ると見込むが、0 とは決めない。
4. **それ以外は作る役の落ち**として数える（選択の違いを含む）。揺れた組を持つが、工場・期待値・待ちのどれでもないシナリオは、揺れた組だけを除き（上の規則）、残りの組の結果は使う。

ゲート `screen-specs` と `screen` でも、承認者は待ちを抜いたシナリオを探す。見つけたら、そのゲートで止めて書き直すか除くかを決める（build の前なので、採点し直しは要らない）。

## 帯に入らなかったときの扱い

10 周目の「帯に依頼が無いとき」に、この周の形を足す。どれも、ゲート `main` で止まった状態で窓口に知らせ、オーナーが決める。

- **すべて天井**: 本番は流さない。10・11・12 周目と、絡み・外部サービス・画面のどれを足しても天井だった、という結果を報告する。3 周続けて天井になるので、報告の「次の周への候補」には、これまで採らなかった候補（作る役を替える、長さを変える、既存のアプリの拡張）を並べ、どれが問いを変えるかを書く。依頼を難しくした版を、この周の中で作ることはしない（帯に入るまで依頼を作り直すと、選別が依頼を選ぶ寄りが大きくなる）。
- **すべて床、または天井と床だけ**: 床の依頼の全員が落ちたシナリオと揺れた組を、工場の不具合・期待値の誤り・待ちの誤りから読み直す。どれも無ければ、画面の規則が強すぎたという結果として報告する。依頼を緩めた版は、この周では作らない（10 周目と同じ）。
- **揺れの止める線を超えた依頼がある**: その依頼は帯の判定に使わない。工場の不具合なら直して採点し直す（上の「比べる判定」）。待ちの誤りなら `screen-errors.json` に書いて Q を出し直す。どちらでもなく、判定の仕組みそのものが揺れているなら、その依頼は外し、揺れの中身を報告に書く。browser-estimate.md の go の前提（判定の揺れは小さい）が本番の負荷で崩れたことになるので、残りの依頼を本番に回すかどうかもオーナーに諮る。
- **帯に 1 つだけ**: 本番に回す（10 周目の規則で、その依頼の判定は報告するが、前提 1 の判定には使わない）。8 周目から初めて、天井でない依頼で系統の差を測れるので、1 つでも費用（約 $34〜$70）に見合うと見る。回さない選択もある（末尾の 6）。

## 何が言えないか（あらかじめ）

- **長さと絡みは 10・11 周目にそろえるが、同じ依頼ではない。** 題材が違うので、天井から下りても、画面のせいだと 1 つに決めることはできない。言えるのは「10・11 周目と同じ長さ・同じ絡みの線で、画面を足した依頼」についての結果である。
- **画面の段の選び方はシナリオの一部である。** どこに `expect` を置くか、どの振る舞いを画面で、どれを API で確かめるかは、シナリオの下書き役が決めるので、「シナリオの系統」に含まれる。Ds はそれを込みで測る。
- **揺れた組を除くと、Q と P の分母が組ごとに変わる。** 揺れが系統の片方に偏ると、除いた後の差も動く。揺れた組の数を系統ごとに報告に載せ、偏りが大きければ判定を「?」に寄せて読む。
- **判定し直しは同じ機械・同じ負荷の 3 回である。** 毎回落ちる・毎回通る待ちの誤りは見つからない。読みで補うが、読み落としはありうる。待ちを抜いたシナリオの見逃しは、規則の上でも約 15 % 残る（上の「揺れの規則」）。
- **画面の判定の制約に合わせて依頼を書く。** キーボード、選択、ホバー、時間で動く表示、複数のタブは測っていない。実際の画面の難しさの一部だけである。
- **依頼は作成担当（Claude）が書いた。** 事前の基準の数えも作成担当である（10・11 周目と同じ）。
- **予備選別は依頼を選ぶ。** 判定に入る依頼は多くて 3 つで、統計的な検定ではない。U は分類役の読みである。
- 8〜11 周目から引き継ぐ限界（系統 = 1 モデルずつ、Codex の答えたモデルは確かめられない、Codex の費用は回数だけ、lap 台帳にロックが無い、作る役は 1 モデル）。
