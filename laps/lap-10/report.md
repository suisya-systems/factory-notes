# 10 周目の報告（2026-10-23）

工場の 10 周目の結果を報告する。この周のねらいは factory#34 である。8・9 周目は、作る役の合格率が天井に張り付き、下書き役の系統（Claude / Codex）の差を測れなかった。9 周目は依頼の厳密さで難しさを作ろうとして天井だった。そこでこの周は、難しさの軸を規則の絡み（ある応答の正しい値が、複数の規則と前の出来事で決まること）に替え、天井から下りる依頼を予備選別で探した。帯に入る依頼があれば、8 周目と同じ 2×2 を本番で測る計画だった。設計と手順は [runbook.md](runbook.md)、選別の要約は [screen-summary.md](screen-summary.md)、9 周目の報告は [../lap-9/report.md](../lap-9/report.md) にある。

- **窓口の代理承認**: ゲートの承認者を、オーナーでなく窓口（secretary）が務めたこと（下の「ゲートの承認」）。

## 結論

- **4 つの依頼すべてが天井だった。** 予備選別の Q は 94.6〜100.0 % で、帯（30 % ≤ Q < 90 %）に入った依頼は無かった。誤りを除いた後も同じである。
- **本番は流していない。** runbook の「帯に依頼が無いとき（すべて天井）」に従い、本番（8 組 × 依頼ごとの 2×2）は走らせなかった。オーナーが 2026-10-23 に、この形で周を閉じると確認した。lap はゲート `main` で止まったままで、再開していない。
- **言えること。** 9 周目の厳密版より規則が絡んだ依頼（事前の基準で絡み 34〜36 組、9 周目の最大 17 組の 2 倍以上）でも、Claude の作る役（claude-opus-5-5）は、Claude と Codex の両方のシナリオをほぼ通した。「規則をもっと絡ませても、まだ天井」である。
- **言えないこと。** 「系統の差は無い」とは言えない。差を測る本番を回していない。「絡みでは難しくならない」とも言えない（下の「何が言えないか」）。シナリオの系統の効果（前提 1 の問い）は、この周では何も答えていない。
- **費用。** Claude は lap 台帳で **$21.93**（上限 $260 の内側）。Codex は **10 回**（上限 199 回）。

| 組 / シナリオ | 落ちた段 | 分類 | 読み |
|---|---|---|---|
| settle-history-cc-p / weights-history | 9（400 を期待、409） | 作る役の落ち（決まっていない点） | 追加での重複名の状態コードは仕様の Undecided（400 vs 409）で、依頼文も決めていない。シナリオが 400、4 build が 409 を選んだ |

| task-deps-cx-p / unknown-and-foreign-references | 14（400 を期待、404） | 作る役の落ち（決まっていない点） | 別プロジェクトのタスクを `dependsOn` に入れたときの状態コードは仕様の Undecided（400 / 404 / 409）。シナリオが 400、4 build が 404 を選んだ |

- **工場の不具合は 0 本。** 3 本とも落ちた段より前の段（キーや `{{name}}` の置き換えを含む）は通り、落ちた段のリクエストもシナリオどおりに送られていた。置き換えの確かめも 4 組とも問題 0。9 周目のような、系統の書き癖が不具合で差に見える形は、この周の選別には出なかった。
- **期待値の誤りは 1 本。** `screen-errors.json` に載せた（`settle-history-cc-p` の `expense-list-filters`）。これで settle-history の Q は 92.9 から 96.2 % になるが、帯には入らない。

## 何が言えないか（既知の限界）

runbook の「何が言えないか」に沿って、この周の結果で効く限界を書く。

- **依頼は作成担当（Claude）が書いた。** 規則の選び方が、Claude の作る役に有利だった可能性がある。「絡みを増やしても天井」は、「Claude が書いた絡み」についての結果である。
- **長さと絡みを分けていない。** 候補は 694〜901 語で、9 周目の厳密版（408〜499 語）より長い。天井だった理由に、長さと絡みの両方が混ざっている。絡みを増やしても作る役が落ちなかった、とまでは言えるが、絡みだけの効果は分けられない。
- **事前の基準の絡みの数は、作成担当が数えた。** 数え方の偏りは、較正の依頼と候補で同じ手だったが、除けていない。
- **4 依頼 × 4 build と少ない。** 統計的な検定はしていない。Q の差（94.6〜100.0 %）は、この数では依頼ごとの難しさの差とは読めない。
- **作る役は 1 モデル（claude-opus-5-5）である。** 弱い作る役では天井から下りる可能性があるが、それは別の問い（runbook で採らなかった候補）である。
- **前提 1 の問いには答えていない。** 本番を流していないので、別系統のシナリオで合格率が下がるかは、8・9 周目から何も進んでいない。
- **期待値の誤りの除外は、結果を見た後である。** ただし誤りの規則は事前に決めてあり、除外 1 本で結論（4 依頼とも天井）は変わらない。
- **全員が落ちたシナリオのうち、決まっていない点の 2 本は、作る役の落ちとして数えた。** 規則どおりだが、仕様に書かれていない点での割れなので、「作る役が難しさで落ちた」とは読まない。
- **U は分類役（Claude）の読みである。** この周は入口を流さず、U は出していない。
- **1〜9 周目から引き継いでいる限界。** 系統 = 1 モデルずつ。Codex の答えたモデルは確かめられない。Codex の費用は回数だけ。lap 台帳にはロックが無い。

## 次の周への候補（判断はオーナー）

runbook が、天井だった場合の次の候補として挙げたものである。どれも工場の変更が要る。

1. **外部サービスの偽物（#17）。** アプリが外のサービスを呼ぶ依頼を測る。応答の設定と、送った要求の確認の段が要る。8・9 周目に新しい書き方を初めて使った所で工場の不具合が出たので、初めて使う周は、工場の側の確かめを先に置く。
2. **ブラウザの画面（#4）。** 画面の読み取り（見える文字列、待ち）で、作る役の誤りとは別の理由で落ちうる点と、シナリオ 1 本ごとにブラウザを起こす費用の見積もりが先に要る。
3. **既存のアプリの拡張。** `replicate` は新規のアプリしか扱わない（`extends an app; replicate ... only takes new-app changes`）ので、測るには工場の変更が要る。`run` で回すと、やり直しと LLM 判定が入り、8 周目の 2×2 と比べられない。
4. **（参考）作る役を替える、または長さと絡みを分ける。** runbook で今回は採らなかった候補。作る役を替えると、問いが「本番の作る役で前提 1 は成り立つか」から変わる。長さと絡みを分けるには、同じ長さで絡みの少ない版を作る必要がある。
