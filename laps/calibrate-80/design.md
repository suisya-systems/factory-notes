# 合格率 80 % の条件を探す較正の設計

工場の作る役の合格率 Q が、およそ 80 %（帯 30 % ≤ Q < 90 % の中）になる条件を探す較正の設計。10・11・12 周目は、依頼の側に難しさを足す 3 つの軸（規則の絡み、外部サービスの偽物、ブラウザの画面）で天井から下りる依頼を探し、3 周とも 4 依頼すべてが天井だった（[../lap-12/report.md](../lap-12/report.md)「結論」）。オーナーの方針（2026-10-26）は「別軸での検証として、80 % になる条件を探す必要がある」で、改訂の指示は「どの程度の依頼から Opus が 80 % を割るのか、Sonnet ならどうなのかを並行で見ないと」である。

そこで較正を 2 本の系列に分け、並行に回す。

- **系列 O**: 作る役は opus のまま。依頼を段階的に大きくし（既存の依頼を合わせる）、どの大きさから Q が 80 % を割るかを探す。前提 1 の問いは変わらない。
- **系列 S**: 作る役を sonnet にする。既存の 12 依頼で Q を測り、系列 O で作った大きい依頼にも当てる。同じ依頼で opus と sonnet の Q を並べる。

較正は 2×2 の周ではない。予備選別（下書き・作る役の build・採点）だけを使う。80 % 付近の条件が見つかったら、その条件で 2×2 の本番に進む（下の「80 % 付近を見つけた後の道筋」）。

この文書は設計だけを決める。モデルは 1 度も呼んでいない。較正も始めていない。読んだ工場のコードは、factory#62 の入った main（da3de63、12 周目の実行担当の worktree）である。**オーナーに決めてほしいこと**は末尾の 3 点だけにした。ほかの決めごとは、本文に書いたおすすめのとおりに進める。

## 言葉

12 周目の手順書と報告の言葉を使う（系統 c / x、組の名前 R-ab-k、Q、天井、帯、床、判定、判定し直し、揺れた組、期待値の誤り、待ちの誤り）。新しい言葉は次のとおり。

- **較正**: この文書の作業。Q が 80 % 付近になる条件を、予備選別の形で探す。前提 1 の判定はしない。
- **系列 O / 系列 S**: 作る役を opus のままにして依頼を大きくする系列と、作る役を sonnet にする系列。
- **既存の 12 依頼**: 10・11・12 周目の候補の依頼 12 本（下の表）。どれも工場の状態ディレクトリに、承認済みの `R-cc-p`（Claude の仕様とシナリオ）と `R-cx-p`（同じ仕様と Codex のシナリオ）が残っている。
- **合わせた依頼**: 既存の依頼を 2 本または 3 本、1 つのアプリとして書き直した依頼。部品の依頼の規則をすべて持ち、部品の間をつなぐ規則を足す。
- **大きさの段 L0・L1・L2**: L0 は既存の依頼（約 700〜900 語）、L1 は 2 本を合わせた依頼、L2 は 3 本を合わせた依頼。
- **部品の間の絡み**: 合わせた依頼の絡み（10 周目の言葉）のうち、別の部品から来た規則どうしの組。
- **目標の窓**: 70 % ≤ Q < 90 %。帯の上の側で、80 % を中に持つ（下の「目標の窓」）。
- **起動しなかった build**: 作る役が失敗した（`builderOk` が false）か、アプリが立たず、ある組のシナリオの結果が無い build。Q では 0 として数える（12 周目の規則のまま）。

## 何を確かめるか

**較正の問い**:

- 系列 O: 作る役が opus のとき、依頼がどの大きさ（L1・L2）になると Q が 80 % を割るか。
- 系列 S: 作る役が sonnet のとき、L0（既存の 12 依頼）でどこまで下りるか。系列 O の L1・L2 では、opus よりどれだけ低いか。

**較正の後に確かめたいこと**（8 周目からの問い。較正では答えない）: 別の系統のシナリオで、作る役の合格率が下がるか（前提 1「隠せば合わせ込みは防げる」が、同じ系統のシナリオでは過大評価になっていないか）。

**なぜ 80 % か**: 本番の判定の線は、差が 10 点以上で「+」、5 点未満で「0」である（[../lap-10/runbook.md](../lap-10/runbook.md)「計る量」）。本番の天井の印は「8 組すべての P が 95 % 以上」。Q が 80 % なら、上（天井の印まで約 15 点）にも下にも 10 点の差を見る余地がある。50 % 付近でも余地はあるが、作る役の落ちの多くが「作り切れなかった」形になりやすく、シナリオの系統の差が出る前に build 全体が落ちる（下の「落ちの質」）。

**なぜ 2 系列か**: 系列 O だけでは、天井から下りるまで依頼を大きくし続ける費用が読めない。系列 S だけでは、本番の作る役（opus）についての問いが変わる。2 本を並べると、(1) 問いを保てる条件（系列 O）があればそれを本番に使い、(2) 無くても系列 S で本番に進める。さらに (3) 同じ合わせた依頼で opus と sonnet の Q を並べると、「作る役を弱めること」と「依頼を大きくすること」が Q をどれだけ動かすかを、同じ物差しで比べられる。

## 系列 O: 依頼を大きくする（作る役は opus）

### 大きさの段

| 段 | 依頼 | 語数の目安 | 絡みの線 | 依頼の数 |
|---|---|---|---|---|
| L0 | 既存の 12 依頼（測り済み） | 694〜901 | 34 組以上 | 12 |
| L1 | 同じ周の 2 本を合わせる | 約 1,500〜1,800 | 部品の絡みの合計以上、かつ部品の間の絡み 10 組以上 | 3（10・11・12 周目から 1 本ずつ） |
| L2 | 同じ周の 3 本を合わせる | 約 2,300〜2,700 | 同上で、部品の間の絡み 20 組以上 | 3（同上） |

- **同じ周の依頼どうしを合わせる。** 画面（12 周目）・偽物（11 周目）・どちらも無い（10 周目）の違いを、合わせた依頼の中で混ぜないためである。段ごとに 3 本で、3 つの難しさの軸を 1 本ずつ持つ。
- **部品の間の絡みを線にする。** 2 本の依頼を並べただけでは、作る役は部品を別々に作ればよく、難しさは足し算にしかならない。部品の一方の答えが他方の規則に効く文（例: 注文の支払いの状態が出荷の可否を決める）を書き、その組を `rules.json` で数える。
- 部品の規則と文言は、できるだけそのまま残す。合わせた依頼で Q が下がったとき、「大きくなったから」と「規則を書き換えたから」を分けやすくするためである。
- 組み合わせる部品は、作成担当が依頼文を書くときに、データを共有しやすい組から選ぶ（例: 11 周目の ship-orders と pay-refunds は注文を共有する）。L2 は L1 の 2 本に同じ周の 1 本を足す形にし、L1 と L2 の差を「1 本足したこと」に寄せる。
- 画面の依頼（12 周目）を合わせるときは、12 周目の「画面の判定の制約」の表（1 画面 500 要素、一覧の件数、時間で動く表示を入れない、ボタンを無効にしない）をそのまま守る。12 周目の空になった要素の読み（`pageMessage` などが消えたときの長さ）は、合わせた依頼の文で「消える」の意味を決めて避ける（12 周目の報告の候補 4）。

### 段の進め方

1. 作成担当が L1 の 3 依頼と `rules.json` を書き、`arms.ts --precheck` で語数と絡みの線を確かめる（モデルを呼ばない）。
2. L1 の予備選別を、12 周目の予備選別と同じ形で流す（`draft` で `-cc-p`、`--spec-from` で `-cx-p`、`replicate --k 4 --score`、判定し直し 2 回）。ゲート `screen-specs` と `screen` は窓口が承認する（12 周目と同じく、承認者は待ちを抜いたシナリオを探す）。
3. L1 の Q で分ける。

| L1 の結果 | 次 |
|---|---|
| Q < 80 % の依頼がある | 80 % を割る大きさは L1 で見つかった。L2 は流さない。窓（70〜90 %）に入る依頼を本番の候補にする |
| すべて 90 % 以上 | L2 へ |
| 80 % 以上 90 % 未満だけ | 窓には入っている。L2 で 80 % を割るかを見るかは、費用の止める線の内側なら流す（割る大きさを決めるため）。本番の候補は L1 の依頼 |

4. L2 の Q も同じ表で読む。L2 でもすべて 90 % 以上なら、系列 O は「3 本を合わせても天井」で閉じる。L3（4 本を合わせる、約 3,300 語）は、オーナーに諮るまで書かない。

- **依頼を直して流し直すことはしない**（12 周目の規則と同じ。帯に入るまで依頼を作り直すと、選別が依頼を選ぶ寄りが大きくなる）。L1 で期待値の誤りが多かったときは、12 周目と同じ規則で除いて Q を出す。
- 系列 O の L1・L2 は、それぞれ新しい状態ディレクトリ（`.factory-cal80-o1`・`.factory-cal80-o2`）で流す。lap 台帳を段ごとに分け、費用を段ごとに読むためである。

### 長い依頼で効きうる工場の限界

- 作る役の 1 呼び出しは $5 と 20 分で切られる（`CAPS.builderCallUsd`、`CAPS.modelTimeoutMs`）。L2 の opus の build がこれに当たると、起動しなかった build になる。当たった build は数を記録し、下の「落ちの質」で読む。上限を上げるのは工場の変更（下の G）で、当たったときに諮る。
- シナリオの本数は下書き役が決める。依頼が大きくなっても本数が 12〜15 本のままなら、規則あたりの確かめが薄くなり、Q は下がりにくい。段ごとにシナリオの本数と段の数を記録し、報告で L0 と並べる。

## 系列 S: 作る役を sonnet にする

### 段 S0: 今の工場で既存の build を判定し直す（モデルを呼ばない、$0）

- 既存の 3 つの状態ディレクトリを、工場の今の main の worktree に写す（`.factory-cal80-lap10`・`.factory-cal80-lap11`・`.factory-cal80-lap12`）。10〜12 周目の記録に較正の build と判定を混ぜないためと、判定をすべて今の main（factory#62 の後）でそろえるためである。写した lap 台帳には各周の費用（$21.93〜$23.79）が入っている。較正の費用は差分で数える。
- 3 つの写しのそれぞれで、12 依頼の `replicate <own> --score <cross> --rescore` を 3 回ずつかける。揺れの規則は build ごとに最後の 3 回の判定を比べるので、2 回では古い工場の版の判定が 1 回混ざり、工場の直しで変わった合否を揺れと読み違える（12 周目の「比べる判定」で、直した後の 3 回で比べるとしたのと同じ理由）。
- 確かめること: (1) 今の工場が、10・11 周目の状態ディレクトリを読んで採点できるか。(2) 今の工場での opus の Q（上の表と同じになるはずで、変われば工場の版の違いを先に読む）。読み違いや採点の失敗が出たら、モデルを呼ぶ前に止めて窓口に知らせる。
- 合わせて、sonnet の作る役で隔離の確かめ（`probe-isolation`、作る役の役で 1 回）を流す。これはモデルを呼ぶ（5 周目の sonnet で $0.06）。

### 段 S1: 既存の 12 依頼の下見（依頼ごとに 2 build）

- 12 依頼それぞれで、`replicate <own> --k 2 --score <cross> --max-cost 15 --model builder=claude-sonnet-5-5` を流す。24 build。
- build の後に、依頼ごとに判定し直しを 2 回かける（$0）。揺れの規則は 12 周目のまま（[../lap-12/runbook.md](../lap-12/runbook.md)「揺れの規則」）。
- 依頼ごとに、sonnet の 2 build だけで下見の Q を出す（opus の build は数えない）。2 build の Q はぶれが大きいので、ここでは見当をつけるだけにする。

| 下見の結果 | 次 |
|---|---|
| 下見の Q が 60 % ≤ Q < 95 % の依頼がある | 段 S2 へ。該当する依頼のうち、80 % に近い順に最大 6 本 |
| すべて 95 % 以上（sonnet でも天井） | 段 S2 は流さない。L0 では sonnet も天井、という結果として記録する。段 S3 は流す |
| すべて 60 % 未満 | 段 S2 は流さない。起動しなかった build の割合と、全員が落ちたシナリオを読む。作り切れなかった落ちが主なら、sonnet はこの長さでも弱すぎる。段 S3 は止めて諮る（L1・L2 ではさらに落ちるので、測る意味が薄い） |
| 上のどれでもない（60 % 未満と 95 % 以上の依頼だけ） | 段 S2 は流さない。60 % 未満の側を上の行と同じく読み、記録する。段 S3 は流す |

- 60 % と 95 % は、2 build の下見のぶれを見込んだ広めの線である。目標の窓（70〜90 %）の外でも、4 build で窓に入りうる依頼を落とさないようにした。

### 段 S2: 既存の依頼の測り（段 S1 で残った依頼に 2 build を足す）

- 残った依頼（最大 6 本）に、同じ形で `--k 2` を足す（build 3・4）。sonnet の build は依頼ごとに 4 本になる。
- 判定し直しを 2 回かけ、sonnet の 4 build × 2 組で Q を出す。Q の定義・揺れの規則・期待値の誤りの規則は 12 周目のまま（`screen.json` の `errorsRule` と `flakeRule`）。
- 12 周目と同じく、全員が落ちたシナリオと、揺れた組を持つシナリオを読む（工場を先に疑う → 期待値の誤り → 待ちの誤り → 作る役の落ち）。opus の 4 build がすべて通っていたシナリオを sonnet が全員落とした場合も、期待値の誤りではないかを読む（opus の通過は傍証にはなるが、決め手にはならない）。

### 段 S3: 系列 O の合わせた依頼に sonnet を当てる

- 系列 O の L1（と、流したなら L2）の `-cc-p` に、`replicate <own> --k 4 --score <cross> --model builder=claude-sonnet-5-5` を流し、判定し直しを 2 回かける。系列 O の状態ディレクトリの中で流すので、opus の 4 build と sonnet の 4 build が同じ仕様・同じシナリオで採点される。
- 下見は挟まない。依頼が 3 本ずつしか無く、opus と並べるには 4 build ずつそろえる必要があるからである。
- **同じ `-cc-p` では、opus の build が終わってから流す。** build の名前は作る役のモデルで分かれるが、費用の記録 `runs/<id>/replicate-cost.json` は変更ごとに 1 つで、`replicate` は始めに 1 回読み、自分の費用だけを足して書き戻す（`src/replicate.ts`）。同じ変更に 2 本を同時に流すと、後に書いた方が前の方の費用を消し、`--max-cost` の確かめも少なく数える。別の依頼の `-cc-p` どうしなら同時に流してよい（例: 依頼 1 の sonnet と依頼 2 の opus）。ゲート `screen` を通って `-cx-p` が承認された後に限るのも同じ（`--score` が承認済みの組を要るため）。

### 系列 S の結果の並べ方

| 依頼の大きさ | opus の Q | sonnet の Q |
|---|---|---|
| L0（既存の 12 依頼） | 上の表（段 S0 で今の工場で出し直す） | 段 S1・S2 |
| L1（3 依頼） | 系列 O | 段 S3 |
| L2（3 依頼、流したとき） | 系列 O | 段 S3 |

この表で、「大きさを 1 段上げると Q がどれだけ下がるか」と「作る役を sonnet にすると Q がどれだけ下がるか」を、同じ依頼で比べる。

## 2 系列を同時に回す順番

系列 O は依頼文を書くまでモデルを呼べず、系列 S は依頼文が要らない。そこで、系列 O の依頼文づくりの間に系列 S の L0 を回す。

| 時期 | 系列 O | 系列 S | 待ち合わせ |
|---|---|---|---|
| 1 | 作成担当が L1 の 3 依頼と `rules.json` を書き、`--precheck` を通す（モデルを呼ばない）。道具 A・B・E・F を書く | 道具 A・B が入りしだい、段 S0（判定し直し、隔離の確かめ） | 系列 S の段 S1 は道具 A・B の後 |
| 2 | L1 の下書き（`-cc-p`・`-cx-p`）、ゲート `screen-specs`・`screen` | 段 S1（24 build）、続けて段 S2 | なし（状態ディレクトリが別） |
| 3 | L1 の opus の build（12 build）と判定し直し | 段 S3（L1 に sonnet の 12 build） | L1 のゲート `screen` の後。同じ依頼では opus の build が終わってから sonnet（下の段 S3）。依頼をずらせば 2 系列は重ねられる |
| 4 | L1 の結果で分かれ道。L2 へ進むなら L2 の依頼文を書き、時期 2・3 と同じ形で流す | L2 を流したなら、段 S3 を L2 にも | L2 のゲート `screen` の後 |

- 系列 O の L1 と L2 は順番に流す（L1 の結果で L2 を流すかが決まるため）。L2 の依頼文を L1 の結果の前に書いておくと時間は縮むが、L1 で割れたときに書いた分が無駄になる。L2 の依頼文は L1 の結果を見てから書く。
- ゲートの承認は窓口が行う（12 周目のオーナー判断 8 の「後のゲートは窓口に任せてよい」の形）。系列 O の L1 の `screen-specs` だけは、合わせた依頼を初めて読むゲートなので、オーナーが読みたければ止めて待つ。

## 選ぶ規則（2 系列共通）

### 目標の窓

- **70 % ≤ Q < 90 %。** 80 % を中に持ち、上は帯の天井の線（90 %）と同じにした。
- 4 build × 2 組の Q は、build ごとの合格割合の平均である。build ごとの割合が 10 点ほどばらつくとすると、4 build の平均のぶれは約 5 点で、「80 % 付近」は実際には 70〜90 % の幅でしか言えない。窓を ±10 点にしたのはこのためである。
- 窓を狭くするには build を増やす必要があり、1 依頼 4 build ずつ費用が増える。較正では広めの窓で選び、本番の build（1 仕様 8 本）で Q の位置を測り直す。
- 「80 % を割る」は、系列 O の段の分かれ道でだけ使う（Q < 80 %）。本番の候補は、割ったかどうかではなく窓に入ったかで選ぶ。

### 落ちの質（目標の窓に入っても選ばない依頼）

Q を 80 % に下げたいのは、シナリオの系統の差が見える余地を作るためである。作る役が作り切れず、build ごと全部落ちる形で Q が下がっても、その余地はできない。そこで次の依頼は、窓に入っても選ばない。

- 4 build のうち、起動しなかった build が 2 本以上ある依頼。
- 起動した build だけで出した Q が 90 % 以上の依頼（窓に入ったのが、起動しなかった build の 0 によるだけのとき）。

起動しなかった build の数と、起動した build だけの Q は、選ばなかった依頼も含めて記録に残す。

## 何が言えないか（あらかじめ）

- **系列 S の条件では、前提 1 の問いが変わる。** 本番の結論は「sonnet の作る役で、別の系統のシナリオは合格率を下げるか」になる。工場が本番で使う作る役（opus）について同じことが言えるかは、系列 S からは答えられない。系列 O で条件が見つかれば、この限界は無くなる。
- **系列 O は、大きさと題材の組み合わせを同時に変える。** 合わせた依頼は部品の間の絡みも持つので、Q が下がっても「長さだけのせい」とは言えない。言えるのは「L1（L2）の作り方で合わせた依頼」についての結果である。部品の規則を残す書き方で、規則を書き換えたせいかどうかは読みやすくした。
- **合わせた依頼は作成担当（Claude）が書く。** 部品の間の規則の選び方が、Claude の作る役に有利だった可能性がある（10〜12 周目と同じ限界）。

- **シナリオは 10〜12 周目のものを使い回す（系列 S の L0）。** 下書き役は作る役のモデルを知らないので、作る役を替えても採点の条件は同じである。期待値の誤りは各周で読んだもの（`screen-errors.json`）をそのまま使い、sonnet の build で新しく見つかったものは同じ規則で足す。10・11 周目の仕様とシナリオは、古い工場の版の下書き役の出力のままである。
- **長い依頼では、シナリオの確かめが薄くなりうる。** シナリオの本数は下書き役が決めるので、依頼が大きくなっても本数が増えなければ、Q は下がりにくい。段ごとの本数を記録するが、確かめの濃さをそろえることはしない。
- 8〜12 周目から引き継ぐ限界（系統 = 1 モデルずつ、Codex の答えたモデルは確かめられない、Codex の費用は回数だけ、lap 台帳にロックが無い）。
