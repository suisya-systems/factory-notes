# 合格率 80 % の条件を探す較正の設計

工場の作る役の合格率 Q が、およそ 80 %（帯 30 % ≤ Q < 90 % の中）になる条件を探す較正の設計。10・11・12 周目は、依頼の側に難しさを足す 3 つの軸（規則の絡み、外部サービスの偽物、ブラウザの画面）で天井から下りる依頼を探し、3 周とも 4 依頼すべてが天井だった（[../lap-12/report.md](../lap-12/report.md)「結論」）。オーナーの方針（2026-10-26）は「別軸での検証として、80 % になる条件を探す必要がある」である。

この較正は 2×2 の周ではない。予備選別（作る役の build と採点だけ）を使い、難しさのつまみを段階的に動かして Q を測る。80 % 付近の条件が見つかったら、その条件で 2×2 の本番に進む（下の「80 % 付近を見つけた後の道筋」）。

この文書は設計だけを決める。モデルは 1 度も呼んでいない。較正も始めていない。読んだ工場のコードは、factory#62 の入った main（da3de63、12 周目の実行担当の worktree）である。**オーナーに決めてほしいこと**は末尾にまとめた。承認されるまで実走しない。

## 言葉

12 周目の手順書と報告の言葉を使う（系統 c / x、組の名前 R-ab-k、Q、天井、帯、床、判定、判定し直し、揺れた組、期待値の誤り、待ちの誤り）。新しい言葉は次のとおり。

- **較正**: この文書の作業。Q が 80 % 付近になる条件を、予備選別の形で探す。前提 1 の判定はしない。
- **つまみ**: Q を動かすために変える条件 1 つ（作る役のモデル、依頼の長さ、など）。
- **段（較正の）**: つまみを 1 つ決めて、依頼の集まりで Q を測る 1 回分。段ごとにオーナーの承認を取る。
- **既存の 12 依頼**: 10・11・12 周目の候補の依頼 12 本（下の「既存の 12 依頼」）。どれも工場の状態ディレクトリに、承認済みの `R-cc-p`（Claude の仕様とシナリオ）と `R-cx-p`（同じ仕様と Codex のシナリオ）が残っている。
- **目標の窓**: 70 % ≤ Q < 90 %。帯の上の側で、80 % を中に持つ（下の「目標の窓」）。
- **起動しなかった build**: 作る役が失敗した（`builderOk` が false）か、アプリが立たず、ある組のシナリオの結果が無い build。Q では 0 として数える（12 周目の規則のまま）。

## 何を確かめるか

**較正の問い**: どのつまみを、どこまで動かすと、既存の依頼で Q が目標の窓に入るか。

**較正の後に確かめたいこと**（8 周目からの問い。較正では答えない）: 別の系統のシナリオで、作る役の合格率が下がるか（前提 1「隠せば合わせ込みは防げる」が、同じ系統のシナリオでは過大評価になっていないか）。

**なぜ 80 % か**: 本番の判定の線は、差が 10 点以上で「+」、5 点未満で「0」である（[../lap-10/runbook.md](../lap-10/runbook.md)「計る量」）。本番の天井の印は「8 組すべての P が 95 % 以上」。Q が 80 % なら、上（天井の印まで約 15 点）にも下にも 10 点の差を見る余地がある。50 % 付近でも余地はあるが、作る役の落ちの多くが「作り切れなかった」形になりやすく、シナリオの系統の差が出る前に build 全体が落ちる（下の「落ちの質」）。

## 手順（段を分けて、つまみを 1 つずつ）

### 置き場所: 状態ディレクトリの写し

既存の 3 つの状態ディレクトリを、工場の今の main の worktree に写して使う（`.factory-cal80-lap10`・`.factory-cal80-lap11`・`.factory-cal80-lap12`）。理由は次の 2 つ。

- 10〜12 周目の記録（lap 台帳、replicates、history）に、較正の build と判定を混ぜない。
- 10・11 周目の状態ディレクトリは、古い工場の版の worktree にある。較正の判定は、すべて今の main（factory#62 の後）でそろえる。

写した lap 台帳には各周の費用がそのまま入っている。較正の費用は、写した後に増えた分（差分）で数える。lap あたりの上限 $260 は写した台帳の合計に効くが、各周の合計は $21.93〜$23.79 なので届かない。

### 段 0: 今の工場で既存の build を判定し直す（モデルを呼ばない、$0）

- 3 つの写しのそれぞれで、12 依頼の `replicate <own> --score <cross> --rescore` を 3 回ずつかける。opus の 4 build に、今の工場の判定が 3 回足される。揺れの規則は build ごとに最後の 3 回の判定を比べるので、2 回では古い工場の版の判定が 1 回混ざり、工場の直しで変わった合否を揺れと読み違える（12 周目の「比べる判定」で、直した後の 3 回で比べるとしたのと同じ理由）。
- 確かめること: (1) 今の工場が、10・11 周目の状態ディレクトリを読んで採点できるか（11 周目は偽物の段を使う）。(2) 今の工場での opus の Q（12 周目の表と同じになるはずで、変われば工場の版の違いを先に読む）。
- 段 0 で読み違いや採点の失敗が出たら、モデルを呼ぶ前に止めて窓口に知らせる。
- 合わせて、sonnet の作る役で隔離の確かめ（`probe-isolation`、作る役の役で 1 回）を流す。これはモデルを呼ぶ（5 周目の sonnet で $0.06）。

### 段 1: K1 の下見（sonnet、依頼ごとに 2 build）

- 12 依頼それぞれで、`replicate <own> --k 2 --score <cross> --max-cost 15 --model builder=claude-sonnet-5-5` を流す。24 build。
- build の後に、依頼ごとに判定し直しを 2 回かける（$0）。揺れの規則は 12 周目のまま（[../lap-12/runbook.md](../lap-12/runbook.md)「揺れの規則」。最後の 3 回の判定で合否が変わった組を除く）。
- 依頼ごとに、sonnet の 2 build だけで下見の Q を出す（opus の build は数えない）。
- 下見を 2 build にするのは、12 依頼のうちどこが下りるかの見当をつけるためである。2 build の Q はぶれが大きい（下の「目標の窓」）。

### 段 1 の後の分かれ道

| 下見の結果 | 次 |
|---|---|
| 下見の Q が 60 % ≤ Q < 95 % の依頼がある | 段 2 へ。該当する依頼のうち、80 % に近い順に最大 6 本 |
| すべて 95 % 以上（sonnet でも天井） | 段 2 は流さない。K2（Haiku の世代、工場の変更が要る）か K5（依頼を長くする）を、オーナーに諮る |
| すべて 60 % 未満 | 段 2 は流さない。起動しなかった build の割合と、全員が落ちたシナリオを読む。作り切れなかった落ちが主なら、sonnet は弱すぎる。opus に戻して K5 を諮る |
| 上のどれでもない（60 % 未満と 95 % 以上の依頼だけ） | 段 2 は流さない。60 % 未満の側を上の行と同じく読み、95 % 以上の側と合わせて、K2・K5 のどちらか、または較正を止めるかをオーナーに諮る |

- 60 % と 95 % は、2 build の下見のぶれを見込んだ広めの線である。目標の窓（70〜90 %）の外でも、4 build で窓に入りうる依頼を落とさないようにした。

### 段 2: K1 の測り（段 1 で残った依頼に 2 build を足す）

- 残った依頼（最大 6 本）に、同じ形で `--k 2` を足す（build 3・4）。sonnet の build は依頼ごとに 4 本になる。
- 判定し直しを 2 回かけ、sonnet の 4 build × 2 組で Q を出す。Q の定義・揺れの規則・期待値の誤りの規則は 12 周目のまま（`screen.json` の `errorsRule` と `flakeRule`）。
- 12 周目と同じく、全員が落ちたシナリオと、揺れた組を持つシナリオを読む（工場を先に疑う → 期待値の誤り → 待ちの誤り → 作る役の落ち）。opus の 4 build がすべて通っていたシナリオを sonnet が全員落とした場合も、期待値の誤りではないかを読む（opus の通過は、期待値が正しい傍証にはなるが、決め手にはならない）。
- **選ぶ依頼**: Q が目標の窓に入り、落ちの質の条件（下）を満たす依頼を、80 % に近い順に最大 3 本。

### 落ちの質（目標の窓に入っても選ばない依頼）

Q を 80 % に下げたいのは、シナリオの系統の差が見える余地を作るためである。作る役が作り切れず、build ごと全部落ちる形で Q が下がっても、その余地はできない。そこで次の依頼は、窓に入っても選ばない。

- sonnet の 4 build のうち、起動しなかった build が 2 本以上ある依頼。
- 起動した build だけで出した Q が 90 % 以上の依頼（窓に入ったのが、起動しなかった build の 0 によるだけのとき）。

起動しなかった build の数と、起動した build だけの Q は、選ばなかった依頼も含めて記録に残す。

### 目標の窓

- **70 % ≤ Q < 90 %。** 80 % を中に持ち、上は帯の天井の線（90 %）と同じにした。
- 4 build × 2 組の Q は、build ごとの合格割合の平均である。build ごとの割合が 10 点ほどばらつくとすると、4 build の平均のぶれは約 5 点で、「80 % 付近」は実際には 70〜90 % の幅でしか言えない。窓を ±10 点にしたのはこのためである。
- 窓を狭くするには build を増やす必要があり、1 依頼 4 build ずつ費用が増える。較正では広めの窓で選び、本番の build（1 仕様 8 本）で Q の位置を測り直す。

### K1 で見つからなかったときの次の段（承認ごと）

- **K2（Haiku の世代）**: 工場の変更 C（下）を入れた後、段 1・段 2 と同じ形で流す。K1 で天井だった依頼を対象にする。
- **K5（依頼を長くする）**: 既存の 12 依頼から、同じ周の 2 本を合わせた依頼を 3 本書く（同じ周の 2 本なら、画面・偽物の有無がそろう）。作る役は opus のまま。下書き（`-cc-p`・`-cx-p`）と分類が要るので、12 周目の予備選別と同じ形で流す。
- K2 と K5 のどちらを先にするかは、K1 の結果を見てオーナーが決める。sonnet で大きく下りた依頼が多ければ K2 は要らない。sonnet でもほぼ天井なら、作る役を弱めるより依頼を大きくするほうが、問いを保てる分だけよい。

### コマンド（実行担当がホストで打つ）

工場の判定はアプリとブラウザを bwrap の sandbox に入れるので、ワーカーの sandbox の中では起動できない（12 周目と同じ）。lap の定義にはせず、実行担当が手で打つ。較正には gate で固定する事前登録が無く、段ごとにオーナーが承認するからである。

```bash
# 写し（工場の今の main の worktree で。書き先は新しい名前）
cp -a ../factory-lap12-run/.factory-lap12 .factory-cal80-lap12   # lap10・lap11 も同じ形
export FACTORY_HOME="$PWD/.factory-cal80-lap12"

# 段 0: 今の工場で opus の build を判定し直す（依頼ごとに 3 回、$0）
npm run factory -- replicate cart-checkout-cc-p --score cart-checkout-cx-p --rescore   # 同じコマンドを 3 回打つ
# 隔離の確かめ（作る役を sonnet にして 1 回）
npm run factory -- probe-isolation cal80-probe --model builder=claude-sonnet-5-5

# 段 1: sonnet の下見（依頼ごと）
npm run factory -- replicate cart-checkout-cc-p --k 2 --score cart-checkout-cx-p --max-cost 15 --model builder=claude-sonnet-5-5
npm run factory -- replicate cart-checkout-cc-p --score cart-checkout-cx-p --rescore
npm run factory -- replicate cart-checkout-cc-p --rescore --score cart-checkout-cx-p
npm run factory -- tally cart-checkout-cc-p
```

- `--rescore` は、その変更のすべての build（opus と sonnet）を判定し直す。opus の build にも判定が足されるが、モデルは呼ばず、Q の計算は sonnet の build だけで行う。
- `--max-cost` は、その変更の下書きと、これまでのすべての `replicate` の費用を合わせた上限である（`src/replicate.ts`）。既存の `-cc-p` は下書きと opus の 4 build で $2〜$4 を使っているので、12 周目と同じ $15 にした。
- 10 周目の task-deps と 11 周目の pay-refunds は、自組の名前が `-cc-p-r2` である。`--score` の相手は `-cx-p` のまま。

## 80 % 付近を見つけた後の道筋

1. **較正の報告**を書く（`laps/calibrate-80/report.md`）。つまみ、依頼ごとの Q（opus と並べる）、起動しなかった build、全員が落ちたシナリオの読み、費用。

## 何が言えないか（あらかじめ）

- **K1・K2 で見つけた条件では、前提 1 の問いが変わる。** 本番の結論は「sonnet（または Haiku）の作る役で、別の系統のシナリオは合格率を下げるか」になる。工場が本番で使う作る役（opus）について、同じことが言えるかは別の問いで、較正からも本番からも答えられない。opus が天井にいる限り、opus で合わせ込みが起きても起きなくても、合格率の差としては見えない。
- **既存の 12 依頼から選ぶので、選ぶ寄りがある。** 段 2 の Q は、段 1 で 80 % に近く出た依頼に build を足したものである。本番は仕様とシナリオを下書きし直し、build も新しくするので、Q は窓から外れうる。そのときは本番の判定の規則（天井の印・床の印で「?」）で扱う。
- **4 build の Q のぶれは約 5 点である。** 「80 %」は 70〜90 % の幅でしか言えない。
- **シナリオは 10〜12 周目のものを使い回す。** 下書き役は作る役のモデルを知らないので、作る役を替えても採点の条件は同じである。期待値の誤りは、各周で読んだもの（`screen-errors.json`）をそのまま使い、sonnet の build で新しく見つかったものは同じ規則で足す。
- **10・11 周目の依頼は、古い工場の版で承認された。** 段 0 で今の工場で判定し直してから測るが、仕様とシナリオの中身は古い版の下書き役の出力のままである。
- **K5 は、依頼の大きさと題材の組み合わせを同時に変える。** 合わせた 2 本の規則の絡みが増えるので、長さだけのせいとは言えない。
- 8〜12 周目から引き継ぐ限界（系統 = 1 モデルずつ、Codex の答えたモデルは確かめられない、Codex の費用は回数だけ、lap 台帳にロックが無い）。較正は Codex を呼ばない（下書きし直しが無い K1・K2 のとき）。
