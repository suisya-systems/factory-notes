# Request: an office shop, room slots with lunch, a shared task board, and expense reports claiming orders and lunches

An office app, used locally only: employees buy supplies, book room slots, keep a shared task board, and claim the orders and the bookings' lunches in monthly expense reports. It has an HTTP API (every request and response body is JSON) and five pages, `/`, `/new`, `/reports`, `/rooms` and `/board`, that work only through that API. In a request body, a field written with `?` may be left out (its default is given); every other field named is required, and leaving it out is 400. Amounts are whole yen. Dates are `YYYY-MM-DD` and months `YYYY-MM`; one that is not a real calendar date or month is 400. Data is kept in memory; it does not have to survive a restart.

## Shop API

- `POST /products` with `{"sku", "name", "category", "price", "stock"}` adds a product: `sku` 1 to 20 characters and unique (409 if taken), `name` 1 to 40 characters, `category` 1 to 20 lower-case letters, `price` 1 to 100,000, `stock` 0 to 1,000. 201 with the product. `PUT /products/{sku}/stock` with `{"stock"}` (0 to 1,000) sets the stock; 200 with the product. `GET /products` returns 200 with the products in the order added.
- `POST /coupons` with `{"code", "percent", "minSubtotal", "category"}` adds a coupon: `code` 1 to 12 letters or digits, stored upper-case, unique ignoring case (409 if taken), `percent` 1 to 50, `minSubtotal` 0 to 1,000,000, `category` a category or null (required; null for none). 201 with `{"code", "percent", "minSubtotal", "category", "used": false}`.
- **The cart.** `GET /cart` returns 200 with `{"lines": [{"sku", "name", "category", "price", "qty", "lineTotal"}, ...], "subtotal", "coupon", "couponProblem", "discount", "shipping", "total"}`. Lines are in the order their products first entered the cart; `lineTotal` is `price × qty`; `subtotal` sums the line totals.
- `PUT /cart/lines/{sku}` with `{"qty"}` (0 to 1,000) sets a line; 0 removes it; more than the product's stock is 409. 200 with the cart.
- **The coupon.** `PUT /cart/coupon` with `{"code"}` attaches a coupon, matching the code ignoring case (unknown is 404, a used coupon 409), replacing any attached before. `DELETE /cart/coupon` detaches it. Both answer 200 with the cart. `coupon` is the attached code or null. The coupon applies while `subtotal` is at least its `minSubtotal` and, if it has a category, the cart has a line of that category; otherwise `couponProblem` is `"min"` (checked first) or `"category"` and the discount is 0. It is re-checked after every cart change. `couponProblem` is null when no coupon is attached or it applies.
- **Amounts.** `discount` is `percent` of the line totals it covers (all lines, or its category's), rounded down. `shipping` is 500 when the cart has lines and `subtotal − discount` is below 5,000, else 0. `total` is `subtotal − discount + shipping`.
- **Checkout.** `POST /checkout` with `{"employee"}` (checked and stored as a report's `employee`) refuses an empty cart (409) and a cart where a line's `qty` exceeds its product's current stock (409 with `{"error", "short": [{"sku", "stock"}, ...]}`, each such line in cart order). Otherwise it creates an order `{"id", "employee", "lines", "subtotal", "discount", "shipping", "total", "claimedBy": null}` from the cart as `GET /cart` shows it, takes each `qty` off its product's stock, marks an applied coupon `used`, empties the cart and its coupon, and adds the order's pick-up task to the board. Order ids are `"1"`, `"2"`, ... 201 with the order. `GET /orders` returns 200 with the orders in order.

## Rooms API

Slot and booking ids are strings the server assigns. Times are whole hours `HH:00`.

- **The clock.** The server keeps the time `now` as `{"date", "time"}`, starting at `2026-11-02` `08:00`. `GET /clock` returns 200 with it. `POST /clock` with `{"date", "time"}` sets it; an earlier time than `now` is 409. A slot **has started** when its date and start are not later than `now`.
- `POST /slots` with `{"date", "start", "room", "capacity", "lunch"?}` adds a slot: `start` from `09:00` to `17:00`, `room` 1 to 20 characters, `capacity` 1 to 10, `lunch` (yen a place) 0 (the default) to 3,000. A second slot with the same date, start and room (ignoring case) is 409. 201 with `{"id", "date", "start", "room", "capacity", "lunch", "booked": 0}`.
- `GET /slots?date=...` (required) returns 200 with that date's slots, by start, then by room name (ignoring case), each with `booked`, its number of bookings.
- `POST /bookings` with `{"slotId", "user"}` (`user` 1 to 30 characters after trimming, compared ignoring case) books one place. It is refused with 409 and `{"error", "reason"}`, checking in this order: `"started"` (the slot has started), `"full"` (`booked` equals `capacity`), `"overlap"` (the user already has a booking at the same date and start, in any room), `"limit"` (the user already has 3 bookings in slots that have not started). Otherwise 201 with `{"id", "slotId", "user"}`; the slot's `booked` grows by 1.
- `GET /bookings?user=...` returns 200 with the user's bookings in slots that have not started, by date and start, each `{"id", "slotId", "date", "start", "room"}`. `GET /bookings/{id}` returns 200 with any booking as `{"id", "slotId", "user", "date", "start", "room", "lunch", "started", "claimedBy"}`.
- `DELETE /bookings/{id}` cancels a booking and frees its place; 204. It is refused with 409 and `{"error", "reason": "late"}` when `now` is less than 2 hours before the slot's start, or later (for a `10:00` slot, cancelling at `08:00` is allowed and at `09:00` late).

## Board API

- A task is `{"id", "title", "status", "due", "order", "overdue"}`: `status` is `"todo"`, `"doing"` or `"done"`, `due` a date or null, `order` the id of the order it picks up or null. Ids are `"1"`, `"2"`, ... in creation order and never reused.
- `POST /tasks` with `{"title", "due"?}` adds a task with status `todo` and `order` null: `title` is trimmed and must then be 1 to 60 characters; `due` defaults to null. 201 with the task.
- **Pick-up tasks.** Every checkout adds a task titled `Pick up order {id}` with status `todo`, `due` the date of the clock's `now` and `order` the new order's id. It is recorded as an add.
- A task is **overdue** when its `due` is before the date of the clock's `now` and its status is not `done`.
- `PATCH /tasks/{id}` with any of `{"title", "status", "due"}` (same rules; `due` may be null) changes those fields; an empty body is 400. 200 with the task. `DELETE /tasks/{id}` deletes it; 204.
- `GET /tasks` returns 200 with the tasks in **board order**: tasks with a due date first, earliest date first; then tasks without one; within the same date (or no date), by id. `?status=` keeps one status (another value is 400). `?q=` keeps tasks whose title contains the text, ignoring case (an empty `q` keeps all). Both together keep tasks matching both.
- `GET /counts` returns 200 with `{"todo", "doing", "done", "all"}` over every task, whatever the filters.
- **Undo.** Every successful add, change and delete is recorded. `POST /undo` reverts the most recent one not yet undone and answers 200 with `{"undone": "add" | "change" | "delete", "task"}`, the task as it was before the undone action (for an add, as it was added). Undoing an add deletes the task; undoing a change puts back every field it changed; undoing a delete brings the task back with its id and fields. Calling it again reverts the one before, and so on; with nothing left it is 409. An undo is never itself recorded, so it cannot be undone, and actions made after an undo are recorded as usual.

## Report API

- `POST /reports` with `{"employee", "month", "lines": [{"date", "category", "amount", "note", "order"?, "booking"?}, ...]}` submits a report: `employee` 1 to 40 characters after trimming (stored trimmed), 1 to 10 lines, each `date` within `month`, `category` one of `"travel"`, `"meals"`, `"supplies"`, `amount` 1 to 200,000, `note` 0 to 80 characters (required; it may be empty). A breach of these is 400.
- **Order lines.** A line's `order` (default null) claims a shop order: unknown is 404; the line must be `supplies` with the order's `total` as `amount` (400); the order must be the employee's (ignoring case), unclaimed and listed once, and its pick-up task, while it exists, must be `done` (409).
- **Booking lines.** A line's `booking` (default null) claims a booking's lunch: unknown is 404; a line with both `order` and `booking` is 400; the line must be `meals` with the slot's `lunch` as `amount` and its date as `date` (400); the booking must be the employee's (`user`, ignoring case), its slot must have started, and it must be unclaimed and listed once (409).
- **Limits.** In one report, the meals lines of any one date may total at most 5,000, the travel lines at most 100,000, and the supplies lines at most 30,000. A report over a limit is 422 with `{"error", "problems": [...]}`, one problem per breach: `{"limit": "meals", "date", "total"}` for each date over the meals limit (earliest first), then `{"limit": "travel", "total"}`, then `{"limit": "supplies", "total"}`.
- An employee has one report per month: a second for the same `employee` (ignoring case) and `month` is 409. Of the 409s, it is checked first.
- An accepted report gets the next number, `EXP-0001`, `EXP-0002`, ...; a refused one takes none. Its orders and bookings get that number as `claimedBy`. 201 with `{"number", "employee", "month", "lines", "total"}`, the lines in the order sent and `total` their sum. `GET /reports` returns 200 with the reports in number order; `GET /reports/{number}` returns one (404 if unknown). `GET /summary` returns 200 with `{"travel", "meals", "supplies"}`, each category's total over every report.
- Errors: invalid JSON, a missing or wrong-typed field, or a value outside the rules above is 400; an unknown product, order, report, slot, booking or task is 404; the conflicts named above are 409. A refused request changes nothing. Every error body has `"error": string`.

On every page, names in `code` are test ids. Buttons are never disabled or hidden. Amounts show as `¥` and the number with thousands commas (`¥12,300`, `¥0`).

## The page `/`

- **Products**, in the order added, each with `productName`, `productPrice`, `productLeft` (`3 left`, or `Sold out` at 0) and `addButton`. `addButton` adds 1 to that product's line (a new line has qty 1) and saves it; when the line already holds the whole current stock, nothing changes and `pageMessage` shows `Only {stock} of {name} left`.
- **The cart.** Each line has `cartName`, `qtyInput` (its qty), `lineTotal` and `removeButton`. With no lines, `cartEmpty` shows `Your cart is empty`. `subtotal`, `discount`, `shipping` and `total` show the cart's amounts.
- **Quantities.** The user edits `qtyInput`s and clicks `updateButton`. An input that is not digits only gets `{name}: enter a whole number`; a number above the product's current stock (read at the click) gets `{name}: only {stock} left`. These show in `qtyError`, one element each, in cart order. With any problem nothing is saved and the inputs keep what was typed; otherwise every line is saved (0 removes it) and no `qtyError` shows.
- **The coupon.** `couponInput` and `couponApply` attach a code; `couponRemove` detaches it. While a coupon is attached, `couponNote` shows `{CODE}: -¥{discount}` when it applies, otherwise `{CODE} needs a subtotal of ¥{minSubtotal}` or `{CODE} needs a {category} item`. An unknown or invalid code shows `pageMessage` `Unknown coupon code`, a used one `{CODE} has already been used`.
- **Checkout.** `checkoutButton` first checks and saves the `qtyInput`s as `updateButton` does; with a problem it also shows `pageMessage` `Fix the cart before checking out` and orders nothing. Then it checks out for the employee in `buyerInput`; a 400 shows `pageMessage` `Enter your name`. An empty cart gives `pageMessage` `Your cart is empty`. On success `pageMessage` shows `Order {id} placed: ¥{total}`, the cart is empty, `couponNote` is gone and each `productLeft` shows the new stock.
- `pageMessage` shows only the message of the last click; a click that sets none clears it. After every click the page shows the products and cart as the API gives them, except inputs kept after a problem. Reloading shows the saved cart.

## The page `/new`

A wizard of three steps. `stepTitle` shows `Step 1 of 3: Basics`, `Step 2 of 3: Lines` or `Step 3 of 3: Confirm`. Only the current step's elements are shown. Each problem below is one `stepError` element, in the order listed, and every click that moves to another step clears them. The wizard keeps everything typed until it is submitted; reloading the page starts it again empty.

- **Step 1.** `employeeInput` and `monthInput`. `nextButton` checks them: `Enter your name` for an empty (after trimming) or too long name, `Enter the month as YYYY-MM` for a month that is not one. With no problem it goes to step 2.
- **Step 2.** `dateInput`, `categoryInput`, `amountInput`, `noteInput` and `addLineButton` add a line. Problems, in this order: `Enter the date as YYYY-MM-DD` (or `The date must be in {month}` for a real date outside the month), `Category must be travel, meals or supplies` (exactly one of these words), `Enter an amount from 1 to 200,000` (digits only), `The note is too long (80 at most)`, and `A report has at most 10 lines` when it has 10. With a problem nothing is added and the inputs keep their text; otherwise the line is added at the end and the four inputs are emptied. Each line shows `lineText`, `{date} {category} ¥{amount}` followed by ` ({note})` when the note is not empty, and a `removeLineButton`. `linesTotal` shows `Total ¥{sum}`. `backButton` returns to step 1.
- **Order lines.** `addOrderButton` adds a line for the order in `orderInput` (read at the click). The first problem that applies shows: the date problems of `addLineButton`, `Order {id} not found`, `Order {id} is not yours` (another employee's, ignoring case), `Order {id} has not been picked up` (its pick-up task exists and is not done), `Order {id} is already claimed by {number}`, `Order {id} is already in this report`, `A report has at most 10 lines`. Otherwise the line `{date} supplies ¥{total}` noted `Order {id}` is added at the end, and `dateInput` and `orderInput` are emptied.
- **Booking lines.** `addBookingButton` adds a line for the booking in `bookingInput` (read at the click). The first problem that applies shows: `Booking {id} not found`, `Booking {id} is not yours`, `Booking {id} has not started`, `Booking {id} has no lunch`, `Booking {id} is already claimed by {number}`, `Booking {id} is already in this report`, `The date must be in {month}` (the slot's date), `A report has at most 10 lines`. Otherwise the line `{date} meals ¥{lunch}` noted `Lunch {start} {room}` is added at the end, and `bookingInput` is emptied.
- **Leaving step 2.** `nextButton` checks the lines: `Add at least one line`; any line dated outside the month (after the month was changed at step 1): `{date} is not in {month}`, one per such line in line order; then the limits, in the order of the API's problems: `Meals on {date} come to ¥{total}; the limit is ¥5,000 a day`, `Travel comes to ¥{total}; the limit is ¥100,000`, `Supplies come to ¥{total}; the limit is ¥30,000`. With no problem it goes to step 3.
- **Step 3.** `confirmEmployee` (the trimmed name), `confirmMonth`, one `confirmLine` per line (written as `lineText`) and `confirmTotal` (`Total ¥{sum}`). `backButton` returns to step 2 with every line kept, so lines may be removed or added and the step 3 total then shows the new sum. `submitButton` sends the report. On the one-per-month 409 `stepError` shows `{employee} already has a report for {month}`; on another 409, `Order {id} cannot be claimed` for each order line whose order is now claimed, another employee's or not picked up, then `Booking {id} cannot be claimed` for each booking line whose booking is now claimed or another employee's, each in line order; the wizard stays at step 3 with everything kept. On success the page shows only `doneMessage` `Submitted {number}` and `newReportButton`, which starts an empty wizard at step 1.

## The page `/reports`

- One row per report in number order, each with `reportNumber`, `reportEmployee`, `reportMonth` and `reportTotal` (`¥{total}`). With none to show, `noReports` shows `No reports`.
- `subtotalTravel`, `subtotalMeals` and `subtotalSupplies` show `Travel ¥{n}`, `Meals ¥{n}` and `Supplies ¥{n}`, each category's total over the reports shown (all of them: what `GET /summary` gives), and `grandTotal` shows `All ¥{n}`, their sum.
- `employeeFilter` with `filterButton` shows only the reports whose employee equals the trimmed text, ignoring case (empty shows all); the totals then cover only those reports.

## The page `/rooms`

The page has no timers: it reads the API when it loads and after every click.

- **Who and when.** `userInput` (the user's name), `dateInput` and `showButton`. `showButton` shows the slots of the date typed for the user typed. A name empty after trimming shows `message` `Enter your name`; a date that is not a real `YYYY-MM-DD` date `Enter the date as YYYY-MM-DD` (the name is checked first); with a problem the list shown before stays. `clockNow` shows `Now: {date} {time}` as read from `GET /clock`. `listDate` shows `Slots on {date}` for the date shown, and nothing before the first show.
- **Slots**, in the API's order. Each has `slotLabel` (`{start} {room}`), `slotState` and `bookButton`. `slotState` is, in this order: `Started` once the slot has started; `Booked by you` when the shown user has a booking in it; `Full` when it is full; else `{n} of {capacity} left`. A slot showing `Booked by you` also shows `cancelButton`. With no slots, `noSlots` shows `No slots on {date}`.
- **Booking.** `bookButton` books the slot for the shown user (the name given at the last show, not what is typed since). On success `message` shows `Booked {start} {room} on {date}`. A refusal shows, by its reason: `This slot has started`, `This slot is full`, `You already have a booking at {start}`, `You can have at most 3 upcoming bookings`. Clicking `bookButton` on a slot showing `Booked by you` sends the request like any other: the full message if it is full, else the overlap one.
- **Cancelling.** `cancelButton` cancels the shown user's booking in that slot. On success `message` shows `Cancelled {start} {room} on {date}`; a late refusal `Too late to cancel: cancel at least 2 hours before the start`.
- **My bookings.** `myBooking` lists the shown user's bookings from `GET /bookings`, one element each in its order, written `{date} {start} {room}`; with none, `noBookings` shows `No upcoming bookings`.
- After every click the page reads the clock, the slots and the bookings again, so a slot that filled or a clock that moved through the API since the last read shows at once, after a refusal too. `message` shows only the message of the last click; a click that sets none clears it. Reloading the page shows no list and no message, with the inputs empty.

## The page `/board`

The page has no timers: it changes only when the user clicks or the page is loaded.

- **Adding.** `titleInput`, `dueInput` (empty for no date) and `addButton`. A title empty after trimming shows `formError` `Enter a title`; one longer than 60 characters `Title is too long (60 at most)`; a due date that is not a real `YYYY-MM-DD` date `Enter the due date as YYYY-MM-DD`. With both title and date wrong both show, title first, one `formError` each. On a problem nothing is added and both inputs keep their text; on success both are emptied and `notice` shows `Added "{title}"`, or `Added "{title}" (hidden by the filters)` when the new task does not match the current filters.
- **Filters.** `filterAll`, `filterTodo`, `filterDoing` and `filterDone` choose the status filter (all at first). `searchInput` with `searchButton` sets the text filter to the trimmed input (empty clears it); typing alone does not filter. `filterLabel` shows the filters in effect: `All`, `To do`, `Doing` or `Done`, followed by ` matching "{text}"` while a text filter is set (`Doing matching "report"`). The list shows the tasks `GET /tasks` gives with both filters.
- **The list**, in board order, five tasks a page. Each task has `taskTitle`, `taskDue` (`due 2026-11-03`, followed by ` (overdue)` when the task is overdue, or `no due date`), `taskStatus` (`To do`, `Doing` or `Done`), `advanceButton` and `deleteButton`. `advanceButton` moves `todo` to `doing`, `doing` to `done`, and `done` back to `todo`. With nothing to show, `emptyList` shows `No tasks match`.
- **Pages.** `pageInfo` shows `Page {n} of {m}` (`Page 1 of 1` when the list is empty); `prevPage` and `nextPage` move one page and do nothing on the first or last page. Changing either filter goes to page 1. After any other change the page stays where it was, or goes to the last page if it no longer exists. A task that leaves the filters after an advance disappears from the list at once.
- **Counts.** `countTodo`, `countDoing` and `countDone` show `To do: {n}`, `Doing: {n}` and `Done: {n}` from `GET /counts`, whatever the filters.
- **Undo.** `undoButton` calls `POST /undo`. `notice` then shows `Undid adding "{title}"`, `Undid a change to "{title}"` or `Undid deleting "{title}"` with the title from the answer, or `Nothing to undo` on 409. The list, page and counts show the board after the undo, with the filters kept.
- `notice` shows only the message of the last click; a click that sets none clears it. An advance or delete shows no notice. In every notice `{title}` is the saved (trimmed) title. After every click the list and counts show what the API gives. Reloading the page shows the saved tasks with no filters, page 1 and no notice.
