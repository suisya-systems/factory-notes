# 8 周目の報告（2026-10-18）

工場の 8 周目の結果を報告する。この周のねらいは factory#16 である。仕様と隠しシナリオを書く役（下書き役）を、作る役と別のモデル系統にした周を回し、同じ系統の対照と比べる。別の系統は Codex CLI（gpt-6-astra）で、作る役・分類・判定は Claude のままにした。手順と設計は [runbook.md](runbook.md)、入口の確認は [entrance-summary.md](entrance-summary.md)、7 周目の報告は [../lap-7/report.md](../lap-7/report.md) にある。設計の正本は design/grand-design.md。

## この文書での言葉

7 周目の報告と同じ言葉を使う。新しい言葉は次のとおり。

- **8 周目 / この周**: 2026-10-17〜18 に回した、工場の 8 回目の実行。状態ディレクトリは新しく始めた（`.factory-lap8`）。
- **系統**: c = Claude（claude-opus-5-5）、x = Codex（gpt-6-astra、Codex CLI 0.153.4 経由）。
- **組の名前 R-ab-k**: 依頼 R（settle = 割り勘の精算、memo = メモの API）、仕様の系統 a、シナリオの系統 b、k = 1, 2。cc と xx は仕様とシナリオを同じ系統が書いた組、cx と xc は他方の系統の仕様を 1 バイトも変えずに借りて、シナリオだけを書いた組である。
- **腕**: cc・cx・xx・xc の 4 つ。腕ごとに組が依頼あたり 2 つある。
- **D・Ds・Dp**: 主な比較 D = P(cc) − P(xx)、シナリオの系統の効果 Ds_c = P(cc) − P(cx)・Ds_x = P(xc) − P(xx)、仕様の系統の効果 Dp_c = P(cc) − P(xc)・Dp_x = P(cx) − P(xx)。P は 1 回目の build の合格率（やり直しなし）。
- **数えた呼び出し**: Codex の呼び出し。費用は ChatGPT アカウント側で、lap 台帳には USD でなく回数で残す（上限 200 回、窓口の疎通確認 1 回を引いて工場の上限は 199 回）。
- **採点し直し（rescore）**: 残した build の作業場で、モデルを呼ばずにシナリオだけを流し直すこと（`replicate --rescore`）。

## 結論

判定は、採点し直した後の数字で出す（オーナー判断。直した runner で本物の記録の 64 build を `--rescore` した）。直す前の数字も並べる。

- **周としての結論は、事前登録の線で「依頼による、または決められない」である（直す前も、採点し直した後も同じ）。**

## 何が言えないか（既知の限界）

- **2 つの依頼は易しすぎた。** settle は全 build が全シナリオを通し、memo も 2 本の「選択」を除けばほぼ通った。合格率が天井にあるので、系統の差があっても見えない。「差が見えない」は「差が無い」ではない。
- **測ったのは 1 回目の build だけである。** 7 周目の要約の効果が混ざらないように、やり直しはしていない。
- **採点の不具合の直しは、結果を見た後である。** 不具合の仕組み（ヘッダの重複）は結果と関係なく確かめられ、直しは 16 組すべてに同じく効く。ただし、見つけたきっかけは memo-xx-1 の低い合格率である。直す前の数字も並べて残した。
- **集計の道具に 2 つの不具合があり、結果を見た後で直した。** どちらも事前登録の線を正しく当てるための直しで、線は変えていない。
  - 浮動小数の差: memo の Ds_c はちょうど 5.0 点だが、平均の計算で 4.9999… になり、「差なし」と出ていた。差を丸めてから線と比べるようにした（self-test 付き）。直すと「決められない」になる。
  - 補正の数字を出す経路（`errors.json` を渡す場合）が落ちていた。この周で初めて通した経路で、比べる相手を取り違えていた。
- **memo のシナリオの系統が「決められない」のは、1 本のシナリオによる。** memo-cx-1 の missing-required-content（仕様が決めていない、必須の欄の扱い）を 8 build すべてが落とした。これを除けば Ds_c は 0 点だが、手順書の規則ではこれは「選択」で、除かない。
- **書き直しは Codex の cx だけに起きた。** settle-cx-1r2 は 3 回目の下書きで、書き直しで残った組は工場の検査を通る下書きに偏っている。
- **組は腕ごとに 2 つ、build は組ごとに 8 本である。** 統計的な検定はしていない。
- **分類は Claude に固定した。** 仕様の層の線引きは Claude の読みによる。
- **1〜7 周目から引き継いでいる限界。** lap 台帳にはロックが無い。作る役は Claude の認証トークンを読める（Codex のログインは読めない）。

2. **集計の道具を、使う前に全経路で試す。** この周は、補正の数字を出す経路と線ちょうどの差を、self-test が通していなかった。事前登録の線の境目（5 点・10 点ちょうど）と `errors.json` ありの経路を、self-test に入れてから入口に進む。
3. **工場の採点を、シナリオの書き癖に強くする。** この周は、Codex だけが Content-Type を書いたことで不具合が出た。シナリオの手順を送る前に、ヘッダを正規化した形で記録し、承認の要約に出す。2 つ目の系統を入れると、1 つ目の系統では出なかった書き方が増える。
4. **下書き役が検査に従えるかを、系統の差として測る。** 却下の回数と理由は、合格率より系統の差がはっきり出た。修正の往復の回数・却下の理由を、組ごとの計測として事前登録に入れる。
5. **入口の確認を工場に入れる**（7 周目の提案 3 の続き）。この周も、仕様の層が空になることを入口で手で見つけ、定義をオーナーの判断で変えた。
