## 仕様の層の定義を入口で変えた（オーナー判断: 案 B）

事前登録の元の定義（分類ラベル readable で根拠 spec）では、仕様の多くが状態コードを未決に残したため、203 本中 readable は 3 本、根拠 spec の readable は 0 本で、仕様の層が全組で空だった。オーナーの判断で、定義を「状態コード以外の確認がすべて仕様から読める（M、根拠 spec）」に変えた。状態コードの確認しか無いシナリオは入れない。

- 変更は作る前・結果を見る前（ビルド 0 本）。見たのは層ごとの本数の分かれ方だけ。
- 新しい定義での本数: settle 0〜2、memo 4〜8（表の「spec layer」）。settle では、仕様の層の比較はほぼ「決められない」になる見込み。主判定（全シナリオ）は変わらない。
- 変更先: `arms.ts` の `inSpecLayer`（self-test 付き）、手順書の「入口での変更」節、`prereg.json` の note。
