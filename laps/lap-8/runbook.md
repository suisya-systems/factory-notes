# 8 周目の実行手順

工場の 8 周目の手順。factory#16。仕様とシナリオ（確認項目）を書く役（下書き役）を、作る役と別の系統のモデルにする。その周を、同じ系統の対照と比べる。周は工場の `lap` コマンドに定義ファイル 1 つを渡して流す（[lap.json](lap.json)。工場のリポジトリの `examples/lap-8.json` と同じもの）。実行担当が打つのは、そのコマンドとゲートの承認だけである。

## 言葉

- **Claude 系統（c）**: `claude-opus-5-5`。**Codex 系統（x）**: OpenAI の `gpt-6-astra`。工場は Codex CLI（0.153.4）から呼ぶ。課金は ChatGPT アカウント側。
- **作る役**は、すべての腕で `claude-opus-5-5` である。**分類役**（シナリオごとに、仕様から読めるかを決める役）も、すべての組で `claude-opus-5-5` にする。測る道具を腕の間で揃えるためである。
- **組の名前** `<依頼>-<仕様の系統><シナリオの系統>-<番号>`。たとえば `settle-cx-2` は「割り勘の依頼。仕様は Claude が書いた 2 本目、シナリオは Codex が書いた組」。番号は仕様の番号である。
- **同系統の組**は cc（仕様もシナリオも、作る役と同じ Claude）。**別系統の組**は xx（仕様もシナリオも Codex）。cx と xc は、仕様とシナリオのどちらが効いたかを分けるための組である。

## 何を確かめるか

**設計の前提 1**（grand-design「試作で確かめる前提」1）: 「作る役にシナリオを見せなければ、合わせ込みは防げる」。

仕様とシナリオを作る役と同じ系統のモデルが書くと、シナリオは作る役の思い込みと同じものを測るだけになりうる。5 周目では、作る役とシナリオの下書き役が、決められていない点 3 つすべてで同じ答えを選んだ（16/16）。opus と sonnet は同じ系統なので、「教科書どおりの答え（T）」と「Claude 系統に共通の好み」は分けられなかった（lap-5 報告「既知の限界」）。

この周で問うことは次のとおり。下書き役を別の系統にすると、作る役（Claude）の 1 回目の合格率は下がるか。下がるなら、それは仕様と隠しシナリオのどちらの系統によるか。

- シナリオの系統で下がる場合: 同系統の隠しシナリオは、作る役の好みと重なる分だけ甘い。前提 1 の「隠せば防げる」は、同系統では過大評価になる。
- 下がらない場合: 少なくともこの 2 つの依頼では、系統の好みは合格率に出ない。5 周目にそろった答えは T 寄りと読める。

## 設計の要点

着手前の設計レビュー（Codex、1 回）は Blocker 2・Major 8・Minor 1 だった。Blocker 2 つと Major 3・5・6 は、設計の時点で未実装だったもの（定義ファイル、アダプタ、上限、認証の守り、集計の道具）で、この周の実装に入れた（下の「工場に入れた変更」）。設計への指摘は、すべて下に反映した。

1. **測り方は triage の推奨のとおりにする。** 同系統と別系統の drafter/builder の組で、作る役の合格率を比べる。合格率は、`replicate`（LLM 判定・やり直し・出荷なし）で作った 1 回目の build が、隠しシナリオを何本通したかで測る。やり直しを入れると、要約の効果（7 周目）と混ざるためである。
2. **2×2 の要因に分ける**（Major 7 の後半）。仕様の系統（c・x）とシナリオの系統（c・x）を独立に振る。D（同系統 − 別系統）だけでは、差が仕様から来たのかシナリオから来たのかを言えない。仕様 1 本ごとに、作る役を K 回走らせる。各 build は、その仕様を共有する 2 組（同じ系統と別の系統のシナリオ）で採点する（`replicate --score`）。シナリオの系統の効果は、同じ build の上で対にして比べられる。作る役の揺らぎが打ち消し合い、作る役の費用も増えない。
3. **仕様は系統ごとに 2 回、独立に下書きする**（Major 7）。仕様 1 本では、仕様の下書き 1 回の揺らぎを系統の差と取り違える。K 回の build が測るのは作る役の揺らぎだけである。それでも各系統 2 本で、結論は「この 8 本の仕様について」に限られる（「何が言えないか」）。
4. **依頼は 2 つにする。** 割り勘（`requests/split-settle.md`、5〜7 周目の題材。決められていない点が多い）と、メモ API（`requests/memo-api.md`、1〜2 周目の題材。決められていない点の多くは状態コードと入力の検査）。依頼 1 つでは、系統の差を依頼の癖と区別できない。どちらも新規のアプリで、`replicate` が使える。
5. **Codex の下書きを、Claude の費用が出る段より前に置く。** アダプタは偽の CLI でテストした。ワーカーの手元では、フックの規則で実物の Codex を呼べない。最初の段 `settle-xx-1` の下書きが、実物の最初の呼び出しになる。旗や出力の形が違えば、Claude の USD を使う前に周が止まる。
6. **作る役の環境に ChatGPT の認証を渡さない**（オーナーの条件、Major 5）。工場は、Codex 系統のモデルを下書き役 2 つ（`spec-drafter`・`scenario-drafter`）にしか割り当てない。`--model` の解釈と、呼び出しの直前（`modelFor`）の 2 か所で拒否する。Codex の認証ファイルを mount するのは、Codex を呼ぶ下書き役のサンドボックスだけである。作る役のサンドボックスからそのファイルが読めないことは、偽の認証ファイル（カナリア）を使ったテストで確かめる。周の隔離の確認（`probe-isolation`）も、作る役の返答と作業ディレクトリに、本物の認証ファイルのトークン文字列が出ないことを機械的に確かめる。記録に残すのは真偽だけで、トークンは書かない。
7. **費用は 2 本立てで数える**（Major 3）。Claude 側は USD で数え、lap 台帳の上限を $150 にする（オーナーの判断）。Codex 側は USD が返らないので、呼び出しの回数で数える。呼び出しの前に lap 台帳へ 1 行を予約し、修正の往復も、途中で止まった呼び出しも 1 回に数える。上限は 199 回とする。オーナーの上限は 200 回で、窓口が手元のスモークで 1 回使っている。上限に達すると、工場は次の Codex 呼び出しの前に止まる。Codex の呼び出しは USD の台帳に $0 で入り、「費用が返らなかった Claude の呼び出し」（許した予算の全額を数える）とは別に扱う。
8. **分類役は Claude に固定する。** 分類役の系統も振ると、「仕様から読める」のラベル自体が系統ごとに変わり、腕の間で同じ物差しにならない。
9. **「仕様から読める」は、状態コード以外の確認がすべて、仕様から読める（照合 M、根拠 spec）もの**（Major 9。入口で変更、下の「入口での変更」）。分類役は、予測の根拠が慣習（convention）だけでも、すべての照合が合えば readable にする。慣習は系統の好みそのものかもしれないので、仕様が決めた側には入れない。新規のアプリなので、根拠 code は出ない。
10. **どの系統が答えたかは、呼び出しごとに記録して確かめる**（Major 10、Minor 1）。下書きの費用の記録（`draft-cost.json`）に、呼び出しごとの役・指定したモデル・報告されたモデルを並べる（`calls`）。仕様を再利用した組には、元の組の id を残す（`specFrom`）。修正の往復は、同じ役の呼び出しが 2 回あることで見える。Codex CLI は答えたモデルを報告しないので、報告されたモデルは「報告なし」になる。指定どおりに Codex CLI へ渡したことまでしか確かめられない。確かめる段（`arms.ts --provenance`）は、ゲート `specs` と `entrance` のそれぞれの直前に置く。合わなければ周が止まる。

## 組み立て

依頼ごとに次の 8 組を作る（`R` は `settle` または `memo`、`k` は 1 と 2）。

| 組 | 仕様 | シナリオ | 作り方 |
|---|---|---|---|
| R-cc-k | Claude（k 本目） | Claude | `draft`（両方 opus） |
| R-xx-k | Codex（k 本目） | Codex | `draft --model spec-drafter=gpt-6-astra --model scenario-drafter=gpt-6-astra` |
| R-cx-k | R-cc-k の仕様 | Codex | `draft --spec-from R-cc-k --model scenario-drafter=gpt-6-astra` |
| R-xc-k | R-xx-k の仕様 | Claude | `draft --spec-from R-xx-k` |

作る役（opus）は、仕様ごとに K = 8 回走らせる（8 本）:

- `replicate R-cc-k --k 8 --score R-cx-k --max-cost 20`
- `replicate R-xx-k --k 8 --score R-xc-k --max-cost 20`

8 本の `replicate` は、#15 の並列の組（`parallel`、`max` 4）で流す。`--spec-from` には承認済みの組が要るので、ゲートは 2 つ置く。

1. ゲート `specs`: 仕様の元になる 8 組（R-cc-k・R-xx-k）を承認する。
2. ゲート `entrance`: 残りの 8 組（R-cx-k・R-xc-k）を承認し、事前登録（`prereg.json`）を固定する。

`--spec-from` で作った組の仕様が元とバイト単位で同じことは、`cmp` の段で確かめる（7 周目と同じ）。

## 入口の確認（作成担当、費用なし）

ゲート `entrance` で止まったら、作成担当が次を行う。モデルは呼ばない。

1. 系統の記録は、前の段の `arms.ts --provenance` が機械的に確かめ済みである。その出力を `entrance-summary.md` に貼る。
2. 組ごとのシナリオ数、自己申告（`inSpec`）と分類ラベル（readable-spec・readable-convention・その他）の内訳、修正の往復の回数を、`entrance-summary.md` に表にする。
3. 期待値の誤りは、入口では探さない（参照実装は作らない）。誤りは走らせた後に、下の「全員が落ちたシナリオ」の規則で扱う。規則は事前に決めておく。
4. `prereg.json` に承認の版を書く。両方が揃うと、同じ `lap` コマンドでゲートの要約が出る。

              "memo": {"...": "..."}},

`errors` は、走らせた後に作成担当が書く別のファイル（`errors.json`、下の規則）で、事前登録には入れない。集計の道具は、`errors.json` があれば補正の数字も出す。

## 計る量

- **p(b, s)**: build b がシナリオの組 s を通した割合（通した本数 ÷ 組の本数）。
- **組の合格率** P(s): その組を採点した 8 回の build の p の平均。
- **腕の合格率** P(ab): 腕 ab（仕様の系統 a、シナリオの系統 b）の 2 組の P の平均。
- **主な比較（同系統 対 別系統）**: D = P(cc) − P(xx)。単位はパーセントポイント。
- **シナリオの系統の効果**（仕様を固定し、同じ build で対にする）: Ds_c = P(cc) − P(cx)（Claude の仕様の上）、Ds_x = P(xc) − P(xx)（Codex の仕様の上）。
- **仕様の系統の効果**（シナリオの系統を固定する。build は別）: Dp_c = P(cc) − P(xc)（Claude のシナリオで採点）、Dp_x = P(cx) − P(xx)（Codex のシナリオで採点）。
- 上の量をすべて、シナリオの層で 2 つに分けても出す。**spec 層**は、状態コード以外の確認がすべて仕様から読める（M、根拠 spec）シナリオ（状態コードの確認しか無いものは入れない）。**その他の層**は、それ以外のすべてである。前提 1 が効くなら、差はその他の層に出るはずである。readable で根拠が convention のものは、その他の層に入れたうえで、記述として別にも数える。
- 層を分けた組の本数が 0 なら、その組の P は「無し」とする。「無し」を使う量は **決められない（分母が無い）** とする。

## 判定の線（事前に決める）

依頼ごと・層ごとに、各量に次の線を当てる。統計的な検定はしない。K = 8・腕ごとに組 2 つの記述である。

- **+（差あり）**: 差が +10 ポイント以上ある。さらに、比べる組の組み合わせがすべて同じ向きである。D と Dp は、2 つの腕の組を総当たりにした 4 通り（例: D なら cc の 2 組の各 P が、xx の 2 組の各 P を上回る）。Ds は、同じ仕様の上の 2 対（R-cc-k と R-cx-k、k = 1, 2）。
- **−（逆向きの差あり）**: 差が −10 ポイント以下で、組み合わせがすべて逆向き。
- **0（差なし）**: 差の絶対値が 5 ポイント未満である。
- **?（決められない）**: それ以外。分母が無いものを含む。

### 帰属の表（依頼ごと、全シナリオで）

シナリオの系統の効果 S は Ds_c と Ds_x から、仕様の系統の効果 P は Dp_c と Dp_x から、同じ表で決める（a・b は 2 つの量の判定）。

| a と b | 結論 |
|---|---|
| + と + | 系統で下がる（S なら「別系統のシナリオで下がる」） |
| 0 と 0 | 効果なし |
| − と − | 系統で上がる（逆向き） |
| + と 0、0 と + | 片方の側でだけ下がる（交互作用。どちらの側かを書く） |
| − と 0、0 と − | 片方の側でだけ上がる（交互作用） |
| + と − | 側によって向きが逆（交互作用） |
| ? を含む | 決められない |

周としての結論は、依頼ごとの D・S・P を並べて出す。

- 2 つの依頼の両方で D が + なら、**別系統で合格率が下がる**。そのとき、どちらの系統によるかは S と P で述べる。両方の依頼で S が「別系統のシナリオで下がる」なら、**同系統の隠しシナリオは甘い**（前提 1 への反証）。
- 両方で D・S・P のすべてが 0 なら、**この 2 つの依頼では系統の差は見えない**。
- それ以外は、依頼ごとの結果を表で並べ、**依頼による**、または **決められない** とする。

### 全員が落ちたシナリオ（期待値の誤りの扱い）

ある仕様の 8 回の build のすべてが落ちたシナリオは、期待値の誤りかもしれない（5 周目の settle-b1 に 1 本あった）。走らせた後に、作成担当が 1 本ずつ読み、次の規則で 2 つに分ける。結果は `errors.json`（`{"<組>": ["<シナリオ id>", ...]}`、誤りだけ）に書く。

- **誤り**: 期待値が、依頼文の文、または仕様の「依頼が述べる規則」の文と食い違う（その文を引用できる）。または、金額の計算が成り立たない（作成担当が手で計算し直して示す）。
- **選択**: それ以外。決められていない点で、作る役と違う答えを選んだもの。系統の差の中身そのものなので、残す。

結論は、全シナリオの数字（生）と、誤りを除いた数字（補正）の両方で出す。両者で判定が違えば、その量は **決められない（誤りの扱いによる）** とする。作成担当（Claude）の判断が入る箇所はここだけである。そのため、規則に当たらない「誤り」は作らない。分けた結果は、シナリオごとに引用と計算を付けて報告に並べる。誤りを除くと組が空になる場合は、分母が無いものとして扱う。

## 入口での変更: 仕様の層の定義（2026-10-18、オーナーが案 B を選んだ）

元の定義は「分類ラベル readable で根拠 spec」だった。分類のラベルはシナリオ単位で、確認が 1 つでも書かれていなければ unstated になる。仕様の多くが状態コードを未決に残したため、16 組 203 本で readable は 3 本、根拠 spec の readable は 0 本になり、仕様の層が全組で空になった。そこで定義を「状態コード以外の確認がすべて仕様から読める（M、根拠 spec）」に変えた。

- 変えたのは**作る前・結果を見る前**（ゲート `entrance` の承認前で、ビルドは 0 本）である。
- 見たのは**層ごとの本数の分かれ方だけ**（組ごとの、ラベルと照合結果の数）で、合格率は 1 つも見ていない。
- 新しい定義での仕様の層の本数は、settle で組あたり 0〜2、memo で 4〜8（オーナーに示した見積もり 0〜3 / 4〜10 は、状態コードの確認しか無いシナリオも数えていた。定義どおり除くと、この数になる）。settle は少なく、層の比較はほぼ「決められない」になると見込む。主判定（全シナリオ）は変わらない。

## 書けなかった組の扱い（2026-10-18 追加、再実行の前に決めた）

下書きの段が失敗した組（下書きの役が工場の検査を 1 回の修正の往復の後も通らなかった組）は、同じ入力（同じ依頼・同じ `--spec-from`・同じモデル指定）のまま新しい名前（`<元の名前>r1`、`r2`）で書き直す。書き直しは組ごとに 2 回まで。lap は失敗した段を再実行しないので、書き直しのたびに定義を変え、ゲート `specs` を承認し直す（8 組の中身は変わらない）。

- 書き直した組の名前は `arms.ts` の名前の形（`-<k>r<n>`）で読む。組の対応は `prereg.json` の `pairs` が持つ。
- 2 回書き直しても書けなければ、その組は失敗として記録して外す。その依頼の判定は、残る組だけで出し、「決められない」より強くしない。
- 却下された下書き（`runs/<id>/rejected-*.json`）と系統ごとの修正の往復の回数は、結果として報告に書く（下書きの役が工場の検査に従えるかも、系統ごとの差である）。

記録: settle-cx-1（Claude の仕様に Codex がシナリオを書く組）が、要約に手順の値（"repeat"、"fractional cost"）を含めて 2 回とも却下された。settle-cx-1r1 として書き直したが、要約に "aki" を含めて再び却下された（修正の往復の後も）。settle-cx-1r2 として 2 回目の書き直しをする。

## 手順（実行担当）

cwd は工場のこのワークツリー（ブランチ `feat/factory-16-cross-family-lap`）。`codex` が PATH にあり、`~/.codex/auth.json` で ChatGPT にログインしていること（工場は PATH から実体を探し、無ければ明示的なエラーで止まる）。

```bash
npm run factory -- lap examples/lap-8.json
```

1. 最初はゲート `specs` で止まる（exit 3）。オーナーが 8 組の承認要約を読む。承認: `npm run factory -- lap examples/lap-8.json --approve specs --by <承認者名> --version <要約の version>`
2. 同じコマンドで再開する。8 組の下書きの後、ゲート `entrance` で `prereg.json` と `entrance-summary.md` を待って止まる。作成担当に知らせる。
3. 作成担当が入口の確認を済ませたら、同じコマンドをもう一度打つ。ゲートの要約が出る。オーナーが読んで承認する（`--approve entrance`）。
4. 同じコマンドで再開する。8 本の `replicate`（並列）と集計まで流れる（`lap lap8: done`、exit 0）。
5. 集計の出力と、`.factory-lap8/` のパスを作成担当へ送る。

緊急停止（Major 4）: 別の端末から `FACTORY_HOME="$PWD/.factory-lap8" npm run factory -- stop`。lap の `home` は lap を回すプロセスの中でだけ効くので、`FACTORY_HOME` を付けないと別の状態ディレクトリに STOP ができる。この周は出荷しないので、本番のプロセスは無い。

## 何が言えないか（あらかじめ）

- **系統の差とモデルの差は分けられない。** 各系統から 1 つのモデル（opus と gpt-6-astra）しか使わない。「系統」はこの 2 つのモデルのことである。
- **仕様は系統ごとに 2 本だけである。** 仕様の系統の効果 P は、この 8 本の仕様についての記述である。
- **Codex の下書き役は、Claude の下書き役とは違う道具の環境で動く。** Codex CLI は読み取り専用のシェルを持つ（サンドボックスの中。$HOME は空で、保管庫は見えない）。Claude の下書き役は道具なしで動く。
- **作る役の系統は振らない**（オーナーの判断で Claude のまま）。「別系統の作る役」（5 周目の提案 3 の元の形）は、この周では測らない。
- **Codex の費用は USD では出ない。** 回数だけである（トークン数は CLI の出力にあるが、工場は記録しない）。
- **Codex に答えたモデルは確かめられない。** CLI がモデルを報告しないため、「指定どおりに渡した」までである。
- **分類役が Claude なので、spec 層の切り方は Claude 寄りかもしれない。** 層は分けて見るための補助としてだけ使う。帰属の表は全シナリオで決める。
- **依頼は 2 つ、組は腕ごとに 2 つ、build は仕様ごとに 8 回である。** 下書きの揺らぎが大きければ、組み合わせがすべて同じ向きという条件を満たせず、「決められない」が増える。
