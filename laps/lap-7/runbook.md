# 7 周目の実行手順

工場の 7 周目の手順。6 周目（[../lap-6-runbook.md](../lap-6-runbook.md)、結果は [../lap-6-report.md](../lap-6-report.md)）の仕組みをそのまま使い、6 周目の報告の「次の周への提案」1 と 2 を回す。周は工場の `lap` コマンドに定義ファイル 1 つ（[lap.json](lap.json)。工場のリポジトリの `examples/lap-7.json` と同じもの）を渡して流す。実行担当が打つのはそのコマンドだけである。

## 何を確かめるか

**前提 2**: 作る役が一度落ちても、承認済みの 1 行要約だけを返してやり直させれば、合格に近づく。

6 周目では支持された。ただし条件はやさしい側にあった。少数派の点はどれも 1 か所の数行で直る独立した点で、1 行要約は直す向きをそのまま書いていた。要約を返さない対照の run も無かった。この周は次の 2 つを変える。

1. **難しい側。** シナリオの下書き役に、少数派の点を 4〜5 個選ばせる。そのうち 2 個以上は、アプリが計算する金額（各人の負担・端数の行き先・精算の送金）を変える点にさせる。金額に絡む点は、狙ったシナリオ以外のシナリオの金額にも効く。そのシナリオの 1 行要約は、値を書けない決まりのため「どこをどう直すか」を書き切れない。提案 1 の (a)（既存の計算と絡む点）・(b)（向きが読み取りにくい要約）・(c)（点を増やす）を、1 つの束として試す。3 つの効果は分けられない（下の「何が言えないか」）。
2. **対照。** 同じ承認済みの組で、要約を返さない run（`run --feedback bare`）を置く。落ちたシナリオ 1 本ごとに `- failed: a hidden scenario` の 1 行と、LLM 判定の行だけを返す。作る役に伝わるのは、落ちたことと、落ちた本数だけになる。これで測るのは、**落ちたこと・本数・LLM 判定の行に加えて、要約の中身がどれだけ効くか**である。空のフィードバックは試行 1 と同じ指示になり（工場の `build` は空のとき「前回は落ちた」と書かない）、「落ちた」の 1 行だけでは本数も消えるので、どちらも同じ比較にならない（設計レビューの Minor 1）。

## 設計の要点

着手前の設計レビュー（Codex、1 回）は Blocker 0・Major 5・Minor 3 だった。Major はすべて下に反映した。

1. **仕様は 5 周目の settle-a1 のまま**（6 周目と同じ）。この仕様を要約なしで作った作る役の commit が 22 回分ある（5 周目の 16 回と、6 周目の 6 run の 1 回目）。これを入口の確認の裏付けに使う。
2. **下書きの指示文**（`draft --minority --minority-brief <文>`）。文は定義ファイルに英語でそのまま書いてあり、ゲートで承認される。依頼にある言葉（負担・端数・精算）だけを使い、仕様の中身は渡さない。文は仮定に `(experimenter) minority brief: ...` として残るので、承認の版に入る。作る役は仮定を見ない（テストで確かめた）。一覧の順は選ばせない。6 周目に使い、`.reverse()` 1 つで直ったため。
3. **組を承認する条件を、難しい側に合わせて決めておく**（Major 1）。確かめた少数派の点が 3 個以上あり、そのうち金額に絡む点（下の定義）が 2 個以上あること。満たさない組は承認せず、別の id で下書きし直す。定義ファイルが変わるので、ゲートは止まり直す。
4. **点 × シナリオの依存表を、引用に頼らず作る**（Major 2）。参照実装で宣言どおりの答えにし、答えを 1 つずつ多数派に戻して、落ちるシナリオと落ちたチェックを表にする（`entrance.ts` の `revert`）。下書き役が `scenarios:` に何を挙げたかは使わない。
   - **金額に絡む点**: 1 つ戻すと 2 本以上のシナリオが落ち、そのうち 2 本以上で、落ちたチェックが金額（`amount`、`transfers`、負担）にあること。
5. **点ごとの集計は、その点だけに効くシナリオで行う**（Major 3）。表の `only` は、その点を戻したときだけ落ち、ほかの点を戻しても落ちないシナリオである。点ごとの「何回目で通ったか」と「前の作る役 22 回のうち何回が多数派を選んだか」は、この `only` で数える。`only` が空の点は「点だけでは見えない」と記録する。run の分類は、これまでどおり確かめた少数派シナリオ全体で行う。
6. **向きのラベルは、点ごとに、その点にかかわるすべての要約を見て付ける**（Major 5）。その点を戻すと落ちるシナリオの要約を全部並べ、どれか 1 本でも、宣言の答えが分かる程度に向きを書いていれば `directional`、どれも書いていなければ `opaque`。作成担当が入口で付け、事前登録に入れる。要約の曖昧さは、狙って作らない（工場の通常の要約のまま）。金額に絡む点で自然に出るかを見る。
7. **費用の上限で途中が切れても、腕の比較が偏らないようにする**（Major 4）。run は 8 本（組ごとに要約あり 2・bare 2）で、最悪でも約 $26 に収まり、lap の上限 $30 まで余裕を残す。順は 2 つのブロック（各ブロックに 4 腕を 1 本ずつ）に分け、ブロックの中の順は乱数で決めた（`node:crypto` の `randomInt` でシャッフルし、そのまま定義に書いた）。止まった run の扱いは下の「判定の線」で事前に決める。
8. **run ごとに新しい出荷先を作る。** 出荷のポートは 8797（6 周目の本番が 8787 を持ったままかもしれないため）。

## 入口の確認（作成担当、費用なし）

lap がゲート `entrance` で止まったら、作成担当が次を行う。

1. 各組の `[minority]` の宣言を、参照実装（[refapps/server.cjs](refapps/server.cjs)。6 周目の版から始め、足りない答えは切り替えを足す。既定の動きは 6 周目と同じに保つ）の設定に写す。
2. `entrance.ts` で、宣言どおりの参照実装で全シナリオを流し、答えを 1 つずつ戻して依存表（`revert`・`only`）を出す。宣言どおりで落ちたシナリオは、作成担当が読んで次のどれかに決める: 期待値の誤り／宣言されていない別の選択／参照実装の不足。金額の期待値は手でも計算する。
3. `baseline.ts` で、22 回分の commit を 2 組のシナリオで流す。
4. **確かめた少数派シナリオ**: 宣言どおりの参照実装で通り、どれか 1 つの答えを戻すと落ち、22 回のうち過半で落ちるもの。**確かめた点**: その点の `only`（空なら `revert`）のシナリオが、22 回のうち過半で落ちる点。それ以外のシナリオは、参照実装でも 22 回すべてでも通るはずである。通らないものがあれば上の 3 分類で決め、期待値の誤りがあれば組を承認しない。
5. 上の「設計の要点」3 の条件で、組を承認するかを決める。
6. 結果を `docs/lap-7/entrance-summary.md`（ゲートの `read`）と `docs/lap-7/prereg.json`（ゲートの `fix`）に書く。両方が揃うと、同じ `lap` コマンドでゲートの要約が出る。

## 事前登録（`prereg.json` の形）

```json
{"maxAttempts": 5,
 "sets": {"hard-1": {"minority": ["<確かめた少数派シナリオ>"],
                     "points": {"<点>": ["<その点の only のシナリオ>"]},
                     "arms": {"summaries": ["hard-1", "hard-1-b"], "bare": ["hard-1-bare-a", "hard-1-bare-b"]}},
          "hard-2": {"...": "..."}},
 "labels": {"hard-1": {"<点>": {"amount": true, "direction": "directional|opaque"}}}}
```

`labels` は集計の道具（`attempts.ts`）は読まない。報告で点ごとの結果と並べる。

## 判定の線（事前に決める）

run ごとに、組の確かめた少数派シナリオ（`minority`）で分類する（6 周目と同じ。正確には「少数派シナリオの部分集合での収束」）。

- **P1**: 1 回目で少数派シナリオがすべて通った（やり直しは試されない）。
- **CONV**: 1 回目は落ち、5 回以内のどこかの試行で少数派シナリオがすべて通った。
- **INCOMPLETE**: CONV に届かないまま、5 回目より前に止まった（費用の上限・緊急停止・エラー）。
- **NEAR**: 5 回目まで走り、少数派シナリオの合格数が 1 回目より最後に多く、それ以外の合格数が減っていない。
- **STUCK**: それ以外。

判定:

- 腕ごとの判定（要約あり: 組ごとと 2 組を合わせて／bare: 組ごとと 2 組を合わせて）。試された run（CONV・NEAR・STUCK）が 3 未満なら **決められない**。過半が CONV なら **支持**、過半が STUCK なら **支持しない**、それ以外は **決められない**。組ごとは各腕 2 本しかないので、組ごとの判定は必ず「決められない」になる。組ごとの結果は表として並べる。
- **要約の効果**（2 組を合わせて、組ごとにも出す）: d = CONV の割合（要約あり）− CONV の割合（bare）。分母は CONV・NEAR・STUCK・INCOMPLETE の run。P1 と走らなかった run は分母に入れない。INCOMPLETE を CONV とみなした場合と、みなさない場合の両方で d を出す（要約ありの腕の INCOMPLETE を CONV にしない・bare の INCOMPLETE を CONV にする場合が下限）。d ≥ 0.5 なら **効果あり**、d ≤ 0 なら **効果は見えない**、それ以外は **不明**。下限と上限で結論が違えば **不明（打ち切りのため）**。統計的な検定はしない。
- 記述として出すもの: 全シナリオが初めて通った試行と、最後の試行の合否（出荷したか）。点ごとに、各 run で `only` が初めて通った試行。後退（試行 n で通り n+1 で落ちたシナリオ）。LLM 判定だけで落ちた試行。作る役が実際に受け取った文。

## 手順（実行担当）

cwd は工場のこのワークツリー（ブランチ `feat/factory-lap-7`）。5 周目の状態ディレクトリ `../factory-lap-5/.factory-lap5` があること（settle-a1 をコピーする）。

```bash
npm run factory -- lap examples/lap-7.json
```

1. 最初はゲート `entrance` で、`prereg.json` と `entrance-summary.md` を待って止まる（exit 3）。作成担当に知らせる。
2. 作成担当が入口の確認を済ませたら、同じコマンドをもう一度打つ。ゲートの要約のパスが出る（exit 3）。オーナーが要約と `entrance-summary.md` と 2 組の承認要約を読む。
3. 承認: `npm run factory -- lap examples/lap-7.json --approve entrance --by <承認者名> --version <要約の version>`
4. 同じコマンドで再開する。run 8 本と最後の集計まで流れる（`lap lap7: done`、exit 0）。run の失敗（試行上限以外）・費用上限・緊急停止は lap の失敗として止まり（exit 1）、最後の集計だけは走る。
5. 集計の出力と、`.factory-lap7/` のパスを作成担当へ送る。

緊急停止: 別の端末から `npm run factory -- stop`。後片付け: `kill "$(cat .factory-lap7/prod/server.pid)"`。

## 何が言えないか（あらかじめ）

- 3 つの「難しさ」（金額に絡む・向きが読めない・点が多い）は 1 つの束で、どれが効いたかは分けられない。点ごとの表（`only` とラベル）で手がかりだけ出す。
- run は 8 本で、組ごとの各腕は 2 本しかない。組ごとの判定は出せない。
- 下書き役が指示文どおりの点を選ぶとは限らない（6 周目には「少数派」の見立てが 1 点外れた）。条件を満たさなければ下書きし直しで費用が増える。
