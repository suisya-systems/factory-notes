# 7 周目の報告（2026-10-18）

工場の 7 周目の結果を報告する。この周には 2 つのねらいがあった。1 つは、`factory lap <定義ファイル>` を初めて実戦で使うこと。もう 1 つは、6 周目の報告の「次の周への提案」1・2 を実施することである。提案 1 は、前提 2（やり直しで合格に近づくか）を難しい側で試す。提案 2 は、不通過の要約を返さない対照の run を置く。手順と設計は [runbook.md](runbook.md)、入口の確認は [entrance-summary.md](entrance-summary.md)、6 周目の報告は [../lap-6-report.md](../lap-6-report.md) にある。設計の正本は design/grand-design.md。

## この文書での言葉

6 周目の報告と同じ言葉を使う。新しい言葉は次のとおり。

- **7 周目 / この周**: 2026-10-17〜18 に回した、工場の 7 回目の実行。状態ディレクトリは新しく始めた（`.factory-lap7`）。
- **定義ファイル**: この周の手順をすべて書いた英語の JSON（[lap.json](lap.json)、factory リポジトリの `examples/lap-7.json`、sha256 `86439bce2ffcf8283d438c5b145de90a9187bf61438c559b2e8683b68241fbd4`）。実行担当が打ったのは、`factory lap` のコマンドと、ゲートの承認コマンドだけである。
- **要約あり / bare**: run の 2 つの腕。
  - 要約あり（summaries）は、これまでどおりの run である。落ちたシナリオの承認済みの 1 行要約が、作る役に返る。
  - bare は対照の run である（`run --feedback bare`）。落ちたシナリオ 1 本ごとに「- failed: a hidden scenario」の 1 行だけが返る。作る役にわかるのは、落ちたことと落ちた本数だけで、どれが・なぜ落ちたかはわからない。LLM 判定が承認しなかったときの行は、どちらの腕にも残る。
- **確かめた少数派の点 / 少数派シナリオ**: 入口の確認を通り、事前登録で固定した点とシナリオ（[prereg.json](prereg.json)）。
- **金額に絡む点**: 少数派の答えを多数派に戻すと、精算の金額か送金が変わる点。
- **向きが読める（directional）/ 読めない（opaque）**: 要約を読めば、何をどちらへ直せばよいかがわかるか。作成担当が要約ごとに判断した。

- **前提 2 は、この周の条件では支持された。対照ではまったく収束しなかった。**

  - bare の 4 run は、すべて 5 試行の上限で STUCK だった。

## 入口の確認

詳しくは [entrance-summary.md](entrance-summary.md) にある。要点は次のとおり。

- **確かめ方は 6 周目と同じで、モデルは呼んでいない。**
  - 参照実装（[refapps/server.cjs](refapps/server.cjs)）を宣言どおりに設定し、全シナリオが通ることを確かめた。
  - 答えを 1 つずつ多数派に戻し、どのシナリオが落ちるかを見た（[entrance.ts](entrance.ts)、結果は entrance-hard-1.json・entrance-hard-2.json）。
  - 同じ仕様から要約なしで作った 22 回（5 周目の 16 回と、6 周目の 6 run の 1 回目）の commit でも流した（[baseline.ts](baseline.ts)、結果は baseline-output.md）。
- **下書き役への追加の指示（`--minority-brief`）。** 点を 4〜5 個選ぶこと。そのうち 2 個以上は、アプリが計算する金額を変える点にすること（分担額・端数・送金と金額）。一覧の順は選ばないこと。
- **下書き役はどちらの組でも端数を選んだが、2 組とも外れた。**
  - hard-1 は「N 件目の支出では、受益者の N mod k 番目から端数を配る」を選んだ。22 回のうち 11 回が、すでにこの答えと同じ金額になった。
  - hard-2 は「グループに 1 つのカーソルで、受益者でない人を飛ばして配る」を選んだ。参照実装で多数派に戻しても、落ちるシナリオが無かった。
  - 下書き役の「多数派は最初の受益者に配る」という見立ては、6 周目の「送金の並び」と同じく外れていた。多数派の作り方は「それまでの端数が最も少ない人へ、同数ならグループの順」だった。
- **確かめた点。**
  - hard-1: ペアごとの相殺（シナリオ 2 本）、空の受益者は全員、1 人のグループは拒む。
  - hard-2: ペアごとの相殺（2 本）、受益者を省くと支払った人以外の全員、同じ人を 2 回並べると 2 人分、同名のメンバーを拒む。

- **少数派以外で、22 回のうちに落ちたシナリオがある。** hard-1 の offsetting-expenses-settle-to-net（11 回）、hard-2 の payer-among-beneficiaries（5 回）、remainder-rotation-skips-non-beneficiaries（3 回）。どれも、端数を同数のときに誰へ配るかの選び方による。期待値の誤りではない。これらは「ほか」の列に入る。

### 作る役が受け取ったもの

- **要約あり。** 1 回目の後に、落ちたシナリオの 1 行要約が返った（上の要約の一覧は vault の scenarios.json）。例:
  - hard-1: 「When one member owes a second and the second owes a third, both real debts stay as separate transfers」

### 作る役の直し方

各 run で、試行ごとの commit の差分を読んだ。

- **要約ありの 2 回目は、少数派の点を一度に直していた**（差分は追加・削除あわせて 130〜175 行で、作る役自身のテストと README を含む）。精算は、差し引きの残高を組む作りから、支払った人と受益者の組ごとに相殺する作りに書き換えた。そのうえで、受益者が空・省略のとき、受益者の重複、同名のメンバーを直した。
- **bare は、どこが落ちたかを当て推量で探していた。** 試行 2〜5 で足されたテストの名前に、それが出ている。
  - 送金の本数: 「settlement uses minimal transfers」（hard-1-bare-a）、「settlement uses the minimum number of transfers」（hard-1-bare-b）、「transfers are minimal」（hard-2-bare-b）。少数派の答えと逆の向きである。
  - 端数の配り方を何度も変えた: 「payer absorbs leftover yen…」「leftover yen … is not tied to payer or list position」「leftover yen follows exact fair share…」。
  - 仕様にない周辺: 保存をグループごとのファイルにする、本文の上限を 1 MB から 10 MB にする、クライアントが id を指定できるようにする（hard-2-bare-a・hard-2-bare-b・hard-1-bare-b）。
  - 少数派の点に当たる直し（受益者が空、受益者の重複、同名、人数）に向かった試行は 1 つも無かった。

- **対照の結果は、設計からほぼ予想できた。** 少数派の答えは、定義上、作る役が自分からは選ばない答えである。22 回の baseline でも、確かめた点はほぼ 22 回とも外れていた。bare の作る役が落ちた本数だけを頼りに当てられないのは、自然な結果である。対照が示したのは「やり直しの偶然では直らない」ことで、要約のどの性質（向きを書くこと、シナリオを特定すること、本数）が効いたかは分けていない。中間の対照（たとえば、シナリオの種類だけを返す run）は置いていない。
- **run は 8 本で、組ごと腕ごとに 2 本しかない。** 組ごとの判定は、事前登録の線で「未決」である。統計的な検定もしていない。
- **少数派の点は、下書き役が選んだものである。** 2 組とも「ペアごとの相殺」を選んだので、金額に絡む点は 2 組で同じ 1 種類だけである。点ごとに見ても、2 組は独立していない。
- **hard-1 の 3 試行目の観察は、事前登録の外である**（opaque に近い要約で 1 回で直った例）。少数派シナリオではなく、1 例を 2 回見ただけである。
- **LLM 判定は、少数派シナリオが落ちた試行もすべて承認した。** AND の判定が無ければ、どの run も 1 回目で出荷していた（6 周目と同じ）。
- **1〜6 周目から引き継いでいる限界。** lap 台帳にはロックが無い。作る役は認証トークンを読める。合成トラフィックは本番の観測にほとんど意味が無い。入口の確認は工場の外で、作成担当が手で回している。
