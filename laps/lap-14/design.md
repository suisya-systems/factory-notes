# 14 周目の設計: 規模の作り方の比較と推奨

13 周目（[../lap-13/report.md](../lap-13/report.md)）は題材 A 単独の 495 語で、Q = 100 % は目的（依頼を大きくしても合格率が保たれるか）の測定にならなかった（[../../decisions.md](../../decisions.md) D13-7）。オーナー判断（2026-10-27）は、14 周目を「割れるかもしれない大きさ」で組み、成功の線を Q 90 % に置くこと。題材の候補は監査 [../../research/runtime-fit-audit-2026-10-27.md](../../research/runtime-fit-audit-2026-10-27.md) の A・B・C。

### 案 2 を採らない理由（C の偽サービス）

`run` の手のプログラムはネットワークなしで走る（`factory:src/program.ts:54, 165`）。`run` の手が持てるキーは `run` `stdin` `files` `read` `env` `expect` `capture` だけで、偽サービスの手（`service: true`）は HTTP の手に限る（`factory:src/scenario.ts:77, 98`）。つまり、通知先の偽物を立ててプログラムに送らせ、受け取った内容を確かめる 1 本のシナリオは、今の工場では書けない。作るなら工場の変更になり（Issue 案の規模は前例 #17・#24 並み）、14 周目の前提が 1 つ増える。C の issue の本文は通知先を 5 つ挙げ、送る本文を決めていないので、依頼文を書く前に人が通知先を 1 つ選んで形を決める必要もある。どちらも、判断仰ぎに回す（完了報告）。

### 案 3 を採らない理由（plan / part）

`plan` は PR #67 以降、既存リポジトリの上でも部分を積める（`factory:src/plan.ts:184`、`extending`）。ただし plan は部分ごとに `run`（やり直しあり・LLM 判定あり・出荷あり）で進み、`replicate` の Q（build ごとの合格割合の平均、較正と同じ式）は出ない。測るものが「分けると通るか」に変わり、成功の線 Q 90 % と較正の比較が使えない。費用も、部分の数だけ draft と run が増える。大きさの効果を見る次の周の候補として残す。

### 案 4 を採らない理由

語数だけを増やした水増しの依頼は、較正の「大きい依頼」（部品が 4 本、絡みが 37〜49 組）と同じ種類の大きさではなく、結果の読み方が決まらない。

## 推奨: 案 1（A + B を 1 本の依頼にする）

理由:

1. **1 つの commit の上で組める**（`003efef`）。A と B の base が違うという問題が起きない。
2. **決定的に確かめられる**。B は標準入力・終了コード・ファイルだけで、時計の項目は形だけを見る。
3. **工場の変更が最小**（transcript と費用の定数だけ）。偽サービスの手が要らない。
4. **「割れるかもしれない」要素が入る**。B は、同じ変更の中に「失敗したときに安全側へ倒す」性質（書けないときも古い record を消す）を持ち、13 周目の A のように規則を全部書き切る形にしていない。原則 1 文と、書いた規則から導ける細部が、builder ごとにばらつく場所になる。ただし、これで Q が 90 % を割る保証は無い。
5. 規模は、13 周目の 2.2 倍（語数）、1.45 倍（見せる字数）、約 2 倍（シナリオ本数の見込み）。較正の L0〜L1 の間で、**語数の段としては L1 の手前**に当たる。「依頼を大きくしても」の問いには、まだ小さい側である。この点（もっと大きくするか、案 2 にするか）はオーナーの判断に残す。

13 周目との違い（事前登録の `comparability` に書く）: 2 つの変更を 1 本の依頼にした点、`spawn-prompt-step` が標準入力と生成ファイルを使う点、成功の線が 90 % である点、契約のコマンドが `dispatcher` までで、サブコマンドは各シナリオの argv が選ぶ点。

## 依頼文の語数の考え方

目安は 900 語前後。上限は、見せる範囲の字数が 200,000 字（`--base` の上限）を超えないことと、分類が呼ぶたびに見せる全文を入れるので費用が字数とシナリオ数の積で増えること。書いた版は 1,082 語で、目安より 2 割長い。削るなら Part 1 の説明（表の説明の重複）か Part 3 の記述を縮められるが、規則の欠けが増えると「推測が要る場面」の質が変わる。決めるのは窓口（長さを揃えるなら、B の 3 つの `--` の説明を 1 つの表にして 100 語ほど削れる見込み）。

## 見せる範囲（`--base-path`）

A の範囲（13 周目の 7 範囲 + `docs/cli.md:1-160` + 試験 3 範囲、約 81,000 字）に、B の分を足す。

| 範囲 | 字数 | 理由 |
|---|---|---|
| `runner.py:2549-2607` | 約 3,350 | `approve_spawn_prompts_step`。`decide_argv` を作る所。13 周目の範囲（2279-2349、2610-3160）の間に落ちている |
| `src/claude_org_runtime/dispatcher/spawn_prompt.py`（全体） | 13,599 | `decide`、状態の名前、終了コード、引数の定義 |
| `tests/test_spawn_prompt.py`（全体） | 19,122 | 画面の例（シナリオの標準入力に使う形）の見本 |

合計 約 117,500 字（`003efef` で、`sed` と `wc -c` による実測: runner 58,845 + 3,349、`docs/cli.md` 10,193、`tests/test_dispatcher_runner.py` 12,372、`spawn_prompt.py` 13,599、`test_spawn_prompt.py` 19,122）。200,000 字の上限の 59 %。13 周目の 81,000 字の 1.45 倍で、分類の費用がその分増える（[factory-issues.md](factory-issues.md) の 2）。費用が高ければ、試験 → 文書 → `build_plan` の順に削る（13 周目の runbook と同じ）が、`test_spawn_prompt.py` を削ると標準入力の画面の形が見えなくなり、期待値の誤りが増える。最後に削る。
