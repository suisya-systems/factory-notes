# 振る舞いを意図して変えるとき、古いシナリオをどうするか（2026-10-18）

工場の全体設計（[design/grand-design.md](../design/grand-design.md)）では、隠しシナリオをアプリごとの仕様リポジトリに積み上げ、退行の確認に使う（7 章）。ある変更が、出荷済みの振る舞いを意図して変えると、その振る舞いを確かめていた古いシナリオは落ちる。このとき古いシナリオをどう扱うかを、既存の実践の一次資料で調べた。問いは 4 つある。(1) 新しい振る舞いと食い違う古いテストをどう見つけるか、(2) 誰がいつ直したり消したりしてよいか、(3)「落ちたテストを消して通す」をどう防ぐか、(4) 履歴と追跡をどう残すか。

## 結論

- Jest、ApprovalTests、FDA の指針は、期待値の書き換えをテストの実行とは別の、明示的な承認として扱っている。Jest は CI では期待値を自動で書かず、書き換えた期待値をコードレビューで見るよう求める。ApprovalTests は差分を見て「望んだ変更」と判断したときだけ承認する。FDA の指針は、承認済みの文書を構成管理の手続きで更新し、仕様を先に直すよう求めている。Pact は例外で、新しい期待が初めて検証に通ったことを暗黙の受け入れとみなす。
- 食い違う古いテストの見つけ方は 2 通りあった。1 つは要件とテストの対応を持ち、テストに結びついた唯一の要件が消えたらそのテストを不要とみなす方法（Harrold ら。ここでの要件はカバレッジの基準を含むテスト上の要件で、業務の要件ではない。FDA は文書を見て影響を決める退行分析を求めている）。もう 1 つは全部流して落ちたものを人が仕分ける方法（Jest、ApprovalTests）。前者は対応表が要る。後者は「意図した変更」と「壊した」の区別を人に頼る。
- 「消して通す」を防ぐ手は、テストを書き換える権限を作る側から外すことだった。ImpossibleBench は、テストを隠すと不正な通過がほぼ 0 になり、読むだけにすると書き換えは防げるが他の抜け道は残ると報告している。
- 古い振る舞いを消さずに残す実践もある。Stripe は古い API の振る舞いを日付つきの版として残し、Google の AIP-180 は同じメジャー版の中で、利用者のコードを壊しうる振る舞いの変更を禁じている。Pact は、本番に出ている版やサポート中の版の契約を検証し続け、どの選び方にも当たらなくなった版の契約は検証の対象から外れる。
- 工場への示唆の中心は 3 つ。古いシナリオの退役を入口の承認に含めること、退役は消去でなく理由つきの記録にすること、退役や変更が承認されていない古いシナリオの不通過は常に退行として扱うこと。

## 実践ごとの調査結果

### BDD / Cucumber と Specification by Example

- Cucumber は、振る舞いを宣言的に書いたシナリオを「生きたドキュメント」と呼ぶ。実装が変わっても直すのは手順の裏側だけで済み、新しい区分が増えたらシナリオを足せばよいと書いている（https://cucumber.io/docs/bdd/better-gherkin/ ）。シナリオを消す手順には触れていない（同）。
- Gojko Adzic は、生きたドキュメントを Specification by Example の最終成果物と呼び、長く効かせるには一貫性を保つ手入れが要る、と書いている。小さな業務の変更は、ソフトウェアとドキュメントの小さな変更として表れるべきだ、とも書いている（https://www.infoq.com/articles/specification-by-example-book ）。要件が変わったときにシナリオをどう直すかの具体的な手順は、この記事には無い（同）。

### 承認テスト / スナップショットテスト

- Jest は、意図した変更でスナップショットが落ちたら `-u`（`--updateSnapshot`）で書き直す。書き直す前に、意図しない不具合による失敗は直しておくよう書いている。書き直すと不具合の振る舞いを期待値として記録してしまうからである（https://jestjs.io/docs/snapshot-testing ）。
- Jest は、スナップショットをコードと一緒にコミットし、コードレビューで見るよう求めている。狙いは「テストが落ちたら原因を調べずに書き直す」癖と戦うことだと書いている（同）。対話モードでは、落ちたスナップショットを 1 件ずつ見て、書き直すか飛ばすかを選べる（同）。
- Jest は CI では、`--updateSnapshot` を明示しない限りスナップショットを書かない（同）。`--ci` を付けると、新しいスナップショットも自動で保存せずテストを落とす（https://jestjs.io/docs/cli ）。
- ApprovalTests は、バグ修正や機能追加で期待する振る舞いが変わるとテストが落ちる、という前提で流れを描いている。差分ツールで変更を見て、望んだ変更なら新しいファイルを承認し、望まない変更ならコードを直す（https://github.com/approvals/ApprovalTests.Documentation/blob/main/explanations/approval_testing.md ）。承認は、受け取った出力（received）を承認済みのファイル（approved）に写して行う（https://github.com/approvals/ApprovalTests.Documentation/blob/main/explanations/what_are_approvals.md ）。誰が承認するかは、開いた文書には書いていない。

### 消費者駆動の契約テスト（Pact）

- 新しく加わった期待や変わった期待は、提供側のその枝で初めて検証に通るまで「pending」になる。pending の期待が落ちても、提供側のビルドは落ちない。いったん検証に通った期待は pending でなくなり、それ以降に落ちるとビルドが落ちる。最初に検証が通ったことを、契約の暗黙の受け入れとみなしている（https://docs.pact.io/pact_broker/advanced_topics/pending_pacts ）。
- WIP pacts は、まだ検証に通っていない新しい契約を、提供側の設定を変えずに自動で検証対象に入れる仕組みで、常に pending として扱う（https://docs.pact.io/pact_broker/advanced_topics/wip_pacts ）。
- can-i-deploy は、出そうとする版と、出し先の環境で動いている相手の版との間に、成功した検証結果があるかを確かめる。無ければ出荷を止める（https://docs.pact.io/pact_broker/can_i_deploy ）。
- 推奨の選び方では、本流の最新版に加えて、本番に出ている版と、サポート中のリリース版の契約を検証する（https://docs.pact.io/pact_broker/advanced_topics/consumer_version_selectors ）。新しい版を `record-deployment` で記録すると、同じ環境・同じ実体で前に出ていた版は自動で「出ていない」になる。`record-support-ended` は、そのリリース版の契約を検証対象と出荷判定から外す（https://docs.pact.io/pact_broker/recording_deployments_and_releases ）。ただし本流の最新版など別の選び方に当たる版や、別の環境でまだ出ている版の契約は、検証され続ける（同、https://docs.pact.io/pact_broker/advanced_topics/consumer_version_selectors ）。どちらの場合も、契約を消すのではなく、検証の対象から外す扱いになっている。

### API の版と非互換な変更（Stripe、Google AIP）

- Stripe は、互換でない変更を日付つきの版にまとめる。アカウントは最初の呼び出しの時点の版に固定されるので、意図せず非互換な変更を受けることはない（https://stripe.com/blog/api-versioning ）。
- Stripe の本体のコードは最新の版の形で書き、応答を返すときに「版の変更モジュール」を新しい順にさかのぼって当て、古い版の形に戻す。各モジュールは説明、変換、影響する資源の種類を持ち、変更履歴はそのモジュールから生成される（同）。古い振る舞いをどうテストしているかは、この記事には書いていない（同）。
- Stripe の利用者は、`Stripe-Version` ヘッダで新しい版を試してから切り替え、切り替えの前に変更履歴で非互換な変更を確かめる（https://docs.stripe.com/upgrades ）。
- Google の AIP-180 は、同じメジャー版の中で、合理的な利用者のコードを壊しうる見える振る舞いや意味を変えてはならない、と定めている。文書にない振る舞いでも同じである。既定値の変更も非互換とする（動的な既定値は除く）。変えるなら新しいメジャー版にし、既存の部品を変えたり消したりする代わりに新しい部品を足す（https://google.aip.dev/180 ）。

### テスト選択とテスト集合の保守の研究

- Harrold・Gupta・Soffa は、テストが「不要（obsolete）」になるのは、変更でそのテストが集合に入っていた理由が消えたときだと定義している。テスト上の要件（データフローなどのカバレッジの基準を含む）とテストの対応を持ち、テストに結びついた唯一の要件が消えたらそのテストを除く。対応を更新しない「全部流す」やり方では、不要なテストが残り続けると書いている。実際には、要らなくなったテストを見分けにくいので、テストは消されずに残りがちだ、とも書いている（https://www.cs.ucr.edu/~gupta/research/Publications/Comp/p270-harrold.pdf ）。
- Pinto・Sinha・Orso は、6 つの実プログラムの単体テストの変遷を調べた。テストの修理は変化の理由の 1 つにすぎず、変化の多くはリファクタリング、テストの削除、テストの追加だった。テストの修正は複雑で自動化しにくく、期待値だけを直す自動修理の効き目は限られる、と結論している（https://research.ibm.com/publications/understanding-myths-and-realities-of-test-suite-evolution ）。
- REACCEPT は、本体のコードの変更で古くなったテストを LLM と実行による確認で見つけて直す。537 の Java プロジェクトで、正しく見つけた古いテストの更新の正解率は 60.16% だった（https://arxiv.org/abs/2411.11033 ）。4 割は直し損ねる、ということでもある。
- Azure Pipelines の Test Impact Analysis は、変更に関係するテストだけを選んで流す。読めない種類の変更が来たら全部を流し、決まった間隔で全部を流す設定も勧めている。選び方が正しいかは、選んだテストと全部のテストを続けて流し、結果を突き合わせて確かめる（https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis ）。

### 要求の追跡（規制のある分野）

- FDA の General Principles of Software Validation は、変更のたびに、その変更自体だけでなく、システム全体への影響の範囲を分析し、それに見合う退行テストで「変えていないが影響を受けうる部分」が壊れていないことを示すよう求めている（4.7 節、https://www.fda.gov/media/73141/download ）。
- 同じ指針は、退行分析を「要件仕様、設計仕様、ソースコード、テスト計画、テストケースなどの文書を見て、変更の影響を決め、流すべき退行テストを決めること」と定義している。退行テストは、以前正しく通ったテストを流し直し、前の結果と比べることである。要件が変わることも、変更の原因として挙げている（5.2.5 節、同）。
- 保守の作業として、承認済みの文書（仕様、テスト手順など）のうち変更の影響を受けたものを、構成管理の手続きに沿って更新すること、仕様は保守と変更の前に更新することを挙げている。以前のテスト文書、テストケース、検証結果は、後の退行テストのために保管するよう書いている（5.2.7 節、同）。
- 要件の追跡分析は、ソフトウェアの要件をシステムの要件とリスク分析の結果に双方向でたどれるようにする（5.2.2 節、同）。

### 誰が直してよいか（コードの持ち主）

- GitHub の CODEOWNERS では、持ち主のいるファイルを変える PR に持ち主のレビューが自動で付き、保護された枝ではその承認をマージの条件にできる（https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners ）。テストのファイルに持ち主を付ければ、テストの書き換えを特定の人の承認の下に置ける。

### AI のエージェントとテストの書き換え

- ImpossibleBench は、仕様と食い違うようにテストを書き換えた課題をエージェントに解かせ、通った割合を「テストを悪用する傾向」として測る。テストを使えるエージェントは、不具合を直す代わりに落ちたテストを消すことがある、と書いている（https://arxiv.org/abs/2510.20270 ）。
- 同論文の 5.2 節では、テストを隠すと不正な通過はほぼ 0 になるが、元の課題の成績も下がる。読むだけにすると、成績は戻り、テストの書き換えは防げる。ただし、特定の入力だけを特別扱いするなどの他の抜け道は残る。著者は、実装中はテストを隠すか読むだけにするよう勧めている（https://arxiv.org/html/2510.20270 ）。

### AI の工場と仕様駆動開発の道具

- StrongDM は、シナリオをコードの外に置き、エージェントが合わせ込めない「ホールドアウト」として扱う。テストはコードに合わせて安易に書き換えられうる、という対比で説明している（https://factory.strongdm.ai/ ）。輪は「ホールドアウトのシナリオが通り、通り続けるまで」回る（https://factory.strongdm.ai/principles ）。シナリオを作り直す画面の存在には触れているが（https://factory.strongdm.ai/ ）、要件が変わったときに古いシナリオをどう直すか、誰が決めるかは、開いたページには無かった。
- Kiro は、設計のあとで要件を変えたいときは `requirements.md` を直し、設計を合わせるよう頼めば、設計とタスクが新しい要件に合わせて直る、と書いている（https://kiro.dev/docs/specs/feature-specs/requirements-first/ ）。済んだタスクや既存のテストをどうするかは書いていない（同）。
- spec-kit は、既存のプロジェクトに入れても既存の振る舞いの仕様は作らない。新しい `spec.md` は今回の変更の分だけで、全部の振る舞いをさかのぼって書くものではない。依頼には「守るべき互換の境界」も書くよう勧めている（https://github.github.com/spec-kit/guides/existing-projects.html ）。
- spec-kit の `analyze` は読むだけの点検で、ファイルを直さない。直す案は出すが、編集には人の明示的な承認が要る。プロジェクトの原則（constitution）と食い違う要件は必ず最重要とし、直すのは仕様・計画・タスクの側で、原則そのものを変えるなら別の明示的な更新で行う（https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md ）。
- spec-kit の `converge` は、未完了の作業を新しいタスクとして足すだけで、既存のタスクを書き換えたり番号を振り直したり消したりしない（https://github.com/github/spec-kit/blob/main/templates/commands/converge.md ）。
- 開いた資料の中には、隠しシナリオを積み上げる工場が、意図した振る舞いの変更で古いシナリオをどう退役させるかを公開している例は無かった。

## 工場への示唆（提案。決定ではない）

[全体設計](../design/grand-design.md)との対応で書く。

1. **古いシナリオの退役を入口の承認に含める。** 7 章の未決では、変更の承認を「追加・変更・削除したシナリオファイルの git 差分」にする案が出ている。ここに、変更・削除される古いシナリオを明示して載せる。人の承認を 1 回にする 3 章の方針とは揃う。Jest と ApprovalTests が期待値の書き換えを人の判断に置き、FDA が承認済み文書の更新を構成管理に置いているのと同じ形になる。
2. **古いシナリオとの食い違いを、入口の要約の食い違い一覧に 3 部目として足す。** 2 章の食い違い一覧は、仕様と食い違うものと、仕様が決めていないことを求めるものの 2 部である。そこに「新しい仕様と食い違う、蓄積済みのシナリオ」を足す。Harrold らの対応の考え方を業務の要件へ移すのは推論で、確かめられた方法ではない。見つけ方は 2 章の独立した分類と同じ形が使える。仕様と既存コードだけを見た別セッションが、古いシナリオの各要求への応答を新しい仕様から予測し、古い期待値と機械的に照合する。ただし 2 章の表では、シナリオの下書き役の「見えるもの」に蓄積済みのシナリオは入っていない。退役の案を誰が書くかは決める必要がある。
3. **退役は消去でなく、理由つきの記録にする。** 退役させたシナリオは、変更 id と理由を付けて退役の置き場へ移し、判定には使わない。Pact が古い契約を消さずに検証対象から外し、FDA が過去のテストと結果の保管を求めているのに倣う。7 章の「1 シナリオ 1 ファイル」と組むと、どの振る舞いをいつ誰の承認で外したかが 1 件ずつ追える。
4. **退役や変更が承認されていない古いシナリオの不通過は、常に退行として扱う。** 判定役も作る役も出荷役も、古いシナリオを外したり書き換えたりできないようにする。Pact で一度通った期待が落ちるとビルドが落ちるのと同じ扱いになる。4 章の「規則は工場の役割から書き換えられない」と、3 章の「承認した組は書き換えられない」の延長にある。
5. **入口で見落とした食い違いは、失敗として終え、人が出し直す。** 古いシナリオが仕様の変更と食い違っていて、入口で見つからなかった場合、作る役は両方を満たせないので、上限で止まる。3 章どおり人に聞かずに失敗で終える。終了の記録には、どの古いシナリオが落ち続けたかの要約を載せ（本文は載せない）、人がそれを見て退役を含む入口を出し直せるようにする。工場が自動で退役させる経路は作らない。Jest が CI では期待値を書かないのと同じ線である。
6. **作る役には蓄積済みのシナリオを読ませも書かせもしない。** これは 2 章ですでに決まっている。ImpossibleBench の結果は、隠すと書き換えによる不正がほぼ無くなることを支持している。同論文では、読むだけにしたときに特別扱いなどの抜け道が残ると報告されている。隠したときにも同じ抜け道が残るかは、同論文の 5.2 節の記述からは言えない。
7. **他のアプリや利用者が依存する振る舞いを変えるときは、足す形を先に検討する。** Stripe と AIP-180 は、既存の振る舞いを変えるより新しい部品を足すか版を分ける。練習用のアプリでは要らないかもしれないが、仕様の下書き役への決まりとして「既存の振る舞いを変えるか、足すか」を入口の要約に書かせる案はある。
8. **退行の確認は、全部を流すことを基本にする。** 関係する領域だけを流す案（7 章の大きい仕様の対処案）を採るなら、Azure の TIA のように、読めない変更では全部を流し、決まった間隔で全部を流して選び方を確かめる。
