# 大きい仕様・複雑な仕様をどう扱うか（2026-10-18）

工場の全体設計（[design/grand-design.md](../design/grand-design.md)）は、輪の 1 周を「1 件の変更」としている（1 章）。依頼を複数の変更に分ける手順は決めていない。依頼が 1 変更に収まらないほど大きいとき、他の仕組みがどうしているかを一次資料で調べた。

## 結論

- 調べた仕組みの多くは、大きい仕様を作り始める前に小さい単位へ分け、計画として書き出す（Factory の Missions、Kiro、spec-kit、AWS の AI-DLC）。Missions と AI-DLC は、その計画を人が承認してから実行に入る。Kiro は段ごとに見直す流れと、見直しを後回しにする流れを選べる。spec-kit のひな形からは、分け方の承認が必須かは読み取れなかった。
- 分けた単位は 1 つずつ確かめ、区切りごとに全体のつながりも確かめる。Factory はマイルストーンの終わりに統合を確かめる。AI-DLC には、最初に端から端まで通る最小の骨格を作る選択肢がある。
- 曖昧さや矛盾は、作る前に洗い出して人に聞く仕組みが多い。spec-kit は仕様を書く段（specify）で確認の印を最大 3 個に絞り、残りは仮定として書く。
- Kiro・spec-kit・AI-DLC は、互いに依存しない作業だけを並列にする。Factory は、狭い範囲だけを並列にして基本は直列で進めるほうがうまくいったと書いている。
- 失敗の扱いは、確かめた資料では 3 通りあった。失敗時の行き先へ回す（Attractor）、失敗で止める（Attractor、spec-kit）、人が介入する（Missions、AI-DLC）。人に戻さず予算の上限で止まり、その後の扱いまで公開している例は見つからなかった。
- 人が書かずレビューもしない工場を公開している StrongDM は、大きい仕様の分け方を公開していない。公開しているのは、「意図が完全に書かれていれば、無人で端から端まで走れる」という前提と、非対話型エージェント Attractor の仕様（やり直し・終了条件・並列の決まり）である。

## 出典ごとの調査結果

### StrongDM（factory.strongdm.ai）

- 人が書かず人がレビューもしない条件として、「連なる自然言語の仕様（cascades of natural-language specifications）からシステムを育てられる」ことと、ソースを中身で調べずに自動で確かめられることを挙げている（https://factory.strongdm.ai/techniques ）。仕様をどう分けるかは書いていない。
- 輪は「隠しシナリオが通り、通り続けるまで回る」（https://factory.strongdm.ai/principles ）。止まる上限は書いていない。
- 開発を対話型と非対話型に分けている。非対話型は「意図が完全になったら端から端まで走る」。完全な意図の例は、RFC などの正式な仕様と検証用のテスト、それに既に動いているアプリ。対話型は「生成し、不明点を明らかにし、また生成し、承認し、修正する」を繰り返す（https://factory.strongdm.ai/techniques/shift-work ）。曖昧な仕様は非対話型には入れない、という線の引き方になっている。
- 大量の項目を扱う方法として Pyramid Summaries を挙げている。項目ごとに 2 語・4 語・8 語…の要約を並行で作り、似たものをまとめ、必要なところだけ詳しく開く（https://factory.strongdm.ai/techniques/pyramid-summaries ）。対象は要約の読み方で、仕様の分割ではない。
- 非対話型のエージェント Attractor は、工程（実装・最適化・検証など）を頂点にしたグラフとして動き、「収束するか終了条件を満たすまで」グラフをたどる（https://factory.strongdm.ai/products/attractor ）。仕様は公開されている（https://github.com/strongdm/attractor ）。
  - 終わる時点で、通った工程のうち `goal_gate=true` のものが成功か一部成功でなければ、やり直し先へ戻る。やり直し先がどこにも無ければ失敗で終わる（https://github.com/strongdm/attractor/blob/main/attractor-spec.md 3.4 節）。
  - 工程ごとに `max_retries` でやり直し回数を決める。既定は 0 回（同 3.5 節）。
  - 上位のグラフは 1 度に 1 工程しか動かさない。並列は fan-out の工程の中だけで、同時に動かす数の既定は 4。fan-in の工程は結果のうち最良の 1 つを選ぶ（同 3.8 節、4.8 節、4.9 節）。
  - 子のパイプラインを見張る管理役の工程があり、周回数の上限（既定 1000）を超えると失敗で終わる（同 4.11 節）。
  - 人が選ぶまで止まる工程（`wait.human`）も仕様にある（同 4.6 節）。StrongDM の工場でこの工程を使っているかはわからない。
- 同じページで、Dan Shapiro の Kilroy を「英語の要件を Attractor のパイプラインに変えて実行する」実装として紹介している（https://factory.strongdm.ai/products/attractor ）。中身は読んでいない。

### Dan Shapiro の 5 段階

- L4 では、人が仕様を書き、仕様についてエージェントと議論し、計画を見直す。L5 は「仕様をソフトウェアに変える見えない箱」とだけ書いてある（https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/ ）。大きい仕様の扱いには触れていない。

### Factory 社（factory.com）の Missions

- 大きい、複数機能にまたがる仕事向け。人と Droid が対話して計画（機能とマイルストーン）を作り、承認された計画を orchestrator が実行する（https://docs.factory.com/missions/overview.md ）。
- 目安は 1〜500 機能。500 を超えるなら複数の Mission に分ける。数字は目安で、決まった上限ではない（同）。
- 計画づくりの段階で、Droid は質問して制約を探る。「一発のプロンプトではなく会話」と書いている（同）。
- マイルストーンの終わりに検証役が動き、テスト、退行の確認、全体がつながるかの確認をする。問題があれば orchestrator が直す仕事を足してから先へ進む。機能ごとに文脈の空のワーカーを立てる（https://factory.com/news/missions ）。
- 小さい案件はマイルストーン 1 つで足りる。大きい案件はマイルストーンを細かくすると、ずれや手戻りを減らせる（https://docs.factory.com/missions/planning.md ）。
- 見積もりは「総実行回数 ≈ 機能数 + 2 × マイルストーン数」。検証で問題が出ると増えるので、これは下限であって上限ではない（同）。
- 並列について、「直列で進め、狙った箇所だけ並列にするほうが、広く並列にするよりうまくいった」と書いている。長い計画では誤りがたまり、orchestrator が範囲を広く取りすぎることがあるとも書いている（https://factory.com/news/missions ）。
- 止まったときは人が orchestrator に話しかけて立て直す。機能のやり直し上限に達すると警告が出て、人がワーカーを調べる（https://docs.factory.com/missions/overview.md の Troubleshooting）。人を介さずに失敗として終える動きは書いていない。

### BCG（The Agentic Software Factory、2026-03-26）

- 隠しシナリオ（業務要件から作り、エージェントが届くコードベースの外に置く）を挙げている。関門ごとに承認に責任を持つ人がいる、とも書いている（https://www.bcgplatinion.com/insights/the-agentic-software-factory ）。
- 仕様の分け方には触れていない。開発サイクルの考え方として AWS の AI-DLC を引き、「bolt」（数日〜数時間で回す単位）で人が関門ごとに意図を定め、確かめるとしている（同）。

### AWS の AI-DLC（aidlc-workflows）

- 依頼（Intent）を、独立に実装できる単位（Unit）に分ける。分けた結果は単位どうしの依存とともに記録する（https://awslabs.github.io/aidlc-workflows/guide/glossary/ の Unit of work）。
- 依存の無い単位は同時に動かせる（同 swarm の項）。ビルドとテストと CI は、終わった単位の作業全体に対して 1 回走らせる（同 Bolt の項）。
- 「walking skeleton」を有効にすると、端から端まで通る最小の統合済みの断片を最初の単位にする。対象になる単独作業では、その単位は、人が認めた通しの確認コマンドを通り、人の承認を得てから、後の単位が始まる（同 Walking skeleton の項）。
- 対象になるワークフローでは、通常の完了を記録した許可の下で自動承認にできる。ただし計画の承認、有効にした要約の確認、確認コマンドの選択、骨格の承認、失敗の扱いは人に残る（同 Approval gate と Autonomy mode の項）。

### Amazon Kiro

- 仕様は要件・設計・タスクの 3 つの文書で書く（設計から始める流れもある）。タスクは追跡できる個別の作業に分ける。各段の文書には人が見直すボタンがある（https://kiro.dev/docs/specs/ ）。
- タスクの依存をグラフにし、依存の無いものを「wave」にまとめる。wave は順に、wave の中は同時に動かす（同）。
- プロジェクト全体を 1 つの仕様にせず、機能ごとに別の仕様を作ることを勧めている。段ごとに明示的に承認できる点を利点に挙げている。Quick Spec は、段ごとに見直してから次を作るかどうかが通常の流れと違う（https://kiro.dev/docs/specs/best-practices/ ）。
- 利用者が要件の分析を選ぶと、要件どうしの矛盾（1 つずつなら成り立つが、全部は同時に満たせないもの）、曖昧さ、書かれていない仮定を、設計の前に探す。見つけたら人に質問し、人が答えるか、意図したものとして退ける（https://kiro.dev/docs/specs/analyze-requirements/ ）。
- 要件から性質ベースのテストを作り、実装に対して走らせる。落ちたら最小の失敗例まで縮める。Kiro が実装を直すこともあるし、実装・テスト・要件のどれを変えるかを人と相談することもある（https://kiro.dev/docs/specs/correctness/ ）。

### GitHub spec-kit

コマンドのひな形（https://github.com/github/spec-kit/tree/c6a4c18f1d01a8bec241c618eb6dfea952508744/templates/commands ）で確かめた。

- 仕様を書くとき、わからないところは業界の通例で推し量って埋め、仮定として書く。`[NEEDS CLARIFICATION]` の印は最大 3 個まで。付けるのは範囲や体験への影響が大きく、解釈が分かれ、妥当な既定が無いものだけ（specify.md）。
- clarify は質問を 1 回の作業で最大 5 個に絞り、1 問ずつ聞いて仕様に反映する（clarify.md）。
- タスクは利用者の筋書き（user story）ごとに段階に分け、段階ごとに独立して試せる完成単位にする。最初の筋書きだけを最小の出荷単位として勧める（tasks.md）。
- `[P]` の印は、別ファイルで、未完了のタスクに依存しないときだけ付ける（tasks.md）。
- 実装では、依存のあるタスクは順に、`[P]` のタスクは一緒に動かす。並列でないタスクが失敗したら止める。並列のタスクは成功したものを続け、失敗を報告する（implement.md）。
- analyze は仕様・計画・タスクの間の食い違いを読むだけで、ファイルは書き換えない。直す案は出せるが、実際に直すには人の明示的な承認が要る（analyze.md）。
- converge は、仕様・計画・タスクと実装のずれ（未実装、一部だけ、矛盾、頼んでいない追加）を調べ、残りを新しいタスクとして足す。ずれが無ければ「収束」と報告する（converge.md）。
- 設計の文書では、AI が仕様の曖昧さ・矛盾・抜けを調べ、質問するとしている（https://github.com/github/spec-kit/blob/main/spec-driven.md ）。

### OpenAI Codex（ExecPlan）

- 長い作業向けの計画書 ExecPlan の書き方を公開している。実行中は人に「次はどうするか」を聞かずに次のマイルストーンへ進み、曖昧さは自分で解消し、その判断を Decision Log に残す（https://github.com/openai/openai-cookbook/blob/main/articles/codex_exec_plans.md ）。
- 各マイルストーンは単独で確かめられ、全体の目標を少しずつ実現するものにする。確かめ方は、人が確認できる振る舞い（入力と出力）で書く（同）。
- 実現できるかわからない部分は、先に試作のマイルストーンで確かめてよい（同）。

### Devin（Cognition）

- 大きい作業を分けて、並列に動く複数の Devin に渡せる。まとめ役は範囲を決めて割り当て、進み具合を見て、衝突を解消し、結果をまとめる。子の Devin は報告前に自分の変更を確かめられる（https://cognition.com/blog/devin-can-now-manage-devins 、2026-03-19）。
- まとめ役は子の計算資源の使用量を見て、外れた子を止められる（同）。分け方を人が承認する手順と、予算の上限は書いていない。

### GitHub Copilot coding agent

- 明確で範囲の絞られたタスクを渡すと結果が良い、としている。範囲が広く、リポジトリをまたぐ知識が要るリファクタリングや、要件が曖昧なタスクは人がやるほうがよいとしている。PR は人のものと同じ流れでレビューする（https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results ）。このページは小さく明確な依頼を勧めているだけで、大きい依頼を自動で分ける機能があるかは書いていない。

### 論文

- Parsel は、問題を階層的な関数の説明に分け、テストを使って実装の組み合わせを探す（https://arxiv.org/abs/2212.10561 ）。
- RPG / ZeroRepo は、自然言語の計画は不明確になりやすいとして、機能・ファイル構成・データの流れ・関数をグラフで表してから生成し、テストで確かめる（https://arxiv.org/abs/2509.16198 ）。
- CodeTeam は、複数の設計案から 1 つを選び、ファイルの持ち主・公開インタフェース・依存の制約を機械で検査できる約束に直す。そのうえで依存を考えた順番で実装させ、QA 役がテストを回して直させる（https://arxiv.org/abs/2606.22082 ）。
- SWE-RPG は既存リポジトリへの依頼を対象にし、失敗のいちばん大きな原因は書かれていない要件を読み取れないことで、24.5%〜46.0% の実行に当たるとしている（https://arxiv.org/abs/2608.09072 ）。

## 工場への示唆

grand-design.md と比べて足りないところを、案として挙げる。決定ではない。

1. **依頼が大きすぎるときの扱いが決まっていない。** 全体設計は輪の 1 周を 1 件の変更とし（1 章）、上限に達したら失敗で終え、自動で入れ直さない（3 章・4 章）。依頼を分ける手順は無いので、大きい依頼は上限の内に終わらないおそれがある。案 (a): 入口で下書き役が依頼を複数の変更（仕様とシナリオの組）に分け、分け方ごと 1 回で承認してもらう。Missions と AI-DLC は、実装を始める前に分け方を決めて人が承認している。承認は分けた組の列に対して 1 回にとどめる。3 章の「承認を細かく分けると人へ戻る経路が復活する」と両立させるためである。案 (b): 分けずに入口で突き返し、人に小さく出し直してもらう。Copilot の勧め方に近い。Factory が 500 機能を超えたら分けるよう勧めているように、どの大きさから分けるかの目安が要る。

2. **分けたときの全体の確かめ方が決まっていない。** 隠しシナリオは変更ごとにある。分けた変更を全部合わせて通しで動くかを確かめる手順は、全体設計に無い。案: 分けた依頼には、全体を通す隠しシナリオを別に持ち、最後の変更の判定で一緒に走らせる。AI-DLC の walking skeleton のように、最初の変更を端から端まで通る最小の骨格にする手もある。Factory はマイルストーンごとに統合を確かめている。

3. **仕様の中の矛盾を探す手順が決まっていない。** 食い違い一覧（2 章）は、仕様とシナリオの食い違いを見る。仕様の中の要件どうしが同時に満たせないケースを探す専用の手順は無い。Kiro は要件の集合全体で矛盾を探す。案: 独立した分類と同じく別セッションで、仕様の中の矛盾を探し、入口の要約に載せる。

4. **仮定の数に上限が無い。** 3 章は、わからないことを仮定として書き、人が仮定ごと承認するとしている。仮定が増えると読まずに通すおそれも挙げている。spec-kit は仕様を書く段で確認の印を 3 個に絞り、残りは通例で埋めて仮定として書く（仮定の数そのものには上限を置いていない）。案（spec-kit には無い、ここでの提案）: 仮定の数に上限を置き、超えたら入口で「この依頼は曖昧すぎる」と返す。SWE-RPG の結果からは、書かれていない要件の読み落としが一番の失敗原因になりうる。

5. **依頼ごとの事前の見積もりが決まっていない。** 4 章は費用上限を「1 変更あたり」と「全体」の 2 段で持ち、4 役すべてを計上する。どちらも走ってから効く。Factory は「機能数 + 2 × マイルストーン数」で実行回数を事前に見積もり、それを下限として扱っている。案: 下書き役が入口で見積もりを出し、1 変更の上限を超えそうなら分けるか突き返す。分けた場合は、既存の 2 段に加えて、分けた元の依頼ごとの上限を足す。

6. **分けた変更の 1 つが失敗したときの扱いが決まっていない。** spec-kit は、並列でないタスクが失敗したら止め、並列のタスクは成功したものを続ける。Attractor は、必ず成功すべき工程が失敗したまま終わろうとすると、やり直し先へ戻るか、失敗で終わる。案: 失敗した変更に依存する変更は始めずに失敗で終える。依存しない変更は続ける。どこまで出荷したかは記録に残す。3 章の「失敗した変更は自動で入れ直さない」はそのまま使える。

7. **試作では直列でよい。** Factory は直列を基本にしたほうがうまくいったと書いている。Kiro・spec-kit・AI-DLC は、互いに依存しない作業だけを並列にする。案: 試作は直列で回す。並列にするなら、入口で依存関係を明記し、互いに依存しない変更だけを並列にする。

8. **実行中に計画を変えない。** Missions では、人と話して orchestrator が途中で計画を組み直す。工場では、承認した組は書き換えない（3 章）。分け方も承認の対象にするなら、作る役や判定役が途中で分け方を変えることは認めない。変えたいときは失敗で終え、人が出し直す。
