# 手元の開発スタックと L5 の距離（2026-10-17）

## まず結論

遠い。

- 一番の壁は部品の不足ではない。「人が確かめる」前提で決めた規則が、決定記録にたくさん残っていること。部品を足しても、その規則を置き換えない限り L5 にはならない。
- 流れの部品（自動での仕事の投入、並列実行、関門の自動承認、テストが通ればマージ、費用の上限）はかなり揃っている。ただし全部「人が承認した範囲の中で任される」作りになっている。
- 無いものは 3 つ。
  - 隠したシナリオでの検証。作る側のエージェントに見せない筋書きで、出来を判定する仕組み。
  - 外部サービスの双子。外のサービスを模した偽物を立て、その上で試す仕組み。
  - 出荷と、本番からの還流。今の終点は PR とマージで、本番の様子を読んで次の仕事にする経路が無い。

## 用語

- L5（Dark Factory）: 仕様を入れると動くソフトウェアが出てきて、人はコードを書かずレビューもしない状態（https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/ ）。
- rondo / continuo / cadenza: 手元の開発スタックを構成する 3 つのリポジトリ。rondo は人が話しかける常駐の本体で、1 行の依頼を実行に変え、関門ごとに人へ可否を戻す（rondo:README.md:3）。continuo はエージェント組織の実行基盤（rondo:README.md:3, continuo:README.md:3-4）。cadenza は委任の取り決めと関門の意味を持つ層（rondo:README.md:3, cadenza:README.md:3）。
- lap: 依頼 1 件に対してエージェントを 1 回走らせる単位。
- goal / goal scope: オーナーが書く目標と、その中で自動で進めてよい範囲。
- holdout（隠しシナリオ）: 作る側に見せず、判定にだけ使う確認用の筋書き。
- twin: 外部サービスを模した偽物。
- widening: 任された範囲を広げること。
- D-0173 などの番号: 各リポジトリの決定記録の番号。r3.4 などは同じ決定の中の項番号。supersede は、新しい決定で古い決定を置き換えること。
- 出典の `path:line` は、断りが無ければ rondo のもの。

### 距離の要約
1. 最も遠い 1: holdout 検証と満足度判定。3 repo とも隠しシナリオが 0 件。合否はワーカー自身のテスト、形だけを見る reading、別系統モデルの review、CI green で決めている（rondo:src/access/gate-auto.ts:106-156, review.ts:22-29）。どれもエージェントに見える材料。
2. 最も遠い 2: 出荷と本番からの還流。終点は PR と merge（rondo:D-0173 K1）。release・公開・外部送信は「その都度人が承認する」閉リストに入っている（rondo:D-0064 L13016-13024）。deploy の鍵も無い（cadenza:D-0037 §3）。本番シグナルを読む経路は 0 件。
3. 最も遠い 3: 人へ戻る経路。rondo だけで 19 系統（集計は page-logic/waits.ts:89-106,183-221）。起点の approver 指名・goal 記述・goal scope 承認に加え、ワーカーの質問は「沈黙では答えない」（D-0098 r4 / question.ts:1-21）。continuo は plan/risk 承認を人に固定し（D-1121 決定5）、lap の終わりは常に人向けゲート（D-0056 決定2, report_ingress.ts:35-39）。
4. 並列・自動投入・ゲート自動承認・merge on green・lap 費用上限は rondo にほぼ揃っている。ただし全部「人が承認した goal scope の委任」として組まれている（gate-auto.ts:110 no_scope, gate-host.ts:221-237）。
5. 部品の不足より決定記録の層が効く。D-0173 と D-0064 の 2 本線を supersede しないと、部品を足しても L5 にならない。
