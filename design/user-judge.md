# ユーザー役の判定（factory#30）の設計

工場の判定に、2 つ目のやり方を足す設計である。エージェントがユーザー役になって、できたアプリを実際に使い、依頼の仕事をこなせているかを判定する（満足度に近い判定）。今の判定（隠しシナリオを決定的テストとして走らせ、LLM の判定を 1 回付ける）の横に、**別の腕として**置く。この段階では何も決めない。build の合否は今の判定だけで決まり、ユーザー役の判定は記録と比較にだけ使う。

背景は [grand-design.md](grand-design.md) の「決定 1」（2026-10-17）にある。試作では、安くてぶれの小さい決定的テスト + LLM 判定 1 回を採った。そのとき、L5 の本来の姿に近いのはユーザー役の判定だと書き、決定は試作についてのものだとした。2026-10-19 にオーナーが「作る側が落ち着いたら、AI が使って判定するやり方を回す」と言った。始める条件（9〜11 周目の報告が出ていて、作る役とシナリオの走らせ方への変更が進行中でない）は満たしていると、2026-10-25 に窓口が判断した（オーナーから任された判断）。

この文書は設計と仕組みだけを扱う。モデルを呼ぶ実走はしていない。実走はお金がかかるので、後でオーナーの承認を得てから行う。

## 言葉

- **ユーザー役**: できたアプリを使う側のモデルのセッション。工場の役の名前は `user-agent`。
- **今の判定**: 隠しシナリオ（決定的テスト）と、LLM の判定役（`judge`）1 回。`run` では両方、`replicate` ではシナリオだけ。
- **セッション**: ユーザー役が 1 つの build を 1 回使って、判定を 1 つ出すまで。
- **手番**: セッションの中のモデル呼び出し 1 回。ユーザー役は 1 手番で操作をいくつか送るか、判定を出す。

## 全体の形

- 工場のコマンド `user-judge <id> --request <file>` を足した。`run` か `replicate` が終わった後に、**記録に残っている build** を相手に走る。build のやり直しも出荷もしない。`run.json` も replicate の記録も読むだけで、書き換えない。だから、今の判定の合否には触れない。
- 相手にする build は、`run` の各 attempt（`$STATE/work/<id>` の各 attempt の commit）と、replicate の各 build（`$STATE/work/<id>-rep/<model>-<n>`）。
- 1 build につき `--sessions N` 回（0〜5、既定 1）、別々のセッションを流す。記録は `$STATE/runs/<id>/user/<build>--<ユーザー役のモデル>--s<k>.json`。モデルが名前に入るので、`--model user-agent=...` で替えたセッションは別の記録・比較表の別の節になり、モデルの違うセッションがぶれとして混ざらない。
- セッションは、お金を使う前に記録のファイルを排他的に作って（`wx`）押さえる。押さえたセッションは二度と流さない。同じコマンドを打ち直すと、押さえていない組だけが走る。途中で止まった（STOP・上限・プロセスの死）セッションは `stopped` か `running` のまま残り、比較表には「stopped」「interrupted」と出る。流し直したいときは、別の `--sessions` の番号で足す。
- 支出は呼び出しごとに `runs/<id>/user-judge-cost.json` へ書く。プロセスが途中で死んでも、それまでの支出は次のコマンドの上限に数えられる（lap 台帳は今までどおり、呼び出しの前に予算を押さえる）。
- 最後に、今の判定とユーザー役の判定を build ごとに並べた比較表 `$STATE/runs/<id>/user/compare.md` を書き、表示する。セッションが 0 本でも表は作り直す（モデルは呼ばない）。
- lap の定義の `factory` 段としても書ける（`user-judge` を段の一覧に足した）。

## ユーザー役が見るもの・見てはいけないもの

見るもの:

- **依頼の文面**（`--request` のファイル）。承認された組の `base.json` の `requestSha256` と一致しないと始めない。ユーザー役は「この依頼を出した人」として、依頼に照らして判定する。
- **インターフェース**（承認された仕様の末尾の、エンドポイント・パラメータ・フィールドの名前と形だけ）。作る役も仕様の中で同じものを見ている。名前が無いと、API のアプリをユーザーが操作できない。
- アプリに外部サービスの偽物があるか（`draft --service`）、画面があるか（`draft --ui`）の 2 つの印。どちらも承認された仕様にある印から読む。
- 自分が送った操作と、それにアプリ（と偽物）が返したもの。

見てはいけないもの（作る役と同じ線）:

- **隠しシナリオ**、その要約・id、分類のラベル、シナリオの下書き役の仮定、少数派の選び方、事前登録・プローブ。
- **今の判定の結果**（シナリオの合否、LLM 判定の理由、作る役へのフィードバック）。2 つの腕を互いに独立に保つため。
- **仕様の本文**（インターフェース以外）と **Undecided の節**。ユーザー役は依頼に照らして判定する。仕様に照らすのは今の判定役の仕事で、同じものを二度測らないため（オーナーに決めてほしいこと 1）。
- アプリのコード。ユーザーはコードを読まない。
- 保管庫・run の記録・台帳。

どう守るか:

- ユーザー役のセッションは `access: 'none'`（道具なし）で、作業ディレクトリは空の一時ディレクトリである。保管庫は今までどおり、どのサンドボックスからも見えない。
- ユーザー役への指示は、依頼・インターフェース・2 つの印・自分の手番の記録だけから組み立てる（`src/user.ts` の `userInstruction`）。シナリオや判定の結果を受け取る引数そのものが無い。テストで、指示にシナリオの id・要約・仕様の本文が入らないことを確かめている。
- ユーザー役の判定は作る役に返らない。走るのは build が終わった後で、どの経路でもフィードバックにならない。

## アプリの動かし方

今の隔離と偽物をそのまま使う。

- build の commit を、判定役や出荷と同じやり方で書き出し（`exportTree`）、そこからアプリを起動する。アプリは今までどおりサンドボックスの中で動く（自分のデータディレクトリ、自分のポート、ループバックだけ）。
- **1 セッション = 1 つのアプリ**。シナリオは 1 本ごとに空のアプリを起動するが、ユーザー役のセッションの中ではアプリを止めない。ユーザーが使い続けるのと同じく、データは操作の間で残る。セッションごとには空から始まる。
- 外部サービスのあるアプリには、セッションごとに新しい偽物を付ける（`startFake`）。ユーザー役は、シナリオの「応答の設定段」「要求の確認段」と同じ 2 つの形で偽物を操る。偽物は依頼が説明するサービスの代わりで、ユーザー役は依頼にある API の範囲で答えを決める。
- 画面のあるアプリには、セッションの最初の画面の操作で、シナリオと同じ隔離のヘッドレスブラウザを開く（`openBrowser`）。操作は goto / fill / click の 3 つで、見えるのはシナリオと同じ形の `{"<testId>": [見えている文字]}` である。
- ユーザー役のモデルはネットワークにも、アプリにも、ブラウザにも触れない。操作は JSON で返事に書き、工場がそれを実行して、結果を次の手番の指示に載せる。今の隔離の外に、新しい通り道は作らない。

1 手番の流れ:

1. 工場が、依頼・インターフェース・操作の書き方・これまでの手番を指示に書き、ユーザー役を 1 回呼ぶ。
2. ユーザー役は `{"actions": [...]}`（1 手番 8 個まで）か `{"verdict": {...}}` を返す。
3. 操作なら、工場がアプリ（か偽物か画面）に順に送り、結果を記録する。HTTP は状態・応答ヘッダー・本文（JSON でなくても生の文字のまま。ETag や Location をヘッダーから読んで次の操作に使えるように）、偽物は状態と本文、画面は goto の状態と画面の中身である。形の悪い操作は送らず、その理由を結果として返す。
   - 指示に載せるときは、1 つの操作を 500 字、1 つの結果（ヘッダーと画面を含む全体）を 1,500 字で切り、切ったことを書く。記録のファイルには切らずに残す（本文は工場の読み取りの上限 1,000,000 字、画面はブラウザの上限 64,000 字まで）。
4. 手番は 6 回まで。最後の手番では判定を出すよう指示する。判定が出なければ、そのセッションは「判定なし」になる。返事が JSON として読めないとき、アプリが起動しなかったときも「判定なし」で、理由を記録に残す。

## 判定の形

```json
{"satisfied": true, "reason": "<1 段落>", "problems": ["<1 行ずつ: 依頼どおりにならなかったこと>"]}
```

- `satisfied` は真偽値 1 つ。今の判定の合否（`run` は attempt の `pass`、`replicate` は全シナリオの通過）とそのまま並べて比べられる。
- `problems` は、ユーザー役が依頼どおりでないと見たことの一覧。比べたときに、どこで食い違ったかを読むために使う。
- 依頼が決めていないことは、筋の通ったふるまいなら何でもよい、と指示に書く（今の判定役の「Undecided は作る役に任せた」と同じ考え方）。

## 今の判定との比べ方

`compare.md` は build ごとに 1 行で、次を並べる。

| build | シナリオの通過 | 全通過 | LLM 判定 | 今の判定 | ユーザー役（セッションごと） | 一致 |
|---|---|---|---|---|---|---|

- 「今の判定」は `run` なら attempt の `pass`（全通過 AND LLM 判定）、`replicate` なら**その変更自身のシナリオ**（`results[<id>]`）の全通過（replicate には LLM 判定が無い）。`--score` で付けた他の組（11 周目の `-cx-p` など）の通過数は同じ行に括弧で並べるが、今の判定には入れない。
- 「一致」は、判定が出たセッションのすべてが今の判定と同じなら yes、どれかが違えば no、判定が 1 つも無ければ `-`。
- 表の下に数を出す: 両方合格、両方不合格、ユーザー役だけ不合格、今の判定だけ不合格、判定なし。同じ build で 2 セッション以上あり、セッションどうしの判定が割れた build の数も出す（ユーザー役のぶれ）。
- 食い違った build については、ユーザー役の `problems` と、落ちたシナリオの id を並べる。この表は隠しの run ディレクトリに置き、オーナーと実験者が読む。作る役には渡らない。

この表は「どちらが正しいか」を決めない。食い違いを人が読み、ユーザー役が見つけたのが本物の不具合か、ユーザー役の読み違いかを分けるのは、比べた後の仕事である。

## 費用

### 1 回あたりの見込み

- ユーザー役の 1 回の呼び出しは、道具なしの 1 手番である。同じく道具なしの分類役は、11 周目の `fx-invoice-xx-1` で 1 下書き分（シナリオ 8〜15 本、1 本 1 回）が $0.99 だった。1 回あたり約 $0.07〜$0.12。
- ユーザー役の指示は、手番が進むほど長くなる（これまでの操作と結果を毎回載せる）。載せる量は機械で切るので、最後の手番でも 5 手番 × 8 操作 × (500 + 1,500) 字 = 80,000 字に依頼とインターフェースを足した量を超えない。1 回 $0.05〜$0.40 と見込む（推測。分類役の実績に、指示の長さの比で上げた）。
- 1 セッション（6 手番まで）: 約 $0.3〜$2.4。上限（下）で 1 セッション $3 を超えない。
- 比べると、10・11 周目の作る役は 1 build $0.33〜$0.48 だった。ユーザー役の判定は、1 セッションで build の 1〜4 倍の費用になる見込みである。
- 2026-10-17 の見立て（l5-gap-audit (b)）は、隠しシナリオ 20 本 × 3 回をそれぞれユーザー役で走らせる形で、1 変更 $30〜120 だった。この設計は 1 build に 1 セッション（シナリオの本数によらない）なので、ずっと安い。代わりに、1 セッションで調べられる範囲は 6 手番 × 8 操作に限られる。

### 1 変更あたり

| 形 | セッション | 見込み |
|---|---|---|
| `run`（attempt 1〜2） × 1 セッション | 1〜2 | 約 $0.3〜$4.8 |
| `replicate --k 4` × 1 セッション | 4 | 約 $1.2〜$9.6 |
| `replicate --k 4` × 2 セッション | 8 | 約 $2.4〜$19.2（上限 $15 で止まる） |

### 上限

- 1 回の呼び出し: $0.5（`CAPS.userCallUsd`）。時間は 5 分。
- 1 セッション: 6 手番（`USER_LIMITS.turns`）。よって 1 セッション最大 $3。
- 1 変更: `--max-cost`（既定 $10、`run` と同じ既定）。`user-judge` を何度打っても、その変更のユーザー役の支出（`runs/<id>/user-judge-cost.json`）を足して数える。下書きと build の支出とは別に数える。今の判定の上限を食わないためである。
- lap あたりの上限（$260）と lap 台帳は今までどおり効く。ユーザー役の呼び出しも台帳に役 `user-agent` で載る。
- 非常停止（STOP ファイル）も今までどおり効く。

- 4 依頼とも外部サービスの偽物を使うので、偽物を操るユーザー役の書き方も確かめられる。
- 1 build 2 セッション（ぶれを見る）で 32 セッション、約 $10〜$77。上限案は $60（4 依頼 × `--max-cost 15`）。悪い場合は上限で止まり、止まった依頼の残りの build は判定されない（比較表に出ない）。
- 前提: `.factory-lap11` の `work/<id>-rep/` が消されずに残っていること。残っていなければ、次の周の build に付ける。

## 何が言えないか（あらかじめ）

- ユーザー役は 6 手番 × 8 操作しか使わない。依頼の全部を試すとは限らず、「満足」は「試した範囲で依頼どおりだった」の意味である。
- ユーザー役は依頼の書き手そのものではない。依頼の読み方は、作る役・シナリオの下書き役と同じ系統（Claude）のモデルの読み方である。
- アプリの返事は作る役が書いたコードが出すもので、それがそのままユーザー役の指示に載る。返事の中の文がユーザー役の判定を曲げることはありうる（ユーザー役には道具が無いので、判定以外には何もできない）。作る役はユーザー役の存在を知らないが、狙って書かれたら防げない。比べる段階では記録して読むだけで、これが判定を決める前に考え直す。
- 偽物は、セッションの最初の操作より前にアプリが起動する。起動のときに外部サービスを呼ぶアプリは、その呼び出しに答えが設定されていない（404）。シナリオでは先頭の設定段が起動前に走るので、ここはシナリオと違う。
- 画面の操作の後、ユーザー役は 0.5 秒待ってからの画面を見る。シナリオのように、期待が満たされるまで 5 秒読み直すことはしない（ユーザー役には期待が無い）。遅く書き換わる画面は、古い中身に見えうる。
- 1 build 1〜2 セッションでは、ぶれの大きさは粗くしか分からない。
- 1 変更のユーザー役の支出は、呼び出しが終わるたびに書く。呼び出しの最中にプロセスが死ぬと、その呼び出しの支出はこの腕の上限（`--max-cost`）に数えられない（lap 台帳は呼び出しの前に予算を押さえるので、lap の上限には数えられる）。replicate の費用の記録と同じ限界である。
- 同じ変更の `user-judge` は同時に 1 つだけ走る（`runs/<id>/user/.lock`）。プロセスが死んで残ったロックは、人が消す。
- 偽物の上限（要求 100 件など）を超えたアプリは、偽物が通信を切る。その後の結果には、切ったことを書いてユーザー役に見せる。シナリオのように不合格にはしない。
- 記録の名前はモデルで分けるが、手番の上限や指示の文面を変えたことは名前に入らない（記録の `limits` には残る）。工場のコードを変えた後に続きを流すと、違う設定のセッションが同じ節に混ざる。比べる最中は工場を変えない。

## 実装（工場、factory#30）

- `src/user.ts`: ユーザー役の腕。指示の組み立て（`userInstruction`）、操作の形の確かめ（`checkAction`）、1 セッション（`userSession`）、コマンドの本体（`userJudge`）、比較表（`compareTable`）。
- `src/scenario.ts`: 1 つのアプリ（と偽物・画面）を止めずに操作を 1 つずつ送る `withSession` を足した。中身はシナリオの走らせ方（`withApp`、`send`、`startFake`、`openBrowser`）を使い回す。
- `src/adapter.ts`: 役 `user-agent` を足した（claude-opus-5-5）。作る役の書いたものを読む役なので、2 つ目の系統（Codex）は使えない。
- `src/limits.ts`: `CAPS.userCallUsd = 0.5` を足した。
- `src/cli.ts`: コマンド `user-judge`。`--model user-agent=<model>` も受ける。
- `src/lap.ts`: lap の段の一覧に `user-judge` を足した。
- テストは偽のモデルだけを使う（お金を使わない）。アプリを起動するテストは、ワーカーのサンドボックスでは入れ子の bwrap が使えないので落ちる（main でも同じ）。窓口がサンドボックスの外で `npm test` を回す。

## オーナーに決めてほしいこと

1. **ユーザー役が見るもの**: 依頼の文面 + インターフェース（名前だけ）。仕様の本文は見せない。
   - **おすすめ: このとおり。** 依頼に照らす判定は、仕様に照らす今の判定と別のものを測る。仕様を見せると、今の判定役と同じものを二度測ることになりやすい。代わりに「依頼の文面だけ」にすると、API のアプリではエンドポイントの名前が分からず、操作できない。
2. **判定の形**: `satisfied`（真偽値）+ 理由 + 問題の一覧。
   - **おすすめ: このとおり。** 今の判定の合否とそのまま比べられる。点数（1〜5 など）は、ぶれの読みが難しくなるので、比べた後に要ると分かってから足す。
3. **手番と操作の上限**: 1 セッション 6 手番、1 手番 8 操作、結果は 1 つ 1,500 字まで。1 回の呼び出し $0.5。

# 追記: ユーザー役の判定を合否に使う条件（factory#50、2026-10-26）

factory#50 の問い「ユーザー役の判定を、どんな条件なら合否に入れてよいか」への設計である。最初の実走の読み解きは [laps/lap-11/user-judge-first-run.md](../laps/lap-11/user-judge-first-run.md) にある。要点は 2 つ。32 セッションすべてが満足で、ユーザー役が「不満」と言う場面が一度も無かった。notify-queue の食い違い（`PUT /users/{id}` に `muted` の無い body を送ると 200）には、どのセッションも届かなかった。だから、このデータからは「ユーザー役が甘い」のか「試しが浅い」のかを分けられない。

この追記では、この 2 つを分けて測る仕組みを工場に足し、合否への使い方の方針を決める。モデルは一度も呼んでいない。lap も始めていない。実走は窓口がオーナーの承認を得てから打つ（下の「実走の案」）。

## 結論

- **合否には入れない（advisory only）。** ユーザー役の判定は、これからも記録と比較にだけ使う。理由は「合否に入れない理由」の節に書く。
- **甘さは、わざと欠陥を入れた build で測る。** 既知の build に欠陥を 1 つだけ入れた「対照」（以下、変異 build）を作り、ユーザー役がそれに「不満」と言えるかを数える。欠陥は人が書く。モデルには書かせない。
- **浅さには、セッションごとに試す重点を変えて手当てする。** 同じ build の k 番目のセッションに、主筋・入力の形・状態の移り変わり・失敗のときの 4 つの重点を順に割り当てる。
- **ユーザー役が見つけた不具合を合否に効かせたいときは、シナリオに書き起こす。** 判定そのものを合否に入れるのではなく、人が読んで本物と認めた食い違いを決定的なシナリオにして、今の判定に足す。

## 甘さの測り方: 欠陥を 1 つ入れた対照

### 形

工場のコマンドに `--mutants <file>` を足した。ファイルは変異の一覧である。

```json
[{"id": "ship-no-reserve", "build": "claude-opus-5-5-1", "file": "server.js",
  "find": "for (const it of o.items) products.get(it.sku).reserved += it.qty;", "replace": "void 0;",
  "defect": "a booked order does not reserve its quantities: ..."}]
```

- 1 つの変異は、記録に残っている 1 つの build の 1 つのファイルの、ちょうど 1 か所の書き換えである。`find` がそのファイルにちょうど 1 回現れないと、モデルを呼ぶ前に止まる。
- `defect` は依頼に照らして何が間違っているかの説明で、比較表を読む人のためにある。ユーザー役には渡らない。
- ファイルは状態ディレクトリの `vault/` の下に置く（`--probes` と同じ）。どのサンドボックスからも見えない場所である。

### 流れ

1. **採点（モデルを呼ばない）。** 変異ごとに、元の build を書き出し（`exportTree`）、書き換えを当て、その変更自身の隠しシナリオを走らせる。結果は `runs/<id>/user/mutants/<変異 id>.json` に残る。これで「今の判定がこの欠陥を見るか」が分かる。採点はどの呼び出しよりも先に全部済ませるので、書き換えが当たらない変異があれば、お金を使う前に止まる。`--sessions 0` で打てば、採点だけをただで済ませられる。
2. **セッション。** 変異 build にも、普通の build と同じセッションを流す。ユーザー役から見ると、普通の build と区別がつかない（指示の文面に変異のことは何も入らない）。記録は `<build>~<変異 id>--<モデル>--<重点>-s<k>.json` で、記録の中に `mutant` と `focus` を持つ。
3. **比較表。** `compare.md` の先頭に、採点した変異とシナリオの結果の表を出す（セッションが無くても出る）。モデルごとの節には「Seeded defects」の表を足した。

| mutant | build | defect | scenarios on the mutant | user | caught |
|---|---|---|---|---|---|

- `caught` は、判定を出したセッションのうち「不満」と言った数である（例: `1/2`）。
- 表の下に、変異の数、1 セッションでも捕まえた変異の数、判定のあるセッション数と「不満」の数、重点ごとの捕まえた割合（例: `main 0/1, input 1/1`）を出す。
- 変異 build の各セッションの理由と problems を並べる。「不満」が入れた欠陥を指しているか（元の build にもある別のことを指していないか）は、人が読んで確かめる。同じ build の変異していないセッションが、同じ節の上の表にある。
- 書き換えたファイルを後から変えて同じ id で打ち直すと、別の欠陥が同じ行に混ざる。それを防ぐため、採点済みの変異と中身が違えば止まる（新しい id を付ける）。

### 何を測るか

- **見逃し（甘さ・浅さ）**: 今の判定が落とす変異 build に、ユーザー役が「満足」と言った割合。
- **重点の効き目**: 同じ変異に対する、重点ごとの捕まえた割合。入力の形の欠陥を、入力の形に重点を置いたセッションだけが捕まえるなら、浅さは重点で手当てできていると読める。どの重点でも捕まえないなら、甘さか、指示（「依頼が決めていないことは何でもよい」）の読み方の問題である。
- **誤報（厳しすぎ）**: 今の判定が通す普通の build に、ユーザー役が「不満」と言った割合。これは今までの表（「user only fails」）で見る。

甘さと浅さは、次のように分けて読む。セッションの記録（操作と結果）に、入れた欠陥を踏んだ操作があるのに「満足」なら甘い。踏んだ操作が無いなら浅い。この区別は今は人が記録を読んで付ける。機械で付けるには、欠陥ごとに「踏んだ」の判定を書く必要があり、変異の数が少ないうちは割に合わない。

## 浅さの手当て: セッションごとの重点

同じ build の k 番目のセッションは、次の重点を順に使う（5 番目は 1 番目に戻る）。指示に「FOCUS OF THIS TRY」の 1 段落として入る。

| k | 重点 | 指示の中身（要約） |
|---|---|---|
| 1 | main | 依頼の主な仕事を、頼んだ人が毎日使うように端から端まで |
| 2 | input | 入力のある所すべてで、欠けた・余計な・型の違う・範囲外の値、壊れた body を送り、依頼どおりに受け付けるか断るかを見る |
| 3 | state | 順番を変える、繰り返す、変えた後や消した後のものに触る、各段の後に読み返して、残っているものが自分のしたことと合うかを見る |
| 4 | failure | 依頼が決めている「うまくいかないとき」: 外部サービスの失敗やおかしな返事、上限、衝突、無いもの |

- 指示には「重点に操作の大半を使う。ただし重点に要る分は依頼の他の部分も使ってよい。判定は、試した範囲での依頼全体についてである」と書く。重点は試し方を変えるだけで、判定の基準は変えない。
- 重点は記録と記録の名前に入る。重点の付いていない記録（最初の実走の 32 セッション）は、比較表で別の節（`<モデル>, no focus (before #50)`）になり、新しい記録と混ざらない。
- notify-queue の食い違いは、2 番目のセッション（input）の重点がちょうど当たる所である。
- ターン数を増やすより安い。1 セッションの上限（6 手番 × 8 操作）は変えていない。

## 合否に入れない理由

1. **まだ測れていない。** 32 セッション中、「不満」は 0 回だった。ユーザー役が欠陥を捕まえる割合は、一度も測っていない。測っていない判定を合否に入れると、その合否の意味が誰にも分からない。
2. **合否に入れると、片側にしか効かない。** 今の判定に「ユーザー役も満足」を AND で足すと、不合格を増やす向きにしか働かない。増える不合格の中には、ユーザー役の読み違い（依頼が開いている点を「違う」と読むなど）が混ざる。逆に、ユーザー役の満足で今の判定の不合格を覆す（OR）と、試しの浅さがそのまま合格になる。最初の実走の notify-queue がちょうどこれで、8 セッションとも満足だった。
3. **ぶれと費用。** ユーザー役は同じ build でもセッションごとに試す所が違う（重点を入れたので、なおさら違う）。合否に使うなら、1 つの build に何セッション流せば判定が安定するかを先に知る必要がある。1 セッションは build 1 つの 1〜4 倍の費用なので、セッションを増やすと作る費用より判定の費用の方が大きくなる。
4. **独立性が崩れる。** ユーザー役が合否を決めると、落ちた build をやり直す作る役に、その理由を返したくなる。返すと、ユーザー役の判定は作る役から独立でなくなる（作る役がユーザー役に合わせて作り始める）。返さないと、作る役は理由の分からないまま落ち続ける。今の判定が隠しシナリオで避けている問題を、もう一度抱えることになる。
5. **アプリの返事が判定に入る。** ユーザー役は、アプリ（作る役の書いたコード）が返した文字を指示の中で読む。合否を決める立場になると、作る役がユーザー役に向けた文をアプリに仕込む動機が生まれる。記録と比較だけなら、その動機は無い。

代わりに、ユーザー役の見つけたものを合否に効かせる道は、シナリオを通す道にする。比較表の「user only fails」で、人が読んで本物の不具合と認めた点は、その依頼のシナリオとして書き起こし、次の周から今の判定で測る。こうすれば、合否は決定的なまま（同じ build なら同じ結果）で、ユーザー役の見つけたものは合否に入る。

### いつ見直すか

次の 3 つがそろったら、advisory only を見直す。数字はまだ置かない。最初の測りの結果を見てから置く（根拠の無い数字を置かないため）。

- 変異 build を、少なくとも 3 つの依頼にわたって十数個以上流し、見逃しの割合が出ていること。
- 普通の build（今の判定が通すもの）での誤報の割合が出ていること。
- 同じ build の 2 セッション以上で、判定がどれくらい割れるかが出ていること。

見直すときも、最初の候補は「合否を決める」ではなく「人の確認を求める印を立てる」（例: ユーザー役が不満と言い、今の判定が通した build は、出荷の承認の前に人が compare.md を読む）である。

## 実走の案（まだ回さない）

### 何を流すか

11 周目の 16 build（状態ディレクトリ `.factory-lap11`）に、重点付きのセッションと変異 build を流す。

- 普通の 16 build に、重点付きで 2 セッションずつ（main と input）。最初の実走の記録は消さず、別の節に残る。notify-queue の 4 build の input セッションが、`PUT` の欠けた body を試すかを見る。
- 変異 build を 7 つ（依頼ごとに、各依頼の build 1 を元にする）。それぞれ 2 セッション（main と input）。変異のファイルは [laps/lap-11/mutants/](../laps/lap-11/mutants/) にある。

| 依頼 | 変異 id | 入れた欠陥（依頼に照らして） | 当たりそうな重点 |
|---|---|---|---|
| fx-invoice | fx-paidyen-last-only | 2 回目の支払いの後、`paidYen` が最後の支払いの円だけになる（`balanceYen` と `fxDiffYen` もずれる） | main |
| fx-invoice | fx-line-amount-unchecked | 明細の `amount` を検査しない（0・負・文字列・上限超えが通る） | input |
| ship-orders | ship-no-reserve | 予約が成立しても在庫の `reserved` が増えない | main |
| ship-orders | ship-duplicate-sku | 同じ sku を 2 回並べた注文が通る | input |
| pay-refunds | pay-refunded-not-summed | 返金が成功しても注文の `refunded` が増えない | main |
| pay-refunds | pay-discount-unchecked | 範囲外の `discount`（負、小計以上）が通る | input |
| notify-queue | notify-mute-ignored | `muted` の話題の出来事が、ミュートされずに通知になる | main |

- 欠陥は、依頼の文に照らして明らかに違うものを選んだ。依頼が開いている点は選んでいない。シナリオは読まずに、依頼文と build のコードだけから書いた（シナリオに合わせた欠陥にならないように）。
- 各変異の `find` が元のファイルにちょうど 1 回現れることは確かめた。シナリオがこの欠陥で落ちるかは、下の手順 1（ただ）で確かめる。落ちない変異は「今の判定も見ない欠陥」として読む（その場合も、ユーザー役が捕まえるかは意味がある）。
- 主筋の欠陥は「ユーザー役が欠陥を見たのに満足と言うか」（甘さ）を、入力の欠陥は「重点で浅さが手当てできるか」を、主に測る。

### 手順（窓口が打つ。lap は始めない）

前提: この変更（factory#50）が main に入っていること。工場の main の checkout で打つ。

### 費用

- セッションの数: 普通の build 16 × 2 = 32、変異 build 7 × 2 = 14、計 46。
- 見込み: 最初の実走の実績は 1 セッション $0.44〜$0.56 だった。重点で手番の使い方が大きく変わらなければ、46 セッションで約 $20〜$26。依頼ごとには、fx-invoice・ship-orders・pay-refunds が 12 セッションで約 $5.3〜$6.7、notify-queue が 10 セッションで約 $4.4〜$5.6。
- 上限: `--max-cost 15` は、その変更のユーザー役の支出の通算に効く。最初の実走で使った分（fx-invoice $4.25、ship-orders $4.02、pay-refunds $4.44、notify-queue $3.61）を引くと、新しく使えるのは依頼ごとに $10.56〜$11.39、4 依頼で最大 $43.68 である。見込みは上限の半分ほどなので、普通は上限に届かない。
- 1 回の呼び出し $0.5、1 セッション 6 手番（最大 $3）の上限は今までどおり。lap 台帳と STOP も今までどおり効く。
- 上限で止まると、残りのセッションは流れない。普通の build が先、変異 build が後に流れるので、止まったときに欠けるのは変異の方である。同じコマンドを（上限を上げて）打ち直せば、押さえていないセッションだけが流れる。

### 読み方

- 変異 7 つのうち主筋の 4 つを、main のセッションが「満足」と言ったら、甘い疑いが強い。記録を読み、欠陥を踏んだ操作があったかを確かめる。
- 入力の 3 つを、input のセッションだけが捕まえたら、重点が浅さの手当てとして効いている。
- notify-queue の普通の 4 build の input セッションが `PUT` の欠けた body を試し、それでも満足と言ったら、「依頼が開いている点は何でもよい」の読み方の問題である（依頼文 8 行の `{"mode", "muted"}` を開いていると読んだ）。
- 普通の 16 build で「不満」が出たら、誤報か、シナリオの見逃した本物の不具合かを読む。本物なら、シナリオに書き起こす候補にする。

## 何が言えないか（あらかじめ）

- 変異は人（このワーカー）が書いた、分かりやすい欠陥である。本物の作る役の落ち方（今回の notify-queue のような、依頼の読み方の違い）とは形が違う。変異を捕まえられることは、合否に使うための必要条件であって、十分条件ではない。
- 変異は各依頼の build 1 つだけを元にしている。build による違いは見ていない。
- 2 セッションでは、重点のうち main と input しか使わない。state と failure の効き目は、この実走では測れない。
- 「捕まえた」は「不満と言った」を数えるだけである。不満の理由が入れた欠陥を指しているかは、人が読む。
- 変異はアプリのコードの書き換えなので、アプリの起動に失敗するような書き換えも作れてしまう。そうなったセッションは「判定なし」になり、捕まえた数にも見逃した数にも入らない。

## 実装（工場、factory#50）

- `src/user.ts`
  - `FOCI` と `focusOf`: 4 つの重点と、セッション番号からの割り当て。`userInstruction` と `userSession` が重点を受け取る。
  - `validateMutants` と `mutate`: 変異の形の確かめと、書き出した build への当て方（`find` はちょうど 1 回。ファイルは build の中の普通のファイルに限り、リンクの先には書かない）。
  - `userJudge`: `mutantsFile` を受け、変異を全部採点してからセッションを流す。記録の名前に重点を入れる。
  - `compareTable`: 重点の無い古い記録を別の節にし、各節に「Seeded defects」の表と数を足した。
- `src/vault.ts`: `hiddenFile`（`vault/` の下のファイルだけを読む）。`--probes` と `--mutants` が使う。
- `src/cli.ts`: `user-judge` に `--mutants` を足した。
- テストは偽のモデルだけを使う。変異の形・当て方・比較表はサンドボックスなしで回る。`user-judge` を変異付きで端から端まで回すテストは、アプリを起動するので、ワーカーのサンドボックスでは入れ子の bwrap が使えず落ちる（main でも同じ）。窓口がサンドボックスの外で `npm test` を回す。

## オーナーに決めてほしいこと（factory#50）

1. **合否への使い方**: advisory only（合否に入れない）。ユーザー役の見つけた本物の不具合は、シナリオに書き起こして今の判定に入れる。
   - **おすすめ: このとおり。** 理由は「合否に入れない理由」の 5 つ。見直す条件（見逃し・誤報・ぶれの 3 つが測れたこと）だけ決めておき、数字は最初の測りの後に置く。
2. **実走の範囲**: 普通の 16 build（重点付き 2 セッション）と変異 7 つ（2 セッション）の計 46 セッション、見込み $20〜$26、上限は通算で依頼ごとに $15（新しい支出は最大 $43.68）。
   - **おすすめ: このとおり。** 変異だけ（14 セッション、約 $6〜$8）にする案もある。ただしそれだと誤報と、notify-queue の食い違いに input の重点が届くかが測れない。
3. **変異のセッション数**: 2（main と input）。
   - **おすすめ: このとおり。** 4 にすると state と failure も測れるが、変異の費用が倍（約 $12〜$16）になる。今回の変異は主筋と入力の 2 種類だけなので、2 で足りる。
4. **重点の組**: main / input / state / failure を順に。
   - **おすすめ: このとおり。** 最初の実走で見えた浅さ（全セッションが同じ手順）に直接効く。重点ごとの効き目は比較表に出るので、効かない重点は後で替えられる。
5. **notify-queue の食い違いの根（仕様の下書き役が、依頼の決めた点を Undecided に入れた）**: この追記では扱わない。
   - **おすすめ: 別の Issue にする。** ユーザー役の問題ではなく、仕様の下書きの問題である。承認の要約の (b) 欄に挙がった点を依頼文と照らす段を足すかどうかを、12 周目の前に決める。
