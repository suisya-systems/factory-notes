# ユーザー役の判定（factory#30）の設計

工場の判定に、2 つ目のやり方を足す設計である。エージェントがユーザー役になって、できたアプリを実際に使い、依頼の仕事をこなせているかを判定する（満足度に近い判定）。今の判定（隠しシナリオを決定的テストとして走らせ、LLM の判定を 1 回付ける）の横に、**別の腕として**置く。この段階では何も決めない。build の合否は今の判定だけで決まり、ユーザー役の判定は記録と比較にだけ使う。

背景は [grand-design.md](grand-design.md) の「決定 1」（2026-10-17）にある。試作では、安くてぶれの小さい決定的テスト + LLM 判定 1 回を採った。そのとき、L5 の本来の姿に近いのはユーザー役の判定だと書き、決定は試作についてのものだとした。2026-10-19 にオーナーが「作る側が落ち着いたら、AI が使って判定するやり方を回す」と言った。始める条件（9〜11 周目の報告が出ていて、作る役とシナリオの走らせ方への変更が進行中でない）は満たしていると、2026-10-25 に窓口が判断した（オーナーから任された判断）。

この文書は設計と仕組みだけを扱う。モデルを呼ぶ実走はしていない。実走はお金がかかるので、後でオーナーの承認を得てから行う。

## 言葉

- **ユーザー役**: できたアプリを使う側のモデルのセッション。工場の役の名前は `user-agent`。
- **今の判定**: 隠しシナリオ（決定的テスト）と、LLM の判定役（`judge`）1 回。`run` では両方、`replicate` ではシナリオだけ。
- **セッション**: ユーザー役が 1 つの build を 1 回使って、判定を 1 つ出すまで。
- **手番**: セッションの中のモデル呼び出し 1 回。ユーザー役は 1 手番で操作をいくつか送るか、判定を出す。

## 全体の形

- 工場のコマンド `user-judge <id> --request <file>` を足した。`run` か `replicate` が終わった後に、**記録に残っている build** を相手に走る。build のやり直しも出荷もしない。`run.json` も replicate の記録も読むだけで、書き換えない。だから、今の判定の合否には触れない。
- 相手にする build は、`run` の各 attempt（`$STATE/work/<id>` の各 attempt の commit）と、replicate の各 build（`$STATE/work/<id>-rep/<model>-<n>`）。
- 1 build につき `--sessions N` 回（0〜5、既定 1）、別々のセッションを流す。記録は `$STATE/runs/<id>/user/<build>--<ユーザー役のモデル>--s<k>.json`。モデルが名前に入るので、`--model user-agent=...` で替えたセッションは別の記録・比較表の別の節になり、モデルの違うセッションがぶれとして混ざらない。
- セッションは、お金を使う前に記録のファイルを排他的に作って（`wx`）押さえる。押さえたセッションは二度と流さない。同じコマンドを打ち直すと、押さえていない組だけが走る。途中で止まった（STOP・上限・プロセスの死）セッションは `stopped` か `running` のまま残り、比較表には「stopped」「interrupted」と出る。流し直したいときは、別の `--sessions` の番号で足す。
- 支出は呼び出しごとに `runs/<id>/user-judge-cost.json` へ書く。プロセスが途中で死んでも、それまでの支出は次のコマンドの上限に数えられる（lap 台帳は今までどおり、呼び出しの前に予算を押さえる）。
- 最後に、今の判定とユーザー役の判定を build ごとに並べた比較表 `$STATE/runs/<id>/user/compare.md` を書き、表示する。セッションが 0 本でも表は作り直す（モデルは呼ばない）。
- lap の定義の `factory` 段としても書ける（`user-judge` を段の一覧に足した）。

## ユーザー役が見るもの・見てはいけないもの

見るもの:

- **依頼の文面**（`--request` のファイル）。承認された組の `base.json` の `requestSha256` と一致しないと始めない。ユーザー役は「この依頼を出した人」として、依頼に照らして判定する。
- **インターフェース**（承認された仕様の末尾の、エンドポイント・パラメータ・フィールドの名前と形だけ）。作る役も仕様の中で同じものを見ている。名前が無いと、API のアプリをユーザーが操作できない。
- アプリに外部サービスの偽物があるか（`draft --service`）、画面があるか（`draft --ui`）の 2 つの印。どちらも承認された仕様にある印から読む。
- 自分が送った操作と、それにアプリ（と偽物）が返したもの。

見てはいけないもの（作る役と同じ線）:

- **隠しシナリオ**、その要約・id、分類のラベル、シナリオの下書き役の仮定、少数派の選び方、事前登録・プローブ。
- **今の判定の結果**（シナリオの合否、LLM 判定の理由、作る役へのフィードバック）。2 つの腕を互いに独立に保つため。
- **仕様の本文**（インターフェース以外）と **Undecided の節**。ユーザー役は依頼に照らして判定する。仕様に照らすのは今の判定役の仕事で、同じものを二度測らないため（オーナーに決めてほしいこと 1）。
- アプリのコード。ユーザーはコードを読まない。
- 保管庫・run の記録・台帳。

どう守るか:

- ユーザー役のセッションは `access: 'none'`（道具なし）で、作業ディレクトリは空の一時ディレクトリである。保管庫は今までどおり、どのサンドボックスからも見えない。
- ユーザー役への指示は、依頼・インターフェース・2 つの印・自分の手番の記録だけから組み立てる（`src/user.ts` の `userInstruction`）。シナリオや判定の結果を受け取る引数そのものが無い。テストで、指示にシナリオの id・要約・仕様の本文が入らないことを確かめている。
- ユーザー役の判定は作る役に返らない。走るのは build が終わった後で、どの経路でもフィードバックにならない。

## アプリの動かし方

今の隔離と偽物をそのまま使う。

- build の commit を、判定役や出荷と同じやり方で書き出し（`exportTree`）、そこからアプリを起動する。アプリは今までどおりサンドボックスの中で動く（自分のデータディレクトリ、自分のポート、ループバックだけ）。
- **1 セッション = 1 つのアプリ**。シナリオは 1 本ごとに空のアプリを起動するが、ユーザー役のセッションの中ではアプリを止めない。ユーザーが使い続けるのと同じく、データは操作の間で残る。セッションごとには空から始まる。
- 外部サービスのあるアプリには、セッションごとに新しい偽物を付ける（`startFake`）。ユーザー役は、シナリオの「応答の設定段」「要求の確認段」と同じ 2 つの形で偽物を操る。偽物は依頼が説明するサービスの代わりで、ユーザー役は依頼にある API の範囲で答えを決める。
- 画面のあるアプリには、セッションの最初の画面の操作で、シナリオと同じ隔離のヘッドレスブラウザを開く（`openBrowser`）。操作は goto / fill / click の 3 つで、見えるのはシナリオと同じ形の `{"<testId>": [見えている文字]}` である。
- ユーザー役のモデルはネットワークにも、アプリにも、ブラウザにも触れない。操作は JSON で返事に書き、工場がそれを実行して、結果を次の手番の指示に載せる。今の隔離の外に、新しい通り道は作らない。

1 手番の流れ:

1. 工場が、依頼・インターフェース・操作の書き方・これまでの手番を指示に書き、ユーザー役を 1 回呼ぶ。
2. ユーザー役は `{"actions": [...]}`（1 手番 8 個まで）か `{"verdict": {...}}` を返す。
3. 操作なら、工場がアプリ（か偽物か画面）に順に送り、結果を記録する。HTTP は状態・応答ヘッダー・本文（JSON でなくても生の文字のまま。ETag や Location をヘッダーから読んで次の操作に使えるように）、偽物は状態と本文、画面は goto の状態と画面の中身である。形の悪い操作は送らず、その理由を結果として返す。
   - 指示に載せるときは、1 つの操作を 500 字、1 つの結果（ヘッダーと画面を含む全体）を 1,500 字で切り、切ったことを書く。記録のファイルには切らずに残す（本文は工場の読み取りの上限 1,000,000 字、画面はブラウザの上限 64,000 字まで）。
4. 手番は 6 回まで。最後の手番では判定を出すよう指示する。判定が出なければ、そのセッションは「判定なし」になる。返事が JSON として読めないとき、アプリが起動しなかったときも「判定なし」で、理由を記録に残す。

## 判定の形

```json
{"satisfied": true, "reason": "<1 段落>", "problems": ["<1 行ずつ: 依頼どおりにならなかったこと>"]}
```

- `satisfied` は真偽値 1 つ。今の判定の合否（`run` は attempt の `pass`、`replicate` は全シナリオの通過）とそのまま並べて比べられる。
- `problems` は、ユーザー役が依頼どおりでないと見たことの一覧。比べたときに、どこで食い違ったかを読むために使う。
- 依頼が決めていないことは、筋の通ったふるまいなら何でもよい、と指示に書く（今の判定役の「Undecided は作る役に任せた」と同じ考え方）。

## 今の判定との比べ方

`compare.md` は build ごとに 1 行で、次を並べる。

| build | シナリオの通過 | 全通過 | LLM 判定 | 今の判定 | ユーザー役（セッションごと） | 一致 |
|---|---|---|---|---|---|---|

- 「今の判定」は `run` なら attempt の `pass`（全通過 AND LLM 判定）、`replicate` なら**その変更自身のシナリオ**（`results[<id>]`）の全通過（replicate には LLM 判定が無い）。`--score` で付けた他の組（11 周目の `-cx-p` など）の通過数は同じ行に括弧で並べるが、今の判定には入れない。
- 「一致」は、判定が出たセッションのすべてが今の判定と同じなら yes、どれかが違えば no、判定が 1 つも無ければ `-`。
- 表の下に数を出す: 両方合格、両方不合格、ユーザー役だけ不合格、今の判定だけ不合格、判定なし。同じ build で 2 セッション以上あり、セッションどうしの判定が割れた build の数も出す（ユーザー役のぶれ）。
- 食い違った build については、ユーザー役の `problems` と、落ちたシナリオの id を並べる。この表は隠しの run ディレクトリに置き、オーナーと実験者が読む。作る役には渡らない。

この表は「どちらが正しいか」を決めない。食い違いを人が読み、ユーザー役が見つけたのが本物の不具合か、ユーザー役の読み違いかを分けるのは、比べた後の仕事である。

## 費用

### 1 回あたりの見込み

- ユーザー役の 1 回の呼び出しは、道具なしの 1 手番である。同じく道具なしの分類役は、11 周目の `fx-invoice-xx-1` で 1 下書き分（シナリオ 8〜15 本、1 本 1 回）が $0.99 だった。1 回あたり約 $0.07〜$0.12。
- ユーザー役の指示は、手番が進むほど長くなる（これまでの操作と結果を毎回載せる）。載せる量は機械で切るので、最後の手番でも 5 手番 × 8 操作 × (500 + 1,500) 字 = 80,000 字に依頼とインターフェースを足した量を超えない。1 回 $0.05〜$0.40 と見込む（推測。分類役の実績に、指示の長さの比で上げた）。
- 1 セッション（6 手番まで）: 約 $0.3〜$2.4。上限（下）で 1 セッション $3 を超えない。
- 比べると、10・11 周目の作る役は 1 build $0.33〜$0.48 だった。ユーザー役の判定は、1 セッションで build の 1〜4 倍の費用になる見込みである。
- 2026-10-17 の見立て（l5-gap-audit (b)）は、隠しシナリオ 20 本 × 3 回をそれぞれユーザー役で走らせる形で、1 変更 $30〜120 だった。この設計は 1 build に 1 セッション（シナリオの本数によらない）なので、ずっと安い。代わりに、1 セッションで調べられる範囲は 6 手番 × 8 操作に限られる。

### 1 変更あたり

| 形 | セッション | 見込み |
|---|---|---|
| `run`（attempt 1〜2） × 1 セッション | 1〜2 | 約 $0.3〜$4.8 |
| `replicate --k 4` × 1 セッション | 4 | 約 $1.2〜$9.6 |
| `replicate --k 4` × 2 セッション | 8 | 約 $2.4〜$19.2（上限 $15 で止まる） |

### 上限

- 1 回の呼び出し: $0.5（`CAPS.userCallUsd`）。時間は 5 分。
- 1 セッション: 6 手番（`USER_LIMITS.turns`）。よって 1 セッション最大 $3。
- 1 変更: `--max-cost`（既定 $10、`run` と同じ既定）。`user-judge` を何度打っても、その変更のユーザー役の支出（`runs/<id>/user-judge-cost.json`）を足して数える。下書きと build の支出とは別に数える。今の判定の上限を食わないためである。
- lap あたりの上限（$260）と lap 台帳は今までどおり効く。ユーザー役の呼び出しも台帳に役 `user-agent` で載る。
- 非常停止（STOP ファイル）も今までどおり効く。

- 4 依頼とも外部サービスの偽物を使うので、偽物を操るユーザー役の書き方も確かめられる。
- 1 build 2 セッション（ぶれを見る）で 32 セッション、約 $10〜$77。上限案は $60（4 依頼 × `--max-cost 15`）。悪い場合は上限で止まり、止まった依頼の残りの build は判定されない（比較表に出ない）。
- 前提: `.factory-lap11` の `work/<id>-rep/` が消されずに残っていること。残っていなければ、次の周の build に付ける。

## 何が言えないか（あらかじめ）

- ユーザー役は 6 手番 × 8 操作しか使わない。依頼の全部を試すとは限らず、「満足」は「試した範囲で依頼どおりだった」の意味である。
- ユーザー役は依頼の書き手そのものではない。依頼の読み方は、作る役・シナリオの下書き役と同じ系統（Claude）のモデルの読み方である。
- アプリの返事は作る役が書いたコードが出すもので、それがそのままユーザー役の指示に載る。返事の中の文がユーザー役の判定を曲げることはありうる（ユーザー役には道具が無いので、判定以外には何もできない）。作る役はユーザー役の存在を知らないが、狙って書かれたら防げない。比べる段階では記録して読むだけで、これが判定を決める前に考え直す。
- 偽物は、セッションの最初の操作より前にアプリが起動する。起動のときに外部サービスを呼ぶアプリは、その呼び出しに答えが設定されていない（404）。シナリオでは先頭の設定段が起動前に走るので、ここはシナリオと違う。
- 画面の操作の後、ユーザー役は 0.5 秒待ってからの画面を見る。シナリオのように、期待が満たされるまで 5 秒読み直すことはしない（ユーザー役には期待が無い）。遅く書き換わる画面は、古い中身に見えうる。
- 1 build 1〜2 セッションでは、ぶれの大きさは粗くしか分からない。
- 1 変更のユーザー役の支出は、呼び出しが終わるたびに書く。呼び出しの最中にプロセスが死ぬと、その呼び出しの支出はこの腕の上限（`--max-cost`）に数えられない（lap 台帳は呼び出しの前に予算を押さえるので、lap の上限には数えられる）。replicate の費用の記録と同じ限界である。
- 同じ変更の `user-judge` は同時に 1 つだけ走る（`runs/<id>/user/.lock`）。プロセスが死んで残ったロックは、人が消す。
- 偽物の上限（要求 100 件など）を超えたアプリは、偽物が通信を切る。その後の結果には、切ったことを書いてユーザー役に見せる。シナリオのように不合格にはしない。
- 記録の名前はモデルで分けるが、手番の上限や指示の文面を変えたことは名前に入らない（記録の `limits` には残る）。工場のコードを変えた後に続きを流すと、違う設定のセッションが同じ節に混ざる。比べる最中は工場を変えない。

## 実装（工場、factory#30）

- `src/user.ts`: ユーザー役の腕。指示の組み立て（`userInstruction`）、操作の形の確かめ（`checkAction`）、1 セッション（`userSession`）、コマンドの本体（`userJudge`）、比較表（`compareTable`）。
- `src/scenario.ts`: 1 つのアプリ（と偽物・画面）を止めずに操作を 1 つずつ送る `withSession` を足した。中身はシナリオの走らせ方（`withApp`、`send`、`startFake`、`openBrowser`）を使い回す。
- `src/adapter.ts`: 役 `user-agent` を足した（claude-opus-5-5）。作る役の書いたものを読む役なので、2 つ目の系統（Codex）は使えない。
- `src/limits.ts`: `CAPS.userCallUsd = 0.5` を足した。
- `src/cli.ts`: コマンド `user-judge`。`--model user-agent=<model>` も受ける。
- `src/lap.ts`: lap の段の一覧に `user-judge` を足した。
- テストは偽のモデルだけを使う（お金を使わない）。アプリを起動するテストは、ワーカーのサンドボックスでは入れ子の bwrap が使えないので落ちる（main でも同じ）。窓口がサンドボックスの外で `npm test` を回す。

## オーナーに決めてほしいこと

1. **ユーザー役が見るもの**: 依頼の文面 + インターフェース（名前だけ）。仕様の本文は見せない。
   - **おすすめ: このとおり。** 依頼に照らす判定は、仕様に照らす今の判定と別のものを測る。仕様を見せると、今の判定役と同じものを二度測ることになりやすい。代わりに「依頼の文面だけ」にすると、API のアプリではエンドポイントの名前が分からず、操作できない。
2. **判定の形**: `satisfied`（真偽値）+ 理由 + 問題の一覧。
   - **おすすめ: このとおり。** 今の判定の合否とそのまま比べられる。点数（1〜5 など）は、ぶれの読みが難しくなるので、比べた後に要ると分かってから足す。
3. **手番と操作の上限**: 1 セッション 6 手番、1 手番 8 操作、結果は 1 つ 1,500 字まで。1 回の呼び出し $0.5。
