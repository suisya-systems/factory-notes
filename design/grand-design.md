# L5 工場の全体設計（骨組み、2026-10-17）

## この文書の位置づけ

L5 の工場を作り始める前に、後から変えにくい線だけを先に引く。細部は決めない。決めていないことは各章の「試作で確かめること」（7 章は「未決」）に置く。

- L5 は、仕様を入れると動くソフトウェアが出てきて、途中で人がコードを書かずレビューも承認もしない状態（https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/ ）。
- 前提として覆さないこと: L5 を目指す、claude-org の外に作る、モデル呼び出しはアダプタで `claude -p` と Agent SDK を切り替える、予算はオーナーが費用の見立てを見て決める（[decisions.md](../decisions.md)）。
- 「既存スタック」（rondo / continuo / cadenza）、「rondo:D-0173」のような決定記録の番号、lap などの言葉は [用語集](../glossary.md) にある。
- 試作は decisions.md の「次の一手の提案」（未承認）の流れを 1 周回すものを想定している。提案が承認されないなら、この文書の「試作で確かめること」も宙に浮く。
- オーナーに決めてもらった分岐は、末尾の「決定」にまとめた。

## 1. 輪の全体

結論: 1 周は「1 件の変更」で、入口 → 作る → 確かめる → 出す → 本番を見る → 次の仕事、と進む。終点は「出荷済み」で、PR やマージではない。

### 決めたこと

| 段 | 何が起きるか | 次へ渡るもの |
|---|---|---|
| 入口 | 下書き役が仕様と隠しシナリオを書き、人が組として 1 回承認する | 作る役へは仕様だけ。シナリオは判定役へだけ |
| 作る | 作る役が仕様からソフトウェアを作る | 成果物の参照（作る役自身のテスト結果は参考扱い） |
| 確かめる | 判定役が隠しシナリオで成果物を判定する | 合否と、不通過のときの理由 |
| 出す | 出荷役が合格した成果物を出荷する | 出荷済みの印 |
| 本番を見る | 出荷したものの様子を読む | シグナル（障害の兆し、要望など） |
| 次の仕事 | シグナルを新しい入口へ入れる | 仕事の種 |

- 不通過のときは作る役へやり直しを返す。人には戻らない。やり直しの回数と費用は 4 章の上限で止まる。
- 既存スタックの終点は PR とマージ（rondo:D-0173 K1、[research/l5-gap-audit-2026-10-17.md](../research/l5-gap-audit-2026-10-17.md)）。工場はそれを終点にしない。

### 試作で確かめること

- 仕様だけを渡された作る役が、隠しシナリオをどれだけ通すか。
- 不通過 → やり直しが上限の内で収束するか。費用の見立ては「1 変更につき 3 回」を仮定しており、落ちてやり直すと倍増する（l5-gap-audit (b)）。
- 練習用アプリなら、「本番を見る」段をログとヘルスチェックで代用できるか。
- 本番シグナルを、下書き役がどう仕様とシナリオに変えるか（入口で人の承認を通すことは決定 2 で決まった）。

## 2. 役割と、見えてよいもの

結論: 役割は下書き役・作る役・判定役・出荷役の 4 つで止める。隠しシナリオは作る役の実行環境から届かない場所に置き、「見るな」という指示は保証として扱わない。

### 決めたこと

| 役割 | 見えるもの | 見えないもの |
|---|---|---|
| 下書き役（仕様） | 入口の依頼、本番シグナル、拡張する既存アプリの現コード（読むだけ） | — |
| 下書き役（シナリオ） | 入口の依頼、本番シグナル、拡張する既存アプリの現コード（読むだけ）、仕様の下書き役が出したインタフェース（名前と形だけ） | 仕様、仕様の下書き役の仮定 |
| 作る役 | 仕様、自分の作業場所、不通過の理由 | 隠しシナリオ |
| 判定役 | 仕様、隠しシナリオ、成果物（読み取りのみ） | 本番シグナル、作る役の作業場所（成果物へは書き込めない） |
| 出荷役 | 合格の印、成果物 | 隠しシナリオ |

- 隠しシナリオはコードベースの外に置く。StrongDM も同じく、エージェントが合わせ込めないようシナリオをコードの外に置いている（https://factory.strongdm.ai/ 、[research/software-factory-landscape.md](../research/software-factory-landscape.md) §2）。
- 隠しの保証は、作る役の実行環境からその保管場所へ到達できないこと（別の保管場所と権限）で取る。プロンプトでの指示は保証にしない。
- 下書き役と作る役は別のセッションで動かす。同じセッションだと文脈を通じてシナリオが漏れる。
- 下書き役は、仕様とシナリオを別々のセッションで書く。同じ文脈で書くと、シナリオで確かめたいことを仕様にも書いてしまう。そうなると、隠しても判定は「仕様どおりに作れたか」の確認になる（1 周目では、15 本のうち 14 本が仕様に書いてあった）。
- 拡張の依頼では、両方の下書き役に既存アプリの現コードを見せる。見せ方は、読むだけで、書き換えられない形にする。作る役は既存アプリの上で作業するので、見える範囲は作る役と変わらない。
- 仕様の下書き役からシナリオの下書き役へ渡すのは、名前と形のブロック（[インタフェース](../glossary.md#工場の言葉)）だけにする。ブロックに入るのは、エンドポイント、パラメータ名、フィールド名、一覧の形、競合を見分ける値の置き場所である。振る舞いの規則（状態コード、条件の組み合わせ、既定値、境界）は渡さない。仮定の文も渡さない。
  - 名前を共有しないと、名前の違い（`?tag` と `?tags` など）でシナリオが落ちる。不通過の理由には値を含めないので、作る役は隠れた名前を知りようがなく、やり直しが原理的に収束しない。
  - 仮定の文は、当初は渡していた。2 周目の最初の下書き（[変更 id](../glossary.md#工場の言葉) memo-tags-1）では、仮定に仕様の規則がほぼすべて入っており、14 本すべてが仕様から読み取れた。このため、仮定の文は渡さないことにした（2026-10-17、オーナー判断）。
- シナリオが仕様から読み取れるかは、下書き役の自己申告ではなく、別の手続き（[独立した分類](../glossary.md#工場の言葉)）で判定する。判定するのは、仕様と既存コードだけを見た別セッションである。このセッションには、シナリオの期待値・名前・要約を見せない。このセッションが各要求への応答を予測し、シナリオの期待値と機械的に照合する。結果は入口の要約に載せる。
- 仕様とシナリオが食い違うものは、入口の要約に「[食い違い一覧](../glossary.md#工場の言葉)」として載せる。一覧は、仕様と食い違うものと、仕様が決めていないことを求めるものの 2 部に分ける。工場は自動で直さない。承認するか出し直すかはオーナーが決める。
- 判定役から作る役へ返す不通過の理由には、シナリオの本文を含めない。
- 出荷役は判定の結果以外を根拠に動かない。

### 試作で確かめること

- 不通過の理由をどこまで詳しく返すか。案は (a) 合否だけ、(b) 落ちたシナリオの要約（本文なし）。詳しいほど収束しやすいが、漏れも増える。既定は (b) で始め、通過率と漏れ具合を見て決める。
- 出荷役はモデルを呼ばない手続きで足りるか（推測では足りる）。
- 本番の様子を読んでシグナルに変えるのは、下書き役か、モデルを呼ばない別の手続きか。役割の数に効く。
- 隔離は「別の保管場所 + 作る役の作業ディレクトリの外」で足りるか。
- 独立した分類が、仕様から読み取れない振る舞いを十分な本数含む下書きを作れるか。2 周目の memo-tags-2（仮定を渡さない形）の結果は suisya-systems/factory の docs/lap-2-report.md にある。

## 3. 人が関わる場所

結論: 人が関わるのは、入口の承認と緊急停止の 2 か所だけ。それ以外で工場から人へ戻る経路は作らない。

### 決めたこと

- 入口: AI が仕様と隠しシナリオを下書きし、人は「これで完成と言える」と承認するだけ。人に手書き・暗記・コピペを求めない（2026-09-14 にオーナーが明言した方針）。
- 承認は仕様とシナリオの組に対して 1 回。承認のあと人が中身を直すことはしない。直したいなら新しい入口として出し直す。
- 承認した組はバージョンを固定し、工場の役割（下書き役を含む）からは書き換えられない。判定にはどのバージョンを使ったかを記録する。
- 本番シグナルから生まれた仕事もこの承認を通す（決定 2）。
- 工場から人への質問経路を作らない。下書き役がわからないことは「仮定」として仕様に書き、人は仮定ごと承認する。既存の rondo には人へ戻る経路が 19 系統あり、ワーカーの質問は「沈黙では答えない」と決めている（rondo:D-0098 r4、l5-gap-audit「距離の要約」3）。それは持ち込まない。
- 上限で止まったときは失敗として終える。「再開しますか」と人に聞く状態は作らない。止まったことの通知は出してよいが、返事を待たない。
- 失敗で終えた変更を、工場が自動で入口へ入れ直すことはしない。入れ直すと上限が意味を失う。続けるなら人が新しい入口として出す。
- 緊急停止は、人がいつでも工場の外から押せる。

### 試作で確かめること

- 手書き・暗記・コピペなしで承認できる見せ方（1 画面で、仕様の要点・シナリオの数・仮定の一覧が見えるなど）。
- 仮定が増えたとき、人が読まずに通すようにならないか。承認を細かく分けると人へ戻る経路が復活するので、分けずに見せ方で解く。

## 4. 歯止め

結論: 止まる条件は 3 つ（1 変更の費用上限、やり直し回数の上限、緊急停止）で、どれも失敗として終える。規則を変えられるのはオーナーだけで、工場自身は変えられない。

### 決めたこと

- 費用上限は「1 変更あたり」と「全体」の 2 段。全体の額はオーナーが決める（[decisions.md](../decisions.md)）。
- 費用は 4 役すべてを計上する。既存スタックは計上に穴がある（reviewer の費用が入らない、drafter の費用が scope 支出に入らない、Codex の lap に上限がかからない。l5-gap-audit 部品 9）。計上に穴があると上限は守れない。
- 規則（上限、止まる条件、隠しシナリオの置き場所と権限）は工場の外に置き、工場の役割からは書き換えられない。変えるのはオーナー。
- 緊急停止は工場のプロセスの外から効かせる。工場の中のフラグには頼らない。既存スタックには kill switch が無い（l5-gap-audit 部品 7）。

### 試作で確かめること

- `claude -p` の 1 呼び出しごとの費用を、アダプタの中で取れるか（未確認）。
- 1 変更の実費が、見立ての「1 変更 $7〜24」と「$30〜120」のどちらに近いか（l5-gap-audit (b)）。
- やり直し回数の上限をいくつにするか。

## 5. 土台

結論: モデル呼び出しはアダプタ 1 か所に閉じ込め、アダプタの外には CLI 固有の形（コマンド引数、出力の形、セッションファイル）を一切出さない。

### 決めたこと

- アダプタの入出力は、特定のモデルや CLI に依存しない言葉で書く: やらせる仕事、作業場所、許可、上限、結果、費用。
- CLI の引数の並びを、設定・保存形式・許可リストに出さない。continuo では起動の指定 `cli_args` が Claude の引数の形のまま保存・照合され、Codex 用アダプタもそれを読み替えていた（continuo:src/workspace/materializer.ts:1515-1521, continuo:src/control_plane/lap_run_intent.ts:197-203, continuo:src/session/codex_cli_provider.ts:663-683、[research/adapter-boundary-audit-2026-10-17.md](../research/adapter-boundary-audit-2026-10-17.md)）。
- アダプタの外から、セッションファイルなどアダプタの内部の物を読まない。rondo は continuo のセッションファイルを直接読んでいた（rondo:src/continuo/transcript.ts、同 audit）。
- 役割ごとに別のアダプタを作らない。役割の違いはアダプタへ渡す内容の違いで表す。rondo では drafter と reviewer がアダプタを通さず `claude -p` を直接起動していた（rondo:src/access/forge.ts:2678-2750、同 audit）。
- 漏れの見張りは import 文だけでなく、設定と保存形式も対象にする。continuo の見張りテストは import 文しか見ておらず、引数の形の漏れを検出できなかった（continuo:test/gate_item11/no-provider-detail-leaks.test.ts、同 audit）。

### 試作で確かめること

- アダプタに最低限要るものは何か。audit で未確認のまま残った 3 点（起動前にセッション ID を決める、SIGTERM のあと結果を読む、引数の許可リストと同じ意味の制限）が、工場で本当に要るか。
- 試作では Agent SDK への差し替えまでは試さない。差し替えやすさは、上の境界を守ることで確保する。

## 6. 既存スタックから持っていくもの / 持っていかないもの

結論: 並列、費用上限、作業者の囲い込みといった「流れの部品」は持っていく。人が確かめる前提で決めた規則は持っていかない。L5 から遠い一番の理由は、部品の不足よりその規則のほうにある（l5-gap-audit「まず結論」）。

### 決めたこと

持っていく（使う場所）:

- continuo の作業者の囲い込み: 2 章の作る役の実行環境。隠しシナリオに届かない環境を作るのに使う。continuo の起動が fencing と workspace を通っていることからの推測で（continuo:src/fencing/spawn.ts:550-562, continuo:src/workspace/materializer.ts:1515-1521、adapter-boundary-audit）、隔離の強さは確かめていない。
- continuo の並列実行と、lap の費用上限 `--max-budget-usd`（continuo:lap/cli.ts:191-196）: 1 章の「作る」と 4 章の 1 変更上限。
- rondo の自動投入（flow pickNext / order tick、rondo:flow.ts:209-325, rondo:host.ts:375-457）の考え方と、scope 予算の 3 軸（期限・lap 数・費用、rondo:scope.ts:504-534）: 1 章の「次の仕事」と 4 章。ただし approver（rondo で関門に答える人として指名された人。[用語集](../glossary.md#流れの言葉主に-rondo-と-continuo)）必須の部分は外す。

持っていかない:

- 人へ戻る経路すべて: approver の指名必須、plan / risk の人承認（continuo:D-1121 決定5）、lap の終わりの人向けゲート（continuo:D-0056 決定2）、質問を人へ送る経路（rondo:D-0098 r4）、任せる範囲の拡大は人の答えでだけ（rondo:D-0064 r3.2, cadenza:D-0036）、止まったときの終了は人（rondo:D-0068 / D-0195）。
- 終点を PR とマージに置く決定（rondo:D-0173）と、release・外部送信を都度人が承認する閉リスト（rondo:D-0064）。
- 非決定的な判定を退けた決定（rondo:D-0019 r7 / D-0029）。StrongDM の「満足度」による判定（landscape §2）と正面から衝突する。
- 既存の決定記録そのもの。工場は自分の決定記録を持つ。

### 試作で確かめること

- 1 周目は既存スタックを使わずに回し、2 周目で部品を差し込む（decisions.md の提案と同じ順）。
- continuo の囲い込みを、Claude の引数の形に触れずに外から呼べるか。continuo#275（起動の指定をモデル非依存にする Issue）の直し方次第（[actions.md](../actions.md)）。
- 部品を依存として呼ぶか、コードを写すか。依存なら continuo#275（起動の指定をモデル非依存にする Issue）の解決待ちになり、写せば二重に保守することになる。2 周目に入る時点で決める。

## 7. アプリごとの仕様リポジトリ

結論: 置き場所は 4 つに分ける。工場リポジトリ、工場全体の台帳リポジトリ、アプリごとの仕様リポジトリ、アプリリポジトリである。仕様の正本は仕様リポジトリの「今の仕様」1 つにする。以下は 2026-10-18 にオーナーと合意した方向で、決定ではない。

### 方向（オーナーと合意、決定ではない）

置き場所:

| 置き場所 | 数 | 持つもの |
|---|---|---|
| 工場リポジトリ | 1 | 機能だけ（役割、判定、隔離、モデル呼び出し口） |
| 台帳リポジトリ | 1 | アプリの一覧、アプリと仕様リポジトリとアプリリポジトリの対応、全体の予算、費用の記録、各回の記録 |
| 仕様リポジトリ | アプリごとに 1 | 今の仕様（正本）、承認された仮定、隠しシナリオの蓄積、判定役だけが使う外部サービスの偽物 |
| アプリリポジトリ | アプリごとに 1 | コードだけ |

- 台帳は独立したリポジトリにする。工場を他の人に配れるようにするためで、台帳や状態を工場に抱き込むと、工場を配布できなくなる（2026-10-18、オーナー判断）。工場の作業ディレクトリに 2 つのファイルを置いて始める案も検討したが、同じ理由で採らなかった。
- 費用の記録は、モデル呼び出し 1 回につき 1 行を追記するだけにする。2026-10-18 時点の工場の lap 台帳は、lock を取らずに読んで書き戻しており、並列に耐えない（factory:src/limits.ts:47-54）。
- 判定役の理由や結果は、シナリオを引用しうる（factory:src/roles.ts:219-221）。各回の記録にはそれらが入る（factory:src/run.ts:84-85）。これらは台帳に載せないか、載せるなら隠しシナリオと同じ保護の下に置く。
- 2026-10-18 時点の工場の作業ディレクトリ（vault、runs、releases。factory:src/vault.ts:26-34, factory:src/ship.ts:27）は、1 アプリ分の仕様リポジトリに近い形をしており、仕様リポジトリへの移行元になる。ただし今の仕様の正本はまだ無く、変更ごとに `spec.md` を書いている（factory:src/vault.ts:44-53）。
- 仕様リポジトリは作る役から届かない場所に置く。2026-10-18 時点の工場は、$HOME の下にあるディレクトリにだけ隔離の保護をかけ、$HOME の外なら起動を拒む（factory:src/sandbox.ts:22-29、拒否は :26）。
- 秘密情報は仕様リポジトリに置かない。

ルール:

- 承認は「差分を当てた後の仕様、新しいシナリオ、仮定、仕様リポジトリの HEAD のコミット」の組に結びつける。差分の文面だけに結びつけると、古い仕様に向けて書いた差分が新しい仕様に当たってしまう。2026-10-18 時点の工場は、5 つのファイルのハッシュに承認を結びつけている（factory:src/vault.ts:15, factory:src/vault.ts:56-64）。
- 出荷は、アプリを出荷してから、仕様リポジトリに仕様の差分と出荷したアプリのコミットを記録する、の順にする。仕様リポジトリにコミットしていない変更が残っているとき、または仕様リポジトリに記録したアプリのコミットと出荷済みのアプリのコミットが合わないときは、次の run を拒む。出荷の途中で失敗したとき、仕様リポジトリとアプリが食い違ったまま進まないようにするためである。
- 作る役に実際に渡した仕様の切り出しは、変更ごとに凍結して残す。正本はあくまで仕様リポジトリの今の仕様である。
- 外部サービスの偽物は 2 つに分ける。作る役に渡すのは形だけの stub で、振る舞いを持つ偽物は判定役だけが使う。
- 同じアプリへの変更は 1 本ずつ流す。下書きはそのアプリが空いてから始める。こうすると、承認したバージョンが古くならない。別のアプリへの変更は並列にしてよい。ただし、その前に費用の記録を追記式にする。
- 仕様リポジトリの書式は Open Knowledge Format（OKF）から性質だけを借りる。使うのは「Markdown ファイルのディレクトリ、入口の `index.md`、ファイルどうしのリンク」である。OKF は Google Cloud が 2026-06-12 に v0.1 として公開した書式で、バンドルは YAML frontmatter 付きの Markdown ファイルのディレクトリである（https://ppc.land/googles-okf-wants-to-be-the-lingua-franca-for-ai-agent-knowledge/ ）。`index.md` は各ディレクトリの任意の入口で、概念どうしは普通の Markdown リンクでつなぐ（https://agentic-ai.readthedocs.io/en/latest/Standards/open-knowledge-format/ ）。OKF が決めているのは相互運用のための包み方だけで、中身の形は決めていない（https://heise.de/-11332310 ）。`type` の体系と道具は未決とする。

### 未決

- 漏洩経路。作る役は、不通過の要約をコードやコメントに書ける。出荷すると、次の変更の下書き役がそれを「既存アプリの現コード」として読む（2 章の下書き役の入力）。シナリオが積み上がるほど、シナリオの期待が仕様に染み込みうる。2026-10-18 時点の工場は、通過率を「仕様に書いてある」と「書いていない」に分けて記録している（factory:src/run.ts:21）。仕様に書いていないシナリオの通過率が変更を重ねてどう動くかを見る。

仕様が巨大になったときの扱いも決まっていない。調べた他の仕組みは [research/large-spec-handling.md](../research/large-spec-handling.md) にある。

- (a) 下書き役が今の仕様を全部読みきれない。
- (b) 作る役に何を渡すか。全部を渡すか、関係する領域だけを渡すか。関係する領域だけにすると、見落としが出る。
- (c) 過去のシナリオを流し直す時間が増え続ける。

対処の案:

- 仕様を領域ごとのファイルに分け、目次（`index.md`）を置く。
- 作る役には、変更が触れる領域と、そこからのリンク先だけを渡す。
- 他の領域との食い違いは、入口の確認（2 章の食い違い一覧など）で探す。
- (c) 隠しシナリオは決定的テストとして走らせる（決定 1）ので、1 本ずつは安いと見込んでいる。件数が増えたときの所要時間は測っていない。

## 決定（2026-10-17、オーナー）

2026-10-17 の初版で「要判断」として並べた 2 件を、オーナーが決めた。選ばなかった案と理由も残す。記録は [decisions.md](../decisions.md) にもある。

### 決定 1: 判定の形は、試作では決定的テスト + LLM 判定 1 回

- 採用 (a): 隠しシナリオを決定的なテストとして走らせ、LLM の判定を 1 回付ける。見立ては 1 変更 $7〜24、$500 で 20〜70 変更（l5-gap-audit (b)）。安く、LLM の判定が 1 回だけなので (b) よりぶれが小さい。
- 不採用 (b): エージェントがユーザー役になって動かし、満足度で判定する。見立ては検証だけで 1 変更 $30〜120、$500 で 4〜15 変更（同）。StrongDM の満足度判定は (b) に近く、L5 の本来の姿に近いのは (b) だが、試作には費用が重い。
- この決定は試作についてのもの。

### 決定 2: 本番シグナルから生まれた仕事も、入口で人の承認を通す

- 採用 (a): 本番シグナルは下書き役が仕様とシナリオに変え、通常の入口として人の承認を通す。3 章の「人は入口で承認する」とそのまま揃い、本番の情報がシナリオを経て作る役へ漏れる経路も入口で一度切れる。
- 不採用 (b): 本番シグナルから自動で次の仕事を始める。輪が人の承認を待たずに閉じ、Factory 社のいう「監視から新しいシグナルが出て最初に戻る」輪（landscape §3）に近いが、人が入口で承認するという方針と食い違う。
- この決定により、輪は入口で人の承認を待つ。自動では閉じない。

## 試作で最初に確かめる、一番危うい前提

1. 「作る役にシナリオを見せなければ、合わせ込みは防げる」。仕様とシナリオを同じ系統のモデルが下書きするので、シナリオは仕様から推し量れる可能性がある（推測）。そうなら、隠しても判定は作る役の思い込みと同じものを測るだけになり、L5 の信頼の要が崩れる。試作では、隠しシナリオの通過率を「仕様に書いてある振る舞い」と「書いていない振る舞い」に分けて見る。
2. 「人に戻らなくても、やり直しで収束する」。収束しないと上限で失敗終了するばかりで、工場は何も出さない。人に戻す経路を作らないと決めた以上、ここが崩れると代わりの逃げ道が無い。
3. 「費用を全量計上できる」。計上できなければ 4 章の上限は守れず、オーナーが予算を判断する材料も作れない。既存スタックは計上に穴が 3 つある（l5-gap-audit 部品 9）。
